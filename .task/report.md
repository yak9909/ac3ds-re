## 結論と根拠の要約

- ACNL-F0726：UI 3,866,624 B、graphic FCRAM 7,008,256 B、dG3d 235,520 B、VRAM A/Bは別管理。ゲームの正規alloc/freeは存在する。手紙時の空きは未測定。

- ACNL-F0728：画像cacheはaccessor単位。hitは無確保、missはロード＋156 B entry。所有元破棄後も同じ参照を保持できる仕組みではない。
- ACNL-F0729：通常フォントは別FontHeapにあるA4 128×128×154枚。Mgrの状態付きgetterから無確保で参照可能。ASCII・ボタン記号を確認したが、全場面の常駐とgohan全文字の充足は未確定。
- ACNL-F0730：nw::lytは6段TEV、通常画像/独立UVは3組。Repeat・SRT・アニメ・二色補間を板の記録経路から指定できる。6層合成後clampの完全再現とは別問題。
- ACNL-F0731：タイトル実資源は16×16 A4/L4各128 Bを6枚のPictureで共有する。4枚のUVだけでなく親位置も150フレームで動く。材質の明示TEV段は0。

Sは**1フレームの実際の2冪テクスチャ容量**。S=2,048 Bは例えば64×64 L4、S=8,192 Bは例えば128×128 L4であり、今の帯の寸法だと確認した数ではない。CPU更新・元フォント維持の一般式は `98,816 + 32,768 + 2S`、ゲームフォントなら `33,280 + 32,768 + 2S`。削減量はそれぞれ `163,840−2S`、`229,376−2S`。CPUが読む元画像2枚はプラグイン側のデータでよく、ここでUIヒープに256 Bを追加する必要はない。

自作UI 32,768 Bを丸ごとゲームのボタン画像へ置換できる証拠はないため、どの推奨案にもこの削減は織り込まなかった。ボタン記号をゲームフォントへ替える余地はあるが、自作UIの角・窓・キー全ての代替にはならない。

**推す組み合わせと実装前の判定点**

1. まず150フレーム分の163,840 B保持を、同じCPU合成式による現在フレーム2面へ替える。150段階の時刻・画素解像度・丸めを維持すれば、clampや二色化をGPU式へ変える必要がない。Sを実装から確定し、CPU時間とGPU完了待ちを測る。不要な表示時には生成もしない。
2. 窓を閉じたら、その帯2面と窓の地32,768 Bを最後のGPU参照完了後に返す。通知が必要な字・UI等の常駐分とは寿命を分ける。現在の契約で既に返しているなら、その点は維持する。
3. 字形の変更を受け入れられる場合にゲームフォントを共有する。全使用文字をCMAPで検査し、未収録文字だけ小さな自作atlasへ置く案もある。通常CMAPにU+2713が無いので「日本語フォントなら全部揃う」とはしない。時計などのPaneから一度拾って永久保持せず、Mgrの状態・所有世代を確認する。
4. VRAM/graphicHeapは測定後の補助候補。MemoryMgrの正規alloc/freeと同じ所有規則・転送経路を使う。libctruのvramAllocをそのままゲーム内へ持ち込むとゲームのVRAM占有を知らない。Luma Unsafeを使う案は除外した。

GPU案については、二色補間そのものは可能。TEVのINTERPOLATEで定数色と頂点色を端点、L4の色またはA4のalphaを重みにできる。ただし6段あっても通常samplerは3組で、同一画像を別のUVで6回読むことはできない。複数板で合成後にclampするには中間面が要り、L4/A4を直接render targetにはできない。通常16/32 bpp面、転送、GPU同期、再記録を別に扱う必要がある。各層に先に二色化/clampを配るだけで現在式と等しいとはいえない。

clampを含むGPU式も検証候補はある。例えば3サンプルまでなら、正の重みの和を1以下に収めて `T0*w0` → `+T1*w1` → `+T2*w2` → `−閾値` と倍率1/2/4 →二色補間、という5段の構成を検討できる。中間で飽和させず最後に必要なclampを置く発想である。これは今回の6層と同値だと確かめた構成ではなくLOWの案。素材の対称性で実効サンプル数を減らせるか、GPUの丸め、CPU式との一致を別途検査する必要がある。

**手紙の計算**

```text
今回の依頼の標本:
  61,924 + 297,728 = 359,652 B  （自作分が無いとした未確保画像の前）
  359,652 − 131,072 = 228,580 B （画像payloadだけを引いた概算）

提示された内訳:
  98,816 + 196,608 = 295,424 B
  297,728 − 295,424 = 2,304 B の未説明差

停止時標本をそのまま使う不足:
  228,580 − 297,728 = −69,148 B
  字形だけ65,536 B返しても −3,612 B

閉じて背景196,608 Bを返す算術なら:
  228,580 − (297,728 − 196,608) = 127,460 B
  さらに字形65,536 Bを返すと192,996 B
```

この逆算は「297,728 Bがその時点の同じheapへの純増分で、返却しても他の確保が変わらない」ことが前提。2,304 B差の由来は未確認。便箋の画素要求自体もAllocatorが128 B上乗せし、画像メタデータとExpHeap管理費が別にある。従って228,580 Bは再測定された安全予算ではない。旧標本の227,476 Bとの差1,104 Bも、同じ場面・同じ所有状態の誤差として丸めない。
