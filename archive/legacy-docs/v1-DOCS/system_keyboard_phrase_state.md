# 内蔵キーボードのUI変換範囲と文節結果（F-395）

F-397追記: 予測mode0の複合候補は別の内部文節リストを使う。
今回の実機入力でapp+0x2E6DCに3件、件数app+0x2F9C4、読み境界0,4,7,11を取得した。
本書のmode1文節件数が0でも「文節情報なし」とは限らない。
詳細[未確定予測候補の順位と内部文節](system_keyboard_prediction_segments.md)。

## 結論

解析したUI経路は、F-363で直接呼んだ連文節APIと同じ設定ではない。
`0x1031CC → 0x10996C → 0x111FD4(mode=1) → 0x1145AC`では
最下層のR3へ`1`を渡す。直接連文節試験は`55`を渡していた。
`0x135988`は値1で単文節側へ分岐する。UI経路全体を連文節変換とみなしてはいけない。
confidence MEDIUM（複数の静的証拠＋原本ARMのPC実行、実機の変換モードは未観測）。
全番地は提供された日本語SWKBD用。ACNL用ではない。

## 原本ARMによる比較

実際のUI wrapper `0x10996C`をPC上で実行した。mutex enter/leaveのみモック。
辞書は従来のProbeと同じ再構成状態で、利用者個人の学習データではない。

| 入力 | UI呼出経路（R3=1） | 直接連文節API（R3=55） |
|---|---|---|
| かんじ | 感じ | 感じ |
| わたしはねこがすきです | わたしはねこがすきです | 私は／猫が／好きです |
| きょうはいしゃにいく | きょうはいしゃにいく | 今日は／医者に／いく |
| はしをわたる | はしをわたる | 橋を／渡る |

UI経路はいずれも結果1件、読み長は入力全長。生成recordの復号と、別の取得API
`0x1181D0(ctx, output, 0, 0, 112)`の出力が一致する。
別UIモードや編集操作による範囲分割が存在しない、と結論したものではない。

## 保存位置（app = [0x001B7780]）

UIから2回+4するため、変換contextはapp+8。

| appからのoffset | 内容 | 根拠 |
|---|---|---|
| `0x00008` | 変換mode（0=予測側、1=今回の単文節側） | 0x111FD4、0x1181D0 |
| `0x0000D` | 結果ready | 0x112254、0x118204 |
| `0x0000E` | UTF-16入力長u16 | 0x112080 |
| `0x00014` | エンジン内部UTF-16BE入力 | 0x112068、0x1121FC |
| `0x3016C` | 先頭結果の読み長byte | 0x112244 |
| `0x30170` | 予測/代替候補record列 | 0x1181D0、F-389 |
| `0x36890` | 単文節/連文節結果record列、88 bytes/件 | writer 0x112204、reader 0x11833C |
| `0x37B78` | 予測/代替候補の件数u16 | 0x118258、0x1183DC |
| `0x37B7A` | 文節結果件数u16 | 0x112210、0x118308 |

recordの種別下位4bitが1/4の場合、読み長は
`(u16(record+8)&0x7F) + (u16(record+0x50)&0x7F)`。
`record+4`が読みのポインタ。`0x150898`の命令列で確認した。
他種別のrecordへこの読取方法を無条件に適用しない。

## 既存の実機「かんじ」dump

mode=0、ready=1、予測候補17件、文節結果0件、先頭読み長0、文節record先頭88 bytesはゼロ。
したがって、このdumpは予測候補取得の証拠であり、文節境界の証拠ではない。
mode=0では文節領域が過去値を持つ可能性もあるため、件数だけで文節を公開しない。

## UIが扱う変換対象範囲

editor = [0x001B777C]。通常の入力取得側`0x1031CC`ではapp+0x69588のeditorも使う。
両ポインタが同じ対象かは実機取得時に照合する。

`0x15ADC8`の式:

```
start = u32(editor+0x14) - u32(editor+0x24) - u32(editor+0x28)
length = u32(editor+0x28)
text = [editor+0x10] + 2*start
```

取得側0x103230/0x103238と、描画側0x1891C0のstart<=index<start+length判定で独立に一致する。
editor+0x2Cが非ゼロの分岐はeditor+0x2EのUTF-16文字列を参照するため、通常式だけで
全状態を説明しない。`+0x14/+0x24`個々の用途名は未確定。
この区間はUIの変換対象範囲であり、全文を自動分割した文節一覧とは区別する。
