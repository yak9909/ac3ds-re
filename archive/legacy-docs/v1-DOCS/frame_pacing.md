# フレーム制御（FPS とゲーム速度）

確定した知見。根拠は `RE/FINDINGS.md` **F-356 / F-357**、
解析メモは `scratchpad/MEMO_f356_gamespeed.md` / `scratchpad/MEMO_f357_fps_vs_speed.md`。

**結論から: この設計では FPS とゲーム進行は同じ 1 個のつまみで、切り離せない。**

## 2. フレームワークオブジェクトの欄

| off | 意味 |
|---|---|
| **`+0x70`** | **1 フレームに要る VBlank 数。実機で `2` を確認（= 30fps）** |
| **`+0xA0`** | 前フレームを提示したときの VBlank カウンタ（★スピードチートの差し替え先） |
| **`+0xA8`**（64bit） | **フレーム周期**（待ち込み。tick） |
| `+0xB0`（64bit） | `Framework_ProcOneFrame` が Draw の直後に刻む tick |
| `+0xB8`（64bit） | `Framework_WaitAndPresentFrame` が末尾に刻む tick |
| `+0x148` / `+0x14C` | ダブルバッファの索引 / フレーム数の飽和カウンタ（3 まで） |

`qword_96F3F0` = **tick 周波数。実機で 268,111,856 Hz**。1 VBlank = 16.715 ms（59.8261 Hz）。

## 3. なぜ切り離せないか

1. **メインループが 1:1。** `Framework_ProcOneFrame` の 1 反復が
   Calc 1 回 → Draw 1 回 → 待ち → 提示 1 回。別レートで回す機構が無い。
2. **Calc へ経過時間が渡らない。**
   `sub_54B79C` -> `sub_543BD0` -> `MethodTree_WalkAndInvoke(node)` で**引数はノードだけ**。
   `+0xA8`（フレーム周期）を読むのは `Framework_GetFPS` **だけ**で、表示用。

## 4. 実機計測（2026-09-08）

フレームワークオブジェクト = `0x32939880`（この boot）。

| 設定 | 周期 | fps | 待ち+提示 |
|---|---|---|---|
| `+0x70 = 2`（素） | 33.837 / 33.652 / 33.789 ms | 29.55 / 29.72 / 29.60 | 17.42 / 17.78 / 17.62 ms |
| **`+0x70 = 1`（1.5 秒の実験）** | **17.770 ms** | **56.28** | **1.743 ms** |
| `+0x70 = 2`（戻したあと） | 33.751 ms | 29.63 | — |

- **周期の比 33.751 / 17.770 = 1.899 倍**。論理:提示が 1:1 なので**進行も 1.9 倍速**。
- `calc+draw` の実作業 = **14.935 / 15.634 ms（平均 15.28 ms）**
  = 1 VBlank 予算 16.715 ms の **91.4%**。だから `+0x70=1` でも 60fps に届かず 56.3fps 止まり。
- ★この 15.28 ms は**いま映っている 1 場面のもの**。場面をまたぐ一般化はしていない。

### 測り方（コード注入なし）

停止した瞬間の `+0xB0` と `+0xB8` の前後関係で読み分ける:

| 条件 | 意味 |
|---|---|
| `+0xB8 > +0xB0` | 同一フレームの **待ち+提示** = `+0xB8 − +0xB0` |
| `+0xB8 < +0xB0` | 待ちの最中に止まった。**calc+draw** = `+0xB0 − +0xB8` |

★**止めたまま置くと `+0xA8` に停止時間が混ざる**（`svcGetSystemTick` は止まらない）。
必ず「走らせる → 時間切れで止める → 読む」を 1 往復にすること。

## 5. できること / できないこと

| 案 | 判定 |
|---|---|
| `+0x70 = 1`（データ 1 語） | 60fps を狙えるが**進行も 2 倍**。この場面では実測 56.3fps |
| `0x0054C6E8` を `E3E004FF` に（AR チート） | 待ちが全部消える。**同じく進行も速くなる** |
| ループをフックして Calc を 2 回に 1 回 | 提示は増えるが**同じ絵の 2 度出し**。30fps と区別できない。**無意味** |
| ゲーム側の毎フレーム増分を全部半分に | 数千か所 + romfs のアニメ資源も 30fps 前提。**非現実的** |
| フレーム間補間 | エンジンに仕組みが無い。**不可** |

★**遅くするのは綺麗にできる。** `+0x70` は整数の VBlank 数なので
**3 = 20fps / 4 = 15fps と 1/N のスローがデータ 1 語で作れる**（コード改変なし）。

## 6. AR チート「ゲームスピード」

`DOCS/ar_codes.md` の「ゲームスピード（フレーム制限の撤廃）」を参照。
`0x0054C6E8` の素は **`E59400A0` = `LDR R0,[R4,#0xA0]`**、
ON は `E3E004FF` = `MVN R0,#0xFF000000` → `R0 = 0x00FFFFFF`。
経過 VBlank が常に 20 億超になり、待ちループに一度も入らない。

★キーマスクは `0x110`（R+→）/ `0x120`（R+←）が正しい。
`0x012` / `0x022` は **B+→ / B+←** になる。
