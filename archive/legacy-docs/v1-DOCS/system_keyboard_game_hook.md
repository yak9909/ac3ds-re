# とび森キーボード入口から内蔵キーボードを要求する（F-382）

**対象変更（F-383）:** 利用者指定でフレンドチャットは使わず通常チャットを対象にする。
現在の入口は`0x001938AC`。詳細は[通常チャット入口](system_keyboard_normal_chat.md)。
以下のmode3の終了契約は比較資料として残す。通常チャットは送信後に入力を継続するため、そのまま流用しない。

2026-09-09。依頼の2点――入口の実行文脈と、文字列・取消・終了状態の返却――を調べた。
静的解析はidalibの`code.bin.i64`、分岐の独立照合はPC上の原本ARM実行。
実機への接続・状態照会・書込み・再開、ビルドは行っていない。

**方針は「ゲームのキーボード入口をフックして要求を記録し、既存APT位置で内蔵キーボードを起動、
ゲーム側の結果通知と子画面終了処理へ戻す」。**
入口で同期的にAPT待機へ入る安全性は証明できていない。
結果の具体的契約を追えた最小対象は`BsMenuFriendChat`（mode 3）で、全入力画面の置換成功という結論ではない。

## 1. フックする入口と実行文脈

### 共通入口は子画面を作るAPI

`UiScreen_OpenById` (`0x00528C60`) のR0が`0x23E`の呼出しが対象。
R1は親画面。戻り値R0は`BsSkb*`であり、確定文字列やボタン番号ではない。

最小対象の命令は次のとおり。

```text
0x002AE3C0  BsMenuFriendChatの初期化
  mode=3、最大32、改行flag=0、出力先などを設定
0x002AE474  BL UiScreen_OpenById
0x002AE478  STR R0,[R4,#0x7C]  ; 子画面を親に保存
```

**呼出し命令は`0x002AE474`。逆コンパイルの代入行に付いた`0x002AE478`と区別する。**
共通APIでIDと親を識別するか、この単一callsiteを対象にする。最初の試験は対象を限定する。

ほかにもカタログ`0x0021C24C`、掲示板用設定の`0x00285C94`が同じIDを使う。
両者は返された子の`+4424`にも書き込む。子の生成を省いて0やダミーポインタを返すだけでは代替できない。

`UiScreen_OpenChild` (`0x0051EC58`) は親が非NULL、parent+15が0、parent+14が2でないことを要求する。
`0x0051EF38`は子を複数の管理表へ登録し、初期化と親への連結を行う。
`BsSkb`の初期化`0x0057E72C`は資源読み込みを複数段階で行う。
入口から戻っただけでは初期化完了や操作可能を意味しない。

### APTの既存呼出し位置はCalc/Drawの後

F-357のフレーム制御と、今回のvtable/呼出しコードを照合した。

```text
UlcdFrameworkの1フレーム
  Calc（vtable+0x6C）
  Draw（vtable+0x68）
  リスト処理（vtable+0x78 = 0x0024EF10）
    0x0024EF84 → 0x005CE28C
      0x005CE29C → 既存ErrEulaMgr dispatcher
  待機・提示（vtable+0x7C）
```

vtableは`0x008E8B54`。slot30の値を原本で確認。
フレーム関数はvtableから`0x0054C420`のNOPへ入り、`0x0054C424`の本体へ続く。
Calcの`0x00543BD0`はnode+60が非0なら`0x00136460`でロックを取得し、走査後に`0x00138D30`で解放する。
さらに画面生成は子の初期化・管理表更新の途中を含む。

したがって、**入口フックは短い要求記録に使い、APTの同期実行は既存の実行位置へ渡す**。
既存APT呼出しで使う`0x00ADF848`のtry-lockと周辺処理も維持する（F-372）。
単に「ゲームのスレッド上だから安全」とは扱わない。
すべてのキーボード呼出しが同一スレッドであること、該当フック時点の実際の保持ロック、
要求受渡しの競合がないことは実機未観測。既存資料中の別作業のスレッド番号を流用しない。

## 2. ゲームへ返す結果と終了状態

### mode 3の設定・バッファ

| 場所 | 確認した内容 |
|---|---|
| `0x009580E3` | 用途mode。対象の初期化で3 |
| `0x00AD0144` | ボタン数−1。対象は1（2ボタン） |
| `0x00AD0148` | 入力妥当性。対象は2、空・半角/全角空白のみを拒否 |
| `0x00AD0160` | 最大UTF-16コード単位数。対象は32 |
| `0x00AD0253` | 改行設定。対象は0 |
| `[0x00958100]` | 初期文字列の参照元。対象の初期化で0、出力先頭も0にする |
| `[0x00958108]` | 出力UTF-16バッファ。対象では親+44に保持されたもの |
| `0x009580E2` | 出力所有/解放フラグ。対象は0（親側所有） |
| `[0x00958114]` | `sys::TextManager*` |

`0x00522D68`の構築処理と、`0x00521B28`の実際の書込み・長さ更新で照合したTextManagerの欄:

| offset（byte） | 内容 |
|---|---|
| +4 | `sys::LineManager*` |
| +8 | 現在のUTF-16長 |
| +12 | 最大長 |
| +16 | 出力バッファ |
| +20 | カーソル位置 |
| +36 / +40 | 未確定入力等の管理値（`0x00521970`が確定時に処理） |

`0x00521B28`は1コード単位を挿入し、容量、終端、長さ、カーソル、行情報、入力音等も扱う。
**確定文字列を出力バッファへmemcpyするだけでは、TextManagerと行管理が一致しない。**
既存APIを利用するなら挿入/削除/確定の契約を保つ。補助引数を根拠なく0で埋めない。
そのまま投入できる全置換setterを作成・検証済みではない。
改行・ゲーム内部の制御文字・禁止文字・表示容量は別途合わせる必要がある。

### 完了通知

`0x00522D40`（既存ラベル`vc_CALLCHAT`）の実体:

（疑似C を省略。原本は _local/legacy-src/…）

これはキーボード起動APIではない。`r1=-1`は「結果を書き換えない」。
構築時にはready=0、result=-1となる。readyを0にしてもresultは消えない。

`BsMenuFriendChat`の更新`0x002AE4C8`による消費:

| 通知 | 動作 |
|---|---|
| ready=0 | 結果を消費しない |
| ready!=0 / result=2 | 親の文字列を送信/表示する処理へ渡し、readyを消し、子へ終了要求 |
| ready!=0 / result=1 | 送信せず子へ終了要求 |
| ready!=0 / result=-2,-1,3など | このconsumerは終了状態へ進まない |

2ボタンの内蔵キーボードでは、正常な終了通知と設定の`SwkbdResult`を別々に検査した後、
確定文字列をゲーム側に反映してからready/resultを通知する。
画面の「やめる」はゲームのresult=1へ対応させる。初期文字列を取消時に確定内容として書き込まない。
APTの異常・HOME等を生の数値のままresultへ渡すと、終了待ちが成立しない。
異常通知を取消へ変換するのも、アプレット終了とゲーム復帰を確認できた場合に限る。

### 子画面の寿命

確定・取消とも、親は保存した子のvtable+`0x44`（`0x0057B238`）を呼ぶ。
この関数は入力側のフラグ更新、子+4549=1、終了stateへの要求を行い、即座には子を破棄しない。

```text
親の完了消費 0x002AE4C8
  子の終了要求 0x0057B238
    0x0057CE64 → 0x0057CF04（終了アニメ等の待ち）
      0x0051F4C0 → 通常の画面終了処理
        0x0057F944 → 資源/入力エンジン解放、[0x0094A654]=0
親は次の更新で[0x0094A654]==0を待って自身の終了要求を出す
```

`0x005232B4`はTextManagerを破棄し、所有フラグが立っていれば出力バッファも解放する。
共有メモリハンドルと親のUTF-16出力バッファは別物として管理する。
子のglobalだけを強制的に0へする方法は、この寿命管理を満たさない。

## 最小実装へ落とす構成

1. mode 3の入口で親・生成された子・設定を一回要求として記録し、元の戻り値を保つ。
   まず対象は`0x002AE474`の呼出し、または共通入口のID/親による絞込みとする。
2. 元の子が初期化を終え、対象のTextManager・バッファと整合していることを確認する。
   `[0x0094A654]`が非0だけでは不十分。生成中や終了中の実行を防ぐ。
3. 既存APT位置で要求を消費する。F-372の排他・周辺管理条件を満たし、
   `Prepare(0x401)`→`Start`→`Wait`を実行する。
4. APT側から戻った結果は保管し、元のゲーム側更新文脈で文字列反映と完了通知を行う。
   元キーボードとの二重入力・通知の上書きを防ぐ。
   `0x0057F8B0`は子+4620・global `0x0095819C`・ボタンのbitを変えるが、
   これだけで全入力を停止できるとまでは確認していない。
5. 親による子の終了要求と、元の資源解放を最後まで通す。完了まで再要求を受け付けない。

この構成はゲームの`BsSkb`を親との寿命管理に残す案。
自前メニューやgohan.3gxの設計には依存しない。
入口そのものの同期置換や、BsSkbの完全な省略を実装済みとはしていない。

## 検証結果と残る範囲

`SYSTEM_KEYBOARD/verify_game_hook_contract.py`で**12ケースPASS**。
