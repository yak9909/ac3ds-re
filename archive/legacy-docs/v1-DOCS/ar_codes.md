# 本解析で作成した Action Replay コード

`REFERENCES/CHEATS/` は外部の先行情報。**こちらは本解析で根拠を確認して作ったもの。**
各コードに「何を書き換えるか」「なぜそれで効くか」と、素の値を併記する。

## AR コード型の参照資料

CTRPluginFramework の Action Replay コード型は、Nanquitas による次の資料を基準とする。

- [CTRPF-Action Replay Code Types — Nanquitas](https://gist.github.com/Nanquitas/d6c920a59c757cf7917c2bffa76de860)

同資料は CTRPluginFramework v0.5.0 のコード型をまとめており、32/16/8bit 書き込み、
条件式、offset/data/storage レジスタ、ループ、終端、入力、浮動小数点、演算、
データコピー・検索、カスタム ARM32 などを記載している。
本解析で使った `D3`（offset 設定）、`DC`（offset 加算）、`D0`（条件ブロック終端）、
`D2`（全ブロック終端）、`DD`（キー入力条件）およびキー値 `0x100 = R` もここに準拠する。

古いミラーや転載にも同じ基本定義が残っているが、今後は上記 Gist を一次参照とする。

## 会話を一瞬で表示する（漢字・ルビあり）

```
[会話を一瞬で表示（漢字・ルビあり）]
005F8278 E3A00001

[メニュー/ウィンドウのアニメーションをカット]
00568BF8 43B00000
```

| アドレス | 素の値 | 書き込む値 | 意味 |
|---|---|---|---|
| `0x5F8278` | `E5D400CA` `LDRB R0,[R4,#0xCA]` | `E3A00001` `MOV R0,#1` | `script::TalkSeq` の「一気に表示」フラグを常時 ON |
| `0x568BF8` | `3F800000` (1.0f) | `43B00000` (352.0f) | UI アニメの再生レート |

2 行目は好みで外してよい（ウィンドウが普通の速度で開くようになるだけ）。

### なぜ漢字とルビが出るのか

`0x5F8278` はゲーム自身が持つ「一気に表示」フラグ `this+202` の**唯一の読み出し箇所**
（`LDRB [Rx,#0xCA]` はバイナリ全域でここ 1 つだけ）。
ここを 1 に固定すると `TalkSeq_StepText` が本来の一括表示経路に入り、

（疑似C を省略。原本は _local/legacy-src/…）

で **`MsgStream_Emit` を全文字分回す。** ルビ制御コード（種別 14）もすべて処理されるので、
漢字もふりがなも欠けない。**ゲームが元から持っている経路なので副作用が少ない。**

### 既存チートとの違い

`REFERENCES/CHEATS/ui.txt` の「メニューアニメーションをカット」は 3 行:

```
005FAF68 E1A00000   ← ★これが漢字とルビを消していた
005FB298 43B00000   ← 実は効いていない（下記）
00568BF8 43B00000
```

- **`005FAF68 E1A00000`** は `BL TalkSeq_StepText` を潰す。
  すると `R0 = R4`（非ゼロ）のまま `CMP R0,#0` / `MOVNE R6,#1` を通るので
  呼び出し元は即座に「表示完了」を返す。文字が一瞬で出るのはこのため。
  ただし **`MsgStream_Emit` が一度も回らない**ので、
  制御コード 14（ルビ）が処理されず、**漢字とふりがなが両方消える。**
- **`005FB298 43B00000`** は文字送り倍率 1.0 → 352.0 だが、
  上の NOP で `TalkSeq_StepText` 自体が呼ばれなくなるため**実際には効いていない。**
  `TalkSeq_StepText` の呼び出し元は `0x5FAF68` の 1 箇所しかない（`xrefs_to` で確認）。
- **`00568BF8 43B00000`** だけがウィンドウアニメに効いている。

**つまり 3 行のうち 1 行は死んでいて、1 行が不具合の原因だった。**

### 保険版（一括表示ではなく高速化）

万一、上のコードで会話が進まなくなる場面があれば、こちらを使う。
本来の 1 フレームずつ進める経路を残したまま倍率だけ上げるので、より安全。

```
[会話を高速化（漢字・ルビあり）— 保険版]
005FB298 43B00000
00568BF8 43B00000
```

**`005FAF68 E1A00000` は絶対に入れないこと。** これが漢字とルビを消す原因。

### 注意

一括表示経路の `while` ループは
「2 つの `script::TalkRuby` が両方とも出し切る」まで回る。
ゲーム自身が使う経路なので通常は止まるが、
**もし特定の会話で固まるようなら保険版に切り替えること。**

## メニュー・画面遷移を一瞬にする

```
[メニュー/画面遷移を一瞬にする]
00568BF8 43B00000
```

| アドレス | 素の値 | 書き込む値 | 意味 |
|---|---|---|---|
| `0x568BF8` | `3F800000` (1.0f) | `43B00000` (352.0f) | UI レイアウトアニメの再生レート |

### これ 1 行で足りる理由

`0x568BF8` は `UiAnim_Init` が `this+16`（再生レート）へ入れる初期値で、
**このリテラルを参照する命令はバイナリ全域で `0x568BC4` の `VLDR` 1 つだけ。**

そして画面遷移（`Wipe` クラス）も同じ経路を通る:

```
Wipe_Init (0x52A9CC)
  UiAnim_Load(this+952,  リソース, レイアウト)
  UiAnim_Load(this+992,  ...)          ← アニメスロット 3 つ
  UiAnim_Load(this+1032, ...)
UiAnim_Load (0x568A04)
  ... 末尾で UiAnim_Init を呼ぶ         ← ★ここでレートが入る
```

`FaderWipe_Update` (`0x6E3B58`) は `Wipe_IsIdle` を見て状態を進めるだけで、
**固定フレームの待ちを持たない。** つまり遷移の所要時間 = アニメの尺そのもの。

`BsMenuItem`（ポケット）と `BsMenuMyDesign` のモジュールを調べたところ、
**float 定数が 1 つも存在しない**（`BsMenuMyDesign` に 2.0 が 1 つあるのみ）。
メニュー側にも独自の時間定数はなく、タイミングは全部アニメ駆動である。

したがって **`0x568BF8` がメニュー開閉と画面遷移の両方を握る唯一の調整点。**

### 値の選び方

`UiAnim_Set` (`0x568C18`) が `this+8`（現在時刻）に毎フレーム `this+16`（レート）を
足していく形なので、レートはそのまま「1 フレームあたり何フレーム進むか」。

| 値 | float | 備考 |
|---|---|---|
| `43B00000` | 352.0 | **推奨。** UI アニメは通常 60 フレーム以下なので十分 |
| `447A0000` | 1000.0 | さらに余裕を持たせたい場合 |
| `7F7FFFFF` | FLT_MAX | `REFERENCES/CHEATS/speed.txt` の「高速メニュー表示」。**非推奨** |
| `77777777` | 5.0e33 | 同 speed.txt の「画面切り替え」。**非推奨** |

**FLT_MAX や 5.0e33 を勧めない理由**: 現在時刻に毎フレーム加算されるので
2 フレーム目で `inf` に達し、`現在時刻 / 総フレーム` のような補間で `NaN` を生む余地がある。
352.0 なら 1 フレームで確実に終端に届き、値も壊れない。

### カットできないもの

これはアニメの再生速度を変えるだけで、**メニューのレイアウトやリソースの読み込み時間は短くならない。**
開くのに一瞬の間が残る場合、その分は読み込みであってアニメではない。

### 副作用

`0x568BF8` はグローバルなので、**ポケットとマイデザだけでなく全 UI アニメが速くなる。**
個別に効かせたい場合はコードケーブが要る（未実装）。

## 画面遷移のフェードを消す

```
[画面遷移のフェードを消す]
006A52B8 E3A05002
006A52C4 E3A04002
```

| アドレス | 素の値 | 書き込む値 | 意味 |
|---|---|---|---|
| `0x6A52B8` | `E1A05000` `MOV R5,R0` | `E3A05002` `MOV R5,#2` | 上画面のフェーダ種別を 2 に固定 |
| `0x6A52C4` | `E1A04001` `MOV R4,R1` | `E3A04002` `MOV R4,#2` | 下画面のフェーダ種別を 2 に固定 |

**前節の `00568BF8 43B00000` と併用する。** あちらはメニューのレイアウトアニメ、
こちらはフェードで、別系統である。

### なぜ `0x568BF8` だけでは消えないのか

フェードは `Fade` クラスのアニメ（`fade_In_Fade.bclan` など）で動くが、
その `Fade` は **`Fade_Init` が起動時に 1 度だけ**作る。
`UiAnim_Init` はそのとき `g_UiAnimRate` を `this+16` に**コピー**するので、
**後から `0x568BF8` を書き換えても、既に作られたフェードのレートは 1.0 のまま。**

メニューのレイアウトは開くたびに作り直されるので新しいレートを拾う。
「メニューは速くなったのにフェードだけ残る」のはこのため。

### 仕組み

`Fader_CreateAll` (`0x6A4ED0`) が起動時にフェーダを 9 個作って
`g_FaderRegistry` (`0x94C64C`) に登録する:

| # | 種別 | 画面 |
|---|---|---|
| 1 / 6 | `FaderColor` 黒 | 上 / 下 |
| 2,3 / 7,8 | `FaderColor` 白 | 上 / 下 |
| 4 | `FaderWipe` | 上 |
| **5 / 9** | **`FaderMoment`** | 上 / 下 |

`Fader_SetKind(topKind, bottomKind)` (`0x6A52B4`) が種別からこれを引く:

```
kind 0 -> FaderWipe        kind 1 -> FaderColor 黒
kind 2 -> FaderMoment      ★フェードなし
kind 4 -> FaderColor 白    kind 5 -> FaderColor 白(flag1)
```

**`FaderMoment` は「瞬間」フェーダで、`FaderMoment_Update` (`0x1C86E8`) は待ちゼロで即完了する:**

```c
if (state == 2) { state = 1; flags |= 1; /* Fade/Wipe を即座に隠す */ return 1; }
if (state == 3) { state = 0; flags |= 2;                              return 1; }
```

**ゲーム自身が「フェードなし」の実装を持っているので、それを選ばせるだけでよい。**
実際 `0x758F74` / `0x759044` は素の状態で `SetFader(2, 2)` を渡している。
起動時の既定は `0x1B6FEC` の `SetFader(1, 1)` = 黒フェード。

### 副作用

`Fader_SetKind` の呼び出し元は 7 箇所すべてが対象になるので、
**メニューだけでなくエリア移動（ドア）やイベントのフェードも消える。**
フェードが隠していたロードが見えるようになる場面はあり得る。
ドアの遷移だけは残したい、といった選り分けはコードケーブが要る（未実装）。

### 誤りやすい点

`ssys::co::FaderBase` のコンストラクタ (`0x5658F8`) は `this+8 = 20`（フレーム数）を
入れており、いかにもフェードの尺に見える。**しかしこれは使われていない。**
`FaderColor` / `FaderMoment` / `FaderWipe` の 3 つとも `Update` を上書きしており、
カウンタを読む `FaderBase_Update` (`0x5657F0`) は vtable にあるだけで到達不能。
`0x56590C` の `MOV R1,#0x14` を書き換えても何も変わらない。

## 通常ドロップの種別を変える（F-65）

対象: 日本語版無印 `0x0004000000086200`。**メモリパッチなのでゲーム再起動で消える。**

### 前提

通常ドロップは `Player_DropItem`(`0x596084`) が

```c
Item_PlaceItem(10, g_EmptyItem, ItemToPlace, item, wX, wY, IsInside, 0,0,0,0);
```

を呼ぶ。**第 1 引数 `10` = `0x0A` がドロップ種別**で、その即値が **`0x596178`**（`E3A0000A`）。

種別の意味（`drop.txt`「ドロップタイプ」と `sub_5A0C2C` の case が一致）:

| 値 | 意味 |
|---|---|
| `0x0A` | ドロップ（素の値） |
| `0x0B` | スコップ |
| `0x0C` | 花植える |
| `0x0D` | マイデザ |
| `0x0F` | 置いても見えない |
| `0x21` | **検証なし・演出なし** |

### コード A: 種別を 0x21 にする（要望どおり・ただし注意）

```
00596178 E3A00021
```

復元:

```
00596178 E3A0000A
```

**★おそらく「何も起きない」。** `0x21` は `FieldAction_CanApply` を無条件で通るが、
`sub_5A0C2C` に `0x21` の case が無く `default:` に落ちる。
**実際にアイテムを書き込むのは `0x0A`/`0x0B`/`0x0C`/`0x0D` の各ハンドラ**
（`sub_59A4A0` + `Field_SetItemAt` 等）なので、`0x21` では配置処理が走らない。

FOXXY が `pseudoType0x21` で実配置を種別 `0x0F` にやらせ、
`0x21` のレコードを別に注入しているのは**まさにこれが理由**（F-64）。

### コード B: 演出を保ったまま 0x21 の「無検証」だけ貰う（推奨）

種別 `0x0A` のままにして、`FieldAction_CanApply` の判定だけ差し替える。

```
0059F8B0 0059FA58
```

復元:

```
0059F8B0 0059F964
```

**根拠**: 種別表は `FieldAction_CanApply`(`0x59F830`) 内の **`0x59F88C`** 先頭、
**索引 = 種別 − 1** の 34 エントリ（種別 `1`-`0x22`）。
種別 `0x0A` → 索引 9 → `0x59F88C + 0x24` = **`0x59F8B0`**。

ハンドラ早見表:

| addr | 判定 |
|---|---|
| `0x59F954` | `Item_SameId` |
| `0x59F964` | `Item_IsEmpty`（空マスでないと不可）← 種別 0x0A の素 |
| `0x59FA58` | **無条件で 1** ← 種別 `0x21` が使うもの |

効果は「空マス判定を外す」= **物の上にも置ける**。
音・演出・配置は `0x0A` のまま残る。

**★これは `drop.txt` の「物を重ねて置ける」が既にやっていること**
（あちらは索引 9-12 = 種別 `0x0A`-`0x0D` の 4 つをまとめて `0x59FA58` に向ける）。

### ★実機検証の結果（F-93）

| コード | 結果 |
|---|---|
| A | **何も起きない**（予測どおり。`0x21` は配置処理を持たない） |
| B | **変化なし**（★予測が外れた。単独では不十分だった） |

**コード B が効かない理由**: 可否判定は 2 段ある。

- **ゲート1** `Drop_FindTargetTile` → `Field_CanPlaceItemAt`(`0x165448`) … **どのマスを選ぶか**
- **ゲート2** `FieldAction_CanApply`(`0x59F830`) … 選ばれたマスの検証

ゲート1 が空マスしか返さないので、ゲート2 を緩めても通常経路では出番がない。

### コード B': 実際に「物を重ねて置ける」最小構成

```
00165510 E1A00000
0059F8B0 0059FA58
```

復元:

```
00165510 EB065D83
0059F8B0 0059F964
```

`0x165510` は `Field_CanPlaceItemAt` 内の `BL Item_IsEmpty`。
NOP にすると R0 がアイテムポインタ（非0）のまま残り、**どのマスも「空」扱い**になる。

**★副作用**: `Field_CanPlaceItemAt` の呼び出し元は 6 件（`Drop_FindTargetTile` /
`FieldAction_TreeDropItem` / `FieldAction_TreeDropFruit` / `sub_596C2C` /
`sub_598BEC` / `sub_5A1268`）。**木の果実・アイテム落下も占有マスに落ちるようになる。**

種別 `0x0B`-`0x0D`（スコップ・花植える・マイデザ）にも効かせたいなら
`0059F8B4` / `0059F8B8` / `0059F8BC` も同様に `0059FA58` へ。
オンラインで使うなら `drop.txt`「物を重ねて置ける」の HOST 4 行も要る（F-61 / F-63）。

### ★実機確認済み — 完成 (F-93)

| 適用 | 結果 |
|---|---|
| 2 行目のみ | 変化なし |
| 1 行目のみ | 木の果実・アイテム落下が占有マスへ |
| **2 行とも** | **通常ドロップでも重ね置き可** |

木の落下は actionID `8/9/0xE/0xF` でゲート2 に空マス判定が無いため 1 行目だけで効く。
通常ドロップ `0x0A` はゲート2 にも `Item_IsEmpty` があるので 2 行必要。

**副作用（木の落下が占有マスに落ちる）は許容と確認済み。**

種別 `0x0B`-`0x0D`（スコップ・花植える・マイデザ）にも効かせたいなら
`0059F8B4` / `0059F8B8` / `0059F8BC` も `0059FA58` へ。
オンラインなら `drop.txt`「物を重ねて置ける」の HOST 4 行も要る（F-61 / F-63）。

## オンライン髪型変更チートの構造（F-66）

対象: `REFERENCES/CHEATS/player.txt` の「見た目変更(オンライン)」。静的解析のみ。

### コードパッチ

```
00682A8C E1A00000  # 虫取り網の再判定を NOP
00682A68 E1A00000  # 道具種別 4 の判定を NOP
00682A20 E1A00000  # 準備フラグ判定を NOP
00682AA0 E3A010B9  # Actor_SetState の状態 0x70 -> 0xB9
```

4 箇所とも `PlayerAction_TryBugNetSwing` (`0x682994`) 内。
通常の虫取り網状態 `0x70` を、美容室／見た目変更状態 `0xB9` へ差し替える。
OFF コードの値は `code.bin.i64` の元バイトと一致する。

### Gateway 部

CTRPF のコード型として解釈すると次の処理になる。

（疑似C を省略。原本は _local/legacy-src/…）

上記 Nanquitas 資料のキー定義で `0x100` は **R**。配布文の「Aボタン」は
状態キック後に使うゲーム側アクションの説明とみられるが、入力順は未検証。
同じプロジェクト内でも `player.txt` の `[R]` チートが `0x100`、
`speed.txt` の R+右が `0x110` を使っている。

通常側の書き込み先 `0x33099FE4 = player+0x1A8` では、
`0x060D0600` は `[00,06,0D,06]` となる。`+0x1A9=現在状態 6`、
`+0x1AA=直前状態 13` で、髪型値ではなく状態機械のキック。
sentinel により `+0x12C` された代替先 `player+0x2D4` の意味は未確定。

### 髪型データとオンライン同期

状態 `0xB9` は scratch の `player+0x8CA/+0x8CB/+0x8CC` を
髪型 0-33／髪色 0-15／目色 0-5 として読み、プロフィールへ反映する。
記述子 `0x844A70+0x18` の `PlayerState_AppearanceChangeSyncRemote` が
受信パケットから相手プレイヤーにも同じ更新を行うため、「オンライン」は実処理を伴う。

**警告**: 実機検証までは野良オンラインで使わないこと。
通信相手の一時プロフィール表示へ不正値が伝播しうる。

## 髪型変更で頭装備を保持し、1 tick で反映する候補（F-67）

対象: 日本語版無印 `0x0004000000086200`。**静的解析からの候補で、実機未検証。**
上の「オンライン髪型変更」を ON にしている間だけ併用し、使用後は必ず復元すること。

### 推奨候補: 頭装備保持＋ローカル即時化

```
00687F0C E3A010EE
0068323C E3A00001
0068347C E3A00001
006857A4 E1A00000
006857B0 E1A00000
0068BA4C E1A00000
0068BA58 E1A00000
```

### オンライン時の挙動

状態 `0xB9` のパケット送信は enter 後・update 前に行われるため、即時化しても送信自体は残る。
ただし相手側の再生速度は相手の実行コードで決まる。

- 同じパッチを入れた相手: 受信アクターもほぼ即時反映し、頭 2 枠を保持する見込み。
- 未パッチの相手: 237→238 を通常速度で再生し、Hat/Accessory を消す。
- 送信側だけのコードでは、未パッチ相手に「即時＋頭 2 枠保持」を強制できない。

状態パケットが持つ衣装 Item は 1 個だけで、受信処理は Accessory を無条件に空にするためである。
またこのパッチは美容室状態 `0xB9` 全体へ効く。通常の目色変更・Mii マスク変更中は無効にすること。
