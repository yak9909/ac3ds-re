## 1. 何をしているか

タイトルでプレイヤーを選ぶと部屋 **`0x63`（内部名 `PlayerSelect`）**へ入る。
しずえの会話も「準備中」も**すべてこの部屋の中**で起きていて、
「はじめる」を選ぶと **`ModulePlSelect.cro` のイベントハンドラの分岐 [1]** が走り、村へ出る。

このチートは、**その分岐 [1] とまったく同じ手順を、イベントを待たずに実行する**だけ。

ゲーム自身の準備完了判定とプレイヤー番号計算をそのまま借りているため。

## 3. デバッガでの手順（実機で成功した手順そのまま）

**ゲームのコードは 1 語も書き換えない。** 未使用領域にケーブを置き、
PC を 1 回だけそこへ向け、終わったらレジスタを完全に復元する。

### 3.1 事前

```
python PATCHES/plselect_earlystart.py
```

- 語列（41 語）と自己監査（全 LDR のリテラル参照先・全分岐先）が出る。**異常 0 件でなければ進めない**
- objdump でも独立に確認する:
  `arm-none-eabi-objdump -D -b binary -m arm --adjust-vma=0x00838100 cave.bin`

### 3.2 実機

1. **タイトル画面で Suspend。**
2. 置き場が空か確認 — `0x00838100`〜`+0x120` と `0x00838300`〜`+0x20` が**全部ゼロ**であること。
3. ケーブ 41 語を `0x00838100` へ書き、**読み戻し一致**を確認。
4. **ida-pro-mcp で実バイトを逆アセンブル**して 3 本目の検証（BL 5 本の飛び先・リテラル・分岐）。
5. Resume。**プレイヤーを選び、しずえの画面が出たら会話を進めずに Suspend。**
6. 部屋が `0x63` であることを確認（`0x0095133A`）。
7. `Framework_ProcOneFrame`（**`0x0054C424`**）に bp を置いて Resume。
   → **メインスレッドのフレーム境界**で止まる（任意の場所で注入すると別スレッドの危険がある）。
   `LR` が `0x0054C848`（`Framework_MainLoop`）であることで裏が取れる。
8. **全レジスタを保存**（R0-R12, SP, LR, PC）。
9. `0x0054C424` の bp を**削除**し、`0x00838198`（ケーブ末尾）に bp を置き、**PC = `0x00838100`**。
10. Resume → ケーブが走り、末尾の無限ループ手前で止まる。
11. `0x00838300` を読む。
12. **保存したレジスタと PC を全部書き戻し**、bp を削除して Resume。

### 3.3 結果の読み方（`0x00838300`）

| off | 意味 |
|---|---|
| `+0` (u8) | 1 = `Room_UseExit` まで到達した |
| `+1` (u8) | 1 = ガード（`sub_2FB900`）が 0 で中止 |
| `+2` (u8) | 1 = `idx > 3` で中止 |
| `+4` (u32) | プレイヤー番号 |
| `+8` (u32) | 遷移マネージャ |

## 5. ★飛ばしているもの（F-362 で確定）

**「準備しています」のロードが一度も出なかった。** その理由は F-362 で確定した。

しずえ画面（部屋 `0x63`）のイベントハンドラは `ModulePlSelect.cro` にあり、
ジャンプ表 `0x00BE6A7C` の 13 分岐のうち

| case | 役割 |
|---|---|
| **0** | **「準備しています」を出し、村へ入る前の一括処理を走らせる** |
| 1 | 村へ行く（このチートが再現している分岐） |

**このチートは case 1 の動作だけを実行するので、case 0 が丸ごと走らない。**

case 0 が走らせているもの:

| 番地 | 内容 |
|---|---|
| `0x002F9D3C` | 村セーブの各種欄の作り直し |
| `0x0023CBB8` | `byte_94DB2C` / `byte_94DB2E` のクリア |
| `0x0027EB34` | `this+632` の初期化（中で `sub_2F9D3C` も呼ぶ） |
| `0x0058B934` / `0x0058BA10` | 旗 26 の上げ下げ（メッセージ中の抑止） |
| `0x002388BC`(this, **2**, `"SYS_Save"`, this+632) | **「準備しています／電源ボタンに触らないでください」** |
| **`0x0030C994` → `0x0030C9C4`** | **★村へ入る前の一括処理（下記）** |
| `0x00237544` | プレイヤー名の差し込み |

★**`sub_30C9C4`（`0x0030C9C4`）が実害の候補。**
`byte_956231`（`0x00956231`）で **boot 中 1 回だけ**走る一括処理で、
村セーブ + プレイヤー 10 人分（`+= 9496`）× 所持枠 16（`242 * j`）を回り、
`ItemToPlace`（`0x00955FF4`）の品を `sub_30D04C` / `sub_30D894` で配置し、
`sub_10D980` / `sub_110CFC` / `sub_10FF58` / `sub_10DBA0` / `sub_10CCB8` / `sub_110668`
を村セーブに対して実行する。

→ **このチートは「起動時のセーブ」だけでなく、この一括処理も飛ばしている。**

★**未確認**: `sub_10D980` 等の中身は未解析なので、
これが日付変更時の成長処理（草・カブ・住民の引越し）そのものかは**まだ分からない**。

**確かめ方**: 日付をまたいだ状態でこのチートを使い、
雑草の増加・カブ価・住民の引越し・郵便受けの中身が正常かを見る。

**安全側の作り方**: case 1 だけでなく **case 0 も先に 1 回実行する**か、
少なくとも `sub_30C994`（`0x0030C994`）を `Room_UseExit` の前に呼ぶ。
`byte_956231` の番兵があるので二重呼び出しは無害。

## 8. 2026-09-09: 3gx常設統合は撤回

F-361で実機確認できたのは、停止中にゲームのメインスレッドから一度だけ実行したケーブである。
§6の常設コードは設計案であり、3gxとしての安全性を確認したものではない。

別作業で常設`ShizueSkip`を組み込んだ際、切り分け用の
`kDiagNoHooks=true`と入力遮断のコメントアウトが現行ソースへ残り、描画構成を壊した。
F-390で常設統合をソース・ヘッダ・メニュー・追加フォント・Simulatorから除去し、
しずえ統合前の構成へ戻した。
F-361の一回実行という実績と、常設フックの可否を混同しない。

再び常設化する場合は、§5で飛ばすと判明した`sub_30C994`系の一括処理を含めて設計し直し、
独立した検証を通す。既存GUIへ項目を追加するところから始めてはいけない。

## 9. 2026-09-09: case 0を含む常設版（F-391）

F-390復元版の実機復活を利用者が確認した後、その復元状態へ常設版を追加した。
旧F-366のソースをそのまま戻してはいない。

### 9.1 `sub_30C994`の呼出契約

idalib `acnl_code`のassemblyで、`0x0030C994`は引数なしのwrapperと確定した。

```asm
30C994  PUSH {R4,LR}
30C998  BL   Save_GetTownBase
30C99C  BL   sub_2FB33C
30C9A0  MOV  R2,#0
30C9A8  MOV  R1,R2
30C9AC  ADD  R0,R0,#4
30C9B0  B    sub_30C9BC
```

独立した裏取り:

1. CRO case 0の`0x00BE6B34`は、メッセージ完了判定の直後に引数準備なしで呼ぶ。
2. 本体側`0x00608DEC`も`sub_12668C`の直後に引数準備なしで呼ぶ。
3. 本体の別経路3本は、村セーブから同じ対象を作り`sub_30C9BC(target, 0)`を直接呼ぶ。

`sub_30C9C4`は`0x00956231`のboot-once番兵を持つ。常設版は番兵が0の時だけ
`sub_30C994()`を呼び、戻った後に番兵が1であることを確認する。

### 9.2 常設処理

`Sources/ShizueSkip.cpp`が`Framework_ProcOneFrame` (`0x0054C424`)へMITMフックを置く。
次をすべて満たした時だけ発火する。

- 現在の部屋が`0x63`
- メニュー項目の**適用値**がON
- 30フレーム連続して対象部屋にいる
- case 1と同じguard、プレイヤー番号0..3、room managerが解決できる

出口情報を確認→`sub_30C994()`→番兵確認→出口情報を再取得→
`Room_UseExit(mgr, idx, 1, 0, 1, 1)`の順。一度発火したら退室まで再発火しない。
項目OFFまたは対象外の部屋ではゲーム関数を呼ばない。

`PATCHES/verify_shizue_skip_integration.py`でソース、実機ダンプの入口命令、
メニュー/Simulator/フォント、状態遷移、リンク成果物を検査する。F-391作成時は
全既存検査とともにPASSした。リンク後ARMでも上記の呼出順と6引数を確認済み。

成果物: 846,115 bytes、SHA-256
`de406a2187a8b7bb93606e65971bc37f1e44eb32dfd5d458a255147dca90f8f7`。
**この節を書いた時点ではF-391版を実機へ適用していない。** 常設フックの実機確認と、
日付またぎ更新の通常経路との比較は残る。

## 10. 2026-09-09: 画面停止の原因と通常フック化（F-392）

**追記F-393: この版も使用不可。** 利用者がしずえスキップOFFでしずえ画面へ遷移すると
SIGSEGV。PC=0x0054C438、R4=0を実測。通常フックはcallback前後のR0を保持せず、
OFF判定が返す0が元関数のthisへ渡っていた。詳細scratchpad/MEMO_f393_shizue_off_sigsegv.md。
以下はF-392作成時点の記録であり、実機成功を意味しない。

F-391を実機へ適用後、自前メニューをONにしてメニューが開く時点で画面が停止し、
音だけ継続した。§9の「実機未適用」は作成時点の記録であり、その後の実測結果は失敗である。

原因は描画データやフォントではなく、CTRPFフックAPIの契約違反だった。
`InitializeForMitm`は元関数を置換し、callbackへ直接分岐する。元関数を続行するには
callbackが`HookContext::OriginalFunction()`を呼ばなければならない。F-391の`OnFrame`は
状態を調べてreturnするだけだったため、OFF時を含めて`Framework_ProcOneFrame`の残りを
毎フレーム飛ばしていた。画面更新だけ止まり音が継続した観測とも一致する。

F-392では次の通常フックへ変更した。

```cpp
g_hook.Initialize(0x0054C424, (u32)OnFrame);
```

通常フックは素の先頭命令`PUSH {R4-R6,LR}` (`0xE92D4070`)を実行し、callbackの後で
`0x0054C428`へ戻る。ビルド前検査は専用統合検査、既存描画/仕様/ケーブ、
キーボード10,943遷移/15場面、Simulator 49件、ARM構文がすべてPASSした。
クリーンビルド後の成果物検査もPASS。リンク後ARMは次の呼出を持つ。

```asm
0700B1F0  BL  0701F554  ; Hook::Initialize
```

同じELFの`Hook::InitializeForMitm`は`0x0701F570`であり、`ShizueSkip::Install`からは
呼ばれていない。F-392成果物は846,115 bytes、SHA-256
`cc1d416aebd09a2bb52fc0da22a5f0a6225f0d2f5cad04287b481a1b2a6a1e9c`。
修正版の実機確認は未実施。F-391のSHA
`de406a2187a8b7bb93606e65971bc37f1e44eb32dfd5d458a255147dca90f8f7`は使用禁止。

## 11. F-394: OFF時SIGSEGVを防ぐcallback保存処理

**実機成功の追記:** 利用者から「復帰しました。しずえスキップも問題なく動作しました」と報告。

以下の実機未確認表記はビルド完了時点の履歴である。

F-393の実測ではPC=0x0054C438、R4=0。F-392の通常HookもC++ callbackの前後でR0を
保持しないため、OFF判定の戻り値0がゲームのthisへ渡っていた。

d0-d15をスタックへ保存する。無引数ShizueSkipTickを実行後、全て復元する。
