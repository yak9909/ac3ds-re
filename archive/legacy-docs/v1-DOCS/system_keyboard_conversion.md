予測系の検索後、条件に応じて連文節・単文節・単漢字系を含む追加検索へ進む。

### 頻度値と品詞情報の位置

主要2辞書（type `0x00050000`）について、`0x167EF8`で以下を確認した。

- 1始まりの単語IDごとに頻度2バイト。位置は`BE32(header+0x28)+2*(ID-1)`。
  各バイトの下位6ビットを使う。mode 0とmode 1で読むバイトが異なる。
- 10バイト単語レコードの`+0x08..0x09`は**頻度そのものではなく、前後の品詞表を引く索引**。
  ビット幅はheader `+0x4B`/`+0x4F`、表基準は`BE32(header+0x44)`。
  前側の要素数・要素幅、後側の要素幅もヘッダから取得する。
- 品詞IDは接続表のIDと対応する。一般的な「名詞=何番」などの品詞名の対応は未確定。

主要75,770件について、2種類の頻度・前後品詞をPythonで抽出し、
`0x167EF8`の原本ARMと全151,540回照合した。**不一致0件。**
`word_tables/verification_ranking_metadata.json`に件数・原本SHA-256・CSVのSHA-256を保存。
CSVのSHA-256は`6ba89a9cdf57436996c1fabe3034d40974ffb55ae22e6c67eec0e838ba404621`。

`0x18CDDC`の主要辞書設定は、通常変換400..550、予測100..560。
`0x14D4CC`と`0x150EB4`が検索段階ごとに使用する範囲を選ぶ。
`0x1678B8`の算術分岐は次の形（別分岐では計算済みスコアをそのまま使う）:

```text
score = lower + trunc_toward_zero((upper - lower) * raw_weight / 100)
score = clamp(score, floor, cap)
```

ARMのSMULL/ASR/SUBまで確認し、PC実行中に1,441回の入力値と出力値を捕捉して
Pythonの独立計算と照合した。不一致0件。
これで算出した**単語単体の基礎スコアを最終順位と呼んではいけない**。
一致条件、段階、学習、文脈、文節構成、重複除去も結果に影響する。

## 文節変換

`0x1145AC`→`0x12D31C`→`0x135988`→`0x1369F4`が連文節変換の経路。
単語辞書に加え、付属語辞書`njfzk.a`と品詞接続表`njcon.a`を使う。

| 入力 | 先頭文節の固定長（UTF-16単位） | 出力文節 |
|---|---:|---|
| わたしはねこがすきです | 0（自動） | 私は／猫が／好きです |
| きょうはいしゃにいく | 0（自動） | 今日は／医者に／いく |
| きょうはいしゃにいく | 3（きょう） | 今日／歯医者に／いく |
| きょうはいしゃにいく | 4（きょうは） | 今日は／医者に／いく |
| ここではきものをぬいでください | 0（自動） | ここで／履き物を／脱いでください |
| ここではきものをぬいでください | 3（ここで） | ここで／履き物を／脱いでください |
| ここではきものをぬいでください | 4（ここでは） | ここでは／着物を／脱いでください |
| はしをわたる | 0（自動） | 橋を／渡る |

各文節の読みを連結して元の入力と一致することも検査した。
付属語辞書だけを外す比較では、最初の例が「私／羽／古賀／好き／です」に変わった。
単語を最長一致で置き換えるだけの処理とは異なり、付属語と接続制約が分割にも効く。

### 接続表

`njcon.a`の前側品詞数は251、後側品詞数は294。
前向き・逆向きのビット表を持つ。`0x14D808`が品詞IDから行を取得する。

```text
前側品詞数 = BE16(header+0x1C)
後側品詞数 = BE16(header+0x1E)
direction 0: BE32(header+0x20) + (後側ID-1)*ceil(前側品詞数/8)
direction 1: BE32(header+0x24) + (前側ID-1)*ceil(後側品詞数/8)
行内ビット: byte[(相手ID-1)/8] & (0x80 >> ((相手ID-1)%8))
```

両方向の表を全73,794組で照合し、不一致0組。接続可能ビットは8,405組。
元のARM関数でも全545行のアドレスを取得し、Python計算と一致した。
この表は接続可否を示す。数値の文脈コスト表と同一視しない。

### 分割とスコアの選び方

`0x1369F4`は候補経路を保持し、先頭文節を確定して検索窓を進める。
主な構造と処理は次のとおり。

- 仮説は192バイト。88バイトの文節結果を最大2件持つ。
  `0x14A314`のARMが2件上限を検査し、追加時に
  `累積スコア += s16(文節結果+0x0C) - 1000`を実行する。
- `0x13C530`などが品詞の接続可否を調べて仮説を延長する。
- `0x14A15C`は同じ読み被覆長・末尾品詞を持つ仮説を併合し、高スコアを残す。
  スコア同値の場合、末尾文節の読み長も比較する。
- `0x167CD0`は通常の仮説では読みの被覆長を先に、次にスコアを比較する。
  特殊フラグの扱い、短い仮説の刈込み、保持件数の上限もある。

したがって、確認できたものは**最大2文節を先読みする、刈込み付きの探索**。
「全文の全分割を比較して必ず大域最適解を出す」とは結論しない。
付属語側のスコアも別の処理で候補選択に使われるため、上の累積式だけで全処理を代用できない。

## 実機SWKBDの表示候補を読み取る準備（F-387）

F-386でACNL通常チャットからの起動・復帰と漢字確定文字の回収まで実機確認した。
次の観測対象は、SWKBDプロセス内で表示用UTF-16LEへ展開済みの候補キャッシュである。
以下はすべてSWKBDの仮想アドレス/アプリオブジェクト相対オフセットで、ACNLには使わない。

| 項目 | SWKBD内の位置 |
|---|---:|
| アプリオブジェクトポインタ | `[0x001B7780]` |
| 変換対象長 | `app + 0x6958C` |
| 変換対象UTF-16LE | `app + 0x69590`（112 bytes） |
| 変換入力UTF-16LE | `app + 0x69600`（112 bytes） |
| 表示候補キャッシュ | `app + 0x69670`（112 bytes × 12） |
| 全候補数 | `app + 0x69BB0` |
| 選択候補index | `app + 0x69BB4` |
| 表示キャッシュ件数 | `app + 0x69BB8` |

根拠は2経路で一致する。`0x1031CC`→`0x10996C`→`0x111FD4`が入力変更時に
候補を生成し、`0x1099DC`が最大300件を数える。別の表示経路`0x15AB30`は
`0x1122D0`で候補をUTF-16LEへ変換し、先頭を`app+0x69670`、後続を112-byte間隔で
最大12件格納する。同関数のARMでは`app+0x69BB0/+0x69BB4/+0x69BB8`をそれぞれ
全候補数・選択位置・表示件数として読む。後続indexは
`(selected + i) % total`であり、`0x15C79C`のARM除算剰余コードとも一致する。

`SYSTEM_KEYBOARD/read_live_candidates.py`は、SWKBDプロセスへアタッチして候補表示中に
Suspendした後だけ使う読み取り専用スクリプトである。元SWKBDのSHA-256と6領域のコードを
照合し、件数、UTF-16終端、厳密デコード、入力長を検査してJSONを出す。書込み、Resume、
breakpoint設置は行わない。`verify_live_candidate_reader.py`は元ARM 8語、12候補fixture、
折返しindex、異常系5件を検査しPASS。一次記録は
`SYSTEM_KEYBOARD/evidence/verification_live_candidate_reader.json`。

これは画面用に展開された候補とその順序を得る経路である。画面外の全候補、候補の辞書由来、
学習データ、文節境界は同じキャッシュから確定しない。特に文節境界は別の状態を追う。

## 実機「かんじ」の全17候補回収（F-389）

通常チャットから起動中のSWKBDをGDB port 4001へ割り当て、PID 60を一時停止して
読み取り専用で取得した。SWKBDの実行コード`0x00100000..0x001A0000`は、供給された
日本語SWKBDの同範囲と655,360 bytesすべて一致した。グローバル`[0x001B7780]`から
得たapp pointerは`0x08292880`だった。

停止時の状態は、入力長3、入力cache/変換入力ともに`かんじ`、全候補数17、選択index 0、
表示cache件数6だった。全候補の順序は次のとおり。

| 3 | 元日 | 表示cache＋候補record |
| 4 | 幹事 | 表示cache＋候補record |
| 5 | 感じる | 表示cache＋候補record |

| 9 | 漢字 | 候補record |
| 10 | 監事 | 候補record |
| 11 | 寛治 | 候補record |
| 12 | 完治 | 候補record |
| 13 | 寛二 | 候補record |

独立照合として、index 0..13の88-byte候補recordは、実行時ポインタ/資源位置フィールドを

PC側が14件、実機が17件だった差は学習差ではなく、実機の表示候補列が末尾に
ひらがな・全角カタカナ・半角カタカナの3件を加えるためである。
