# F-400: エンジン再配置と内蔵リソースの直接利用

2026-09-10。利用者条件: SDや3gxへ変換テーブルをリソースとして用意する方式は避ける。
画面/APTなし、独立した候補取得を目的にする。

## 結論

**原本エンジンの再配置はPC上で成功した。**
元VAを完全にunmapし、別VAの原本コードだけで初期化から候補取得まで実行した。
実機への再配置適用は未実施。今回の試験を全経路対応のローダー完成とは扱わない。

**同梱する変換テーブルは不要にできる見込みがある。**
辞書とコード内定数は内蔵タイトルから実行時に読み、RAM上へ配置する構成を候補とする。
RAMへのロードは必要だが、SDへの抽出済み辞書保存、3gxへの辞書/表の埋込みは採用しない。
ACNL/CTRPFの現在の実行文脈から内蔵タイトルを開けるかは、まだ実機未検証。

## 再配置の検証方法

trace_relocation_inputs.pyで6入力の初期化/変換/全候補列挙を観測し、
原本領域から読まれた32-bit値のうち原本範囲を指すものを52箇所抽出した。
数値が番地らしいだけでは採用せず、全52箇所についてidalibの
literal元または読取り命令のxrefが実際の参照先と一致することを確認。
switch tableの途中要素はIDAで要素単独のxrefが付かない場合があるため、
LDR PCの参照先も照合した。参照記録はf400_pointer_ida_validation.json。

全セグメントの相対配置を保ち、同じdeltaで移動する。
この方式では内部B/BL・PC相対参照の相対距離が変わらない。
確認した絶対参照52語だけにdeltaを加え、hostで作るcallback辞書3個も移設先へ向ける。
元領域をunmapするため、古いコードや表へ戻って成功している可能性を排除した。
コードはRX、rodata/dataはRO。OS呼出しのmockや未マップ参照の補完は行わない。

| 項目 | 結果 |
|---|---|
| 元base | 0x00100000 |
| PC試験の移設base | 0x04100000 / 0x06100000（実機の空き領域という意味ではない） |
| 観測に使った入力 | かんじ、わたしはねこがすきです、か、し、123、とうきょう |
| それぞれの候補件数 | 17、6、143、195、2、4 |
| 再配置後の比較 | 両baseで元の候補列と順序一致 |
| 未修正コピーの負の対照 | 旧0x0019094Cへのfetchで停止 |
| 追加の未使用入力 | にほんご4件、どうぶつのもり4件、こんにちは6件、あい59件、がっこう5件も一致 |

元コードhashは既存Probeが検証し、各修正語も期待値一致を検査してからPCメモリへ反映する。
対象は日本語mode0、未学習の独立context。別言語、学習、異常入力、全分岐を網羅した
再配置一覧ではない。動いた経路だけから製品用fixup一覧を確定しない。
次は到達可能関数と全switch table/literalを静的に閉じ、未観測分岐を含む検証を行う。
今回はフルイメージを移したため、コードサイズの最小化も別作業。

再現: `python -X utf8 SYSTEM_KEYBOARD/probe_relocated_engine.py`
証拠: SYSTEM_KEYBOARD/evidence/f400_relocated_engine.json、f400_heldout.json。
このPC検証は提供済みローカルファイルを入力にする。実機向けリソースの配布物ではない。

## リソース同梱を避ける経路

必要なデータは二つに分かれる。

| データ | 内蔵の取得元 | 使い方 |
|---|---|---|
| 日本語辞書6本 | TitleID 0x0004009B00011902 のRomFS | JA_small以下をRAMへ読み常駐辞書を構築 |
| 変換コード・表記変換表など | SWKBD TitleID 0x000400300000C002 のExeFS .code | コードを展開し、定数を含めRAMへ再配置 |

辞書TitleIDと原本のマウント経路は、0x18C18C→0x16F13Cおよび
0x1A4158の言語表で確認済み。元キーボードのプロセスを起動してメモリを借りる必要はない構成。

一次ソースの[libctru romfs_dev.c](https://github.com/devkitPro/libctru/blob/master/libctru/source/romfs_dev.c)
はromfsMountFromTitle(tid,mediatype,name)を実装し、タイトルID/媒体を含むbinary pathで
FSUSER_OpenFileDirectlyを呼ぶ。APT経由の起動処理は含まない。
辞書についてはNAND媒体の上記TitleIDを指定する方式が候補。

コード取得の実例は[Luma3DS loader.c](https://github.com/LumaTeam/Luma3DS/blob/master/sysmodules/loader/source/loader.c)。
loadCodeはprogramHandleとExeFS .codeを指定してFSから読み、必要時にLZSS展開する。
このコードはloader側の文脈であり、ACNL側のハンドル/権限を保証する根拠にはならない。
同じarchive引数をACNLへそのまま流用してよいとはまだ結論しない。

実機確認でまず必要なのは、読取り専用で辞書RomFSとSWKBD .codeを開き、
サイズ・版・hashを今回の解析対象と照合できるか、という点。
未知の版に52語のfixupを当てることはしない。必要な取得権限、code解凍情報、
実行可能RAM確保が揃ってからネイティブ実行を設計する。

今回追加したJSONは解析根拠・再配置箇所の開発用記録であり、変換辞書の配布を求めるものではない。
実機用には取得と再配置を担う処理が要る。変換表本体は本体内蔵データを読み込む方針。
実機/SD/3gxへの変更、ビルドは行っていない。
