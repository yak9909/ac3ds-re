# F-399: 画面・APTを使わない変換エンジン実行

2026-09-10。結論: **日本語予測の変換処理そのものは、画面とAPTから切り離して動く。**
原本ARMを使ったPC実行で初期化から候補列挙まで確認した。
**3DS上の独立モジュールとしての実行は未検証**。実機接続・ビルド・適用は行っていない。
自前メニューやgohanの設計を前提にしない調査である。

## 確認した依存

SYSTEM_KEYBOARD/audit_engine_only.pyは初期化前から全メモリ読書きと実行blockを記録する。
元のProbeはARM割込みで必ず停止するため、SVC/OS呼出しを成功扱いにするmockはない。
APT、描画、HID、スレッド、サービス初期化、アプレットmainは呼んでいない。
辞書ファイルはPC側で読み、原本のメモリ常駐辞書構造へ構築して渡す。
これは辞書の入手・ロード自体を不要にするものではない。

| PC実験 | かんじ | わたしはねこがすきです |
|---|---|---|
| 原本イメージ＋独立context＋常駐辞書 | 17件 | 6件 |
| 原本data/BSS全域を読取り専用 | 同じ17件 | 同じ6件 |
| 原本data/BSSを除去し0x1B8000の1ページだけROで保持 | 同じ17件 | 同じ6件 |
| 原本data/BSS全域を除去 | 0x19BFA8で未マップ読取り停止 | 未試行 |

正常試験はF-398の実機保存値と一致する候補列を維持した。
原本data/BSSへの書込みは観測されず、書込みはcontext、stack、入出力、辞書poolに限定。
不足テーブルを外す負の対照でも停止するため、未マップ参照を黙って補ってはいない。
この1ページ以外が全入力で不要、とまでは確定していない。

## 静的証拠との照合

idalibのSWKBD専用IDBで確認:

- 0x190408は渡されたcontextの設定後、engine=ctx+5392へ0x19D4ECを呼ぶ。
- 0x18C628(ctx,1)は登録済み日本語辞書構成848 bytesを複写してengineを初期化する。
- 0x19D4ECはengine内の状態を初期化し、静的テーブル0x1A872Cへのpointerを格納する。
- 0x19BECCの0x19BF00は設定pointerが0なら0x1B8FD0をロード。
  0x19BFA8のLDRSHがその表を読む。data除去試験の停止点と一致。
- 0x19BF20はLDRCC PC,[PC,R1,LSL#2]で絶対アドレスの分岐表を使う。
  callback辞書slot7..9も関数の絶対pointerを持つ。

原本の静的データまで全て不要という見立ては誤り。
必要なのはアプレットの稼働状態ではなく、コードに付随する変換表と定数である。

## 独立モジュールに必要な契約

1. 原本コード・必要定数表・日本語辞書をロードする。
2. zero初期化した専用contextを確保し、0x190408を呼ぶ。
3. 常駐辞書とwork buffer、関数型辞書slot7..9、接続規則njcon.aを登録する。
4. 0x18C628(ctx,1)で日本語設定を反映する。
5. UTF-16LE入力を0x111FD4(ctx,0,input,0,0,55)へ渡す。
6. 0x1181D0(ctx,out,0,index,112)で候補を取得し、0戻りまたは上限300で止める。

呼出しは同一contextについて直列化する。新しい入力ごとの独立contextが現在の検証条件。
個人学習、共有contextの再利用や並行実行はこの試験に含めない。

観測メモリ（スクリプト計算値、最小必要量や最大保証値ではない）:

- 辞書・辞書handle・work bufferのページ丸め済みpool: 2,088,960 bytes。
- contextは先頭から426,864 bytesまで書込み。試験では1 MiBを確保。
- 呼出し開始SPから観測したstack書込み深さ: 5,620 bytes。試験では1 MiBを確保。
- 原本textは655,360 bytes、rodataは77,824 bytesをそのまま保持。
  実行block記録は削減候補の資料であり、安全に切り出せる全関数集合ではない。
- 原本はVFP命令も使う（0x19D4ECの引数複写等）。実機の呼出しABIとVFP状態も要確認。

## 3DS上で残る作業

**有力な方法は変換コードと辞書を独立したモジュールとしてロードする方式。**
必要なコードの切出し・配置と、絶対pointer/分岐表の再配置検証が先になる。
SWKBDの0x100000起点の配置をACNL内へそのまま持ち込むとゲームコードと重なる。
別プロセスのSWKBD関数番地をACNLから直接呼ぶ方式にもできない。

再配置では関数入口だけでなく、literal、絶対jump table、定数内pointer、
初期化が書き込むpointer、callbackを全部扱う必要がある。
数値がアドレスらしいという理由だけで一括加算する方式は採用しない。
今回は再配置したコードを生成していない。

別案は変換アルゴリズムを原本から再実装することだが、順位・曖昧検索・文節の
同一性検証量が大きい。現段階では原本実行を維持して依存と再配置を詰める方が判断しやすい。
辞書常駐用RAMと実行可能領域の確保、処理時間、呼出しABIは3DS側で別途検証が必要。
これらを満たせばAPTは変換処理の前提にはならない、というのが今回の調査結果。
