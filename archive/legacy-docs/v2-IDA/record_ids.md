# 記録ID・解析者・確度（両ブランチ共通）

2026-09-19制定。規則編集: gpt-6-astra。文書の編集者と元の解析者を区別する。

## IDと出自

- FINDINGS・TODO・設計/検証のIDは **`<解析ソフト>-<解析モデル>-<種別><番号>`**。例: `IDA-gpt-6-astra-F001`、`Ghidra-gpt-sol-5.6-F001`。Fは知見、Tは作業。既存のトピックは `Ghidra-gpt-sol-5.6-CHAT-T006` のように保持する。
- ソフトは実際に使った `IDA` / `Ghidra`、モデルは当該解析を行った正確な識別名。ブランチ名や後の編集者から推定しない。不明なら **`unknown`（不明）**。補助ツールは根拠欄へ別記する。
- 利用者指定の過去分: **既存IDA記録はunknown、既存Ghidra記録はgpt-sol-5.6**。今回の文書移行を理由に過去分をgpt-6-astraへ帰属させない。今後のgpt-6-astra解析には実際のソフトとgpt-6-astraを必ず記載する。
- 採番はソフト・モデル・種別（トピックがあればそれも）の組ごと。既存IDを検索し、最大番号と次番号をスクリプトで計算。同じ完全IDの新規定義は禁止。並行作業ではSESSIONで予約し、commit前に再確認する。
- 新規の引用・IDBコメント・ファイルの識別子には完全IDを使う。別ブランチへ取り込んでも元ID/解析者を維持。再検証は検証者の新IDから元IDへ関連付け、根拠・日付・結果を残す。文書の更新担当を元の解析者と混同しない。
- 移行対応表は `work/record_ids.IDA.json` / `work/record_ids.Ghidra.json`。旧番号には出典ブランチ/ファイルを併記。旧原本・生ログ・過去SESSION・スクリプト・DB/XML内の旧表記は来歴として保持し、対応表で引く。旧 `F-xxx` 等の参照資料も出典を明記し、番号を再利用しない。
- 同じ知見の経過・実装・実機結果は小見出しへ追記し、同一IDを別知見として重複定義しない。マージでは番号の類似だけで記録を同一視せず、両方の根拠と反証を比較する。

## 記入項目と確度

各記録に **完全ID、解析ソフト、解析モデル、日付、対象版/SHA、根拠、確度、未確認点/反証条件** を残す。モデル名は実行情報または利用者の明示に基づき、不明な過去分を推測で補わない。SESSIONにもソフト/モデル/変更対象を記載する。

**利用者指定の運用上の前提として、gpt-6-astraによる解析は他モデルの解析より信憑性が高いものとして評価する。** これは事前の評価であり、結論の正しさの保証や実機確認の代替ではない。無条件に信用せず、一次情報・独立した照合・反証を優先する。矛盾をモデル名だけで裁定しない。unknownを誤りと扱わない。

確度は **HIGH=静的＋実測、MEDIUM=複数静的証拠、LOW=仮説**。モデル名だけで確度を上げたり検証を省略したりしない。他モデルの実測をAstraの未検証仮説で上書きしない。

## 小さく頻繁にcommit

検証可能な一区切り・重要な訂正・利用者への報告・中断/引継ぎの前に、変更があれば差分を確認し小さくcommitする。長期間ため込まず、無関係な作業を混ぜない。未完成/未確認は明示し、保存のcommitを完了や実機成功と扱わない。

既存のXML交換・検証・未確認gohanを作業ブランチへ分ける規則は継続。解析DBを変更した場合は最新XMLと付随ファイルを出力・検証して一緒に保存する。pushは有効な利用者指示の範囲で行い、送信後にremoteと照合する。
