> バイト単位で戻った。ゲームは無傷。結果は IDA-opus-5-F022。**

本セッションで作ったもののうち、**カブトムシ 1 体・その骨アニメ・専用ヒープ 2 本・資源は解放済み**。
12 体の `UnitCursor` と、それらが使う資源・ヒープは残してある（共有しているため別途設計する）。

関連: [models3d](models3d.md)（CPU 側の破棄順は既に確定済み）、IDA-opus-5-F017 / F019。

## 1. 何が問題なのか

CPU 側の呼び出し順は既に確定している（`models3d.md` の「更新と破棄」）。

| 関数 | すること |
|---|---|
| `ModelInstance_Destroy 0x004F053C` | `0x4F0184` で mesh ポインタを昇順に戻してから下へ |
| `SceneNodeHolder_Destroy 0x004ED668` | `holder+4` が非0なら **node vtable[0]** を呼び、**`node+4` のアロケータ**の vtable slot3 で free し、`holder+4` を 0 にする |

**未確定なのは 1 点だけ: GPU がいつその記憶を参照し終えるか。**
`models3d.md` が「この前処理と holder dtor には GPU 完了待ちが無い」と書いているとおり、
ゲーム自身の破棄経路は待たない。つまり**待つのは呼ぶ側の責任**で、
ゲームは「自分が安全な位置でしか呼ばない」ことに依存している。

## 2. 今回わかったこと: 待ちは測れる

### 2.1 提出したノードは毎フレーム捨てられる

`Render_FrameEnd 0x004F1CE4` が 3 本のトラバーサを `sub_49944C` でリセットし、
`Scene_ResetAllContexts` を呼び、`dword_94CA54` を 0/1 でトグルする（**コマンドリストは 2 面**）。
**ケーブから外した次のフレームには、自前ノードはどの配列にも入っていない。**

実測（2026-09-21）: カブトムシを表から外して 46 フレーム走らせたところ、
`node` 576 B と骨配列 4 本（640/640/480/480 B）が**1 バイトも変化しなかった**。
ゲーム側から触られていないことの直接証拠。

### 2.2 GX キューには「発行済み」と「完了待ち」が出ている

`GpuCmd_SplitAndSubmit 0x001280CC` は待たない。28 B のエントリをキューに積み、
`GxQueue_Dispatch 0x0012E7D8` が種別で振り分けるだけ。`GxQueue_Dispatch` の中に:

| 欄 | 意味 |
|---|---|
| `mgr = *(0x00AD9960)` | GX キューの管理体（この boot では `0x3229D06C`） |
| `mgr[6]`（`+0x18`） | 28 B エントリの配列 |
| `mgr[8]`（`+0x20`） | **提出された数** |
| `mgr[9]`（`+0x24`） | **GX へ発行し終えた数** |
| `byte_AD98D8` | **1 = 完了割り込み待ちで止まっている**（エントリ `+2` が 1 のときに立つ） |

したがって **`mgr[9] >= mgr[8]` かつ `byte_AD98D8 == 0`** は
「CPU が積んだものは全部 GX へ渡し終え、完了待ちで止まってもいない」を意味する。

**注意**: これは *dispatch* の完了であって、GPU が描き終えた保証そのものではない。
`byte_AD98D8` が立つのは「完了を待てと印の付いたエントリ」のときだけなので、
**この条件は必要条件であって十分条件ではない**。だから下の手順では
フレーム数の待ちと併用する。

### 2.3 park の位置はフレームの途中である

停止中に上の欄を読むと `submitted=2 / dispatched=0` だった。
park（`0x1B7234`）は描画パスの中なので、**そこから解放を呼ぶのはフレームの途中**になる。
ゲーム自身が破棄する位置（Calc 相）とは違う。これは設計上の制約として残る。

## 3. 何が GPU から見えていて、何が見えていないか

**ここを分けると、危険度がまるで違う。**

| 記憶 | 誰が読むか | 解放の危険度 |
|---|---|---|
| **instance 本体**（`node`、3〜4 KB） | **CPU だけ**。コマンドリストを組む側が読む | 提出をやめた次のフレーム以降は安全と考えてよい |
| **アニメ object と専用ヒープ** | CPU だけ（評価して node へ書く） | 同上 |
| **資源（bcres）の頂点・テクスチャ** | **GPU が直接読む**。コマンドリストが番地で指している | **在庫のコマンドリストが消えるまで解放できない** |
| **資源ヒープそのもの** | 上を含む | 同上 |

つまり **instance とアニメの解放と、資源とヒープの解放は別の問題**で、
前者は後者よりずっと安全に踏める。
**実測（IDA-opus-5-F022）**: この順で 6 段ぜんぶ通り、資源ヒープの解放でも何も起きなかった。
ただしそれは「submit をやめてから数百フレーム経っていた」からで、
**描画中に資源を解放したらどうなるかは試していない**。

## 4. 手順（提案。未実行）

対象はカブトムシ 1 体だけ。12 体のカーソルには触らない。

| 段 | やること | 次へ進む条件 |
|---|---|---|
| T0 | ケーブの表から外し `count` を戻す | **実施済み**。12/12/24 per frame に戻った |
| T1 | 90 フレーム以上走らせる（3 秒） | 骨配列と node が 1 バイトも変化しない（**実施済み・46 フレームで確認**） |
| T2 | ~~`mgr[9] >= mgr[8]` と `byte_AD98D8 == 0`~~ | **この条件は使えない。下の訂正を見ること** |
| T3 | `ModelInstance_Destroy 0x4F053C(holder)` | **実測: `holder+4 = 0`、5,484 B 返却、ゲーム無傷** |
| T4 | `g3d::SkeletalAnim` vtable **スロット5** `0x4EC194(anim)` | **実測: AnimObject と専用ヒープが 0、652 B 返却** |
| T5a | `sub_2F73F4 0x2F73F4(instance allocator)` | **実測: 親ヒープが 11,576 → 36,168（作る前と一致）** |
| T5b | `G3dResHolder_Dtor 0x317CFC(holder)` | **実測: vtable が ResourceSet へ戻り要求欄クリア**。**★必ず資源ヒープの破棄より前に呼ぶ** — 逆にすると SIGILL（IDA-opus-5-F027） |
| T5c | `sub_2F73F4(resource allocator)` | **実測: A のヒープが 19,424 → 68,592（作る前と一致）** |

> **★§2.2 の訂正**: 「`mgr[9] >= mgr[8]` かつ `byte_AD98D8 == 0` を確認してから解放」は成立しない。
> park は描画パスの中なので `submitted=2 / dispatched=0` が常態で、この条件は永久に満たせない。
> 実際に効いている条件は「**その instance を submit しなくなってから2フレーム以上経っている**」で、
> `Render_FrameEnd` が毎フレーム全トラバーサを捨て、コマンドリストが2面で回ることから導かれる。
> GX キューの欄は「今このフレームの積み具合」を見るものであって、解放の門にはならない。

**中止条件**: T3 で戻ってこない／画面が固まる／`holder+4` が 0 にならない。
その場合は**復元せずそのまま停止状態を保持**して調べる（call guard の作法と同じ）。

**やらないこと**:
- 12 体のカーソルには触らない。共有している資源とヒープが絡む。
- 資源の解放を instance の解放と同じ段でやらない。上の表のとおり危険度が違う。
- park から呼ぶ以上フレームの途中になるので、**一度に 1 段だけ**。

## 5. 解決した / まだ調べていないこと

**解決（IDA-opus-5-F022）**

- `g3d::SkeletalAnim` の破棄は **vtable スロット5 `0x4EC194`**。デストラクタ（スロット1）ではない。
  `g3d::MaterialAnim` も同じ並びのはずだが**未検証**（12 体のカーソルで確かめられる）。
- `G3dResHolder_Dtor 0x317CFC` がファイル要求側を片付ける。資源そのものはヒープごと消える。
- `sub_2F73F4(allocator)` が heap vtable[4] を呼んで破棄し、**親ヒープへ正確に返る**
  （親 2 本とも作る前の値とバイト単位で一致）。

**まだ調べていないこと**

- **描画中に解放したらどうなるか**（今回は submit をやめてから数百フレーム置いた）。
- 共有資源で `0x4F0184` の分岐が資源側へ書く場合（`node+0x170 == +0x174` のとき）。
- mesh が多いモデル。局所配列は 65 要素で上限検査が見当たらない。
- 場面転換（部屋の出入り）で何が起きるか。**利用者に操作してもらわないと測れない。**
- OOM。資源ヒープが取れなかったときの巻き戻し。
