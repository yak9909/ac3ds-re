# 設計書: 家具の範囲表示（UnitCursor）を屋外の任意座標に出す

2026-09-18 作成。対象は主 IDB `ida/db/acnl_jpn_v15_annotated.i64` と日本版更新 code。
根拠は IDA-unknown-F019〜IDA-unknown-F022（`work/FINDINGS.md`）と `work/evidence/unit_cursor/`。
**静的解析だけで書いた設計であり、実装もビルドも実機確認もしていない。** 新しい実機確認をするまで確度は MEDIUM。
既存の任意モデル表示（IDA-unknown-F007 / IDA-unknown-F010、`models3d.md`）の上に載せる。

## 1. 目的と方針

模様替えで家具の下に出る範囲表示（`UnitCursor`）を、屋外（村など）で好きな座標に出す。

ゲームの実装（`AcObjUnitCursor`、`ModuleIndoor.cro`）は屋内専用で、屋外では
資源もクラスも載らない（IDA-unknown-F019、IDA-unknown-F020）。よって**ゲームのクラスは使わず、資源だけ借りて自前で描く**。

| 方針 | 採否 | 理由 |
|---|---|---|
| ゲームの `AcObjUnitCursor` を屋外で動かす | 不採用 | クラスが `ModuleIndoor.cro` にあり、屋外の場面では載らない（`Room_SelectModules` がビット 8 のときだけ `Indoor` を積む） |
| `ScStage_LoadIndoorRes` の屋内判定を外す | 補助的 | 資源は読めるようになるが、描く側が無いので単独では成立しない |
| **資源を自前で読み、自前でモデルを作って描く** | **採用** | 屋外でも描画基盤（`BsFtrMgr`・シーン）は動いている（IDA-unknown-F020）。既存の任意モデル表示と同じ土俵 |

## 2. 全体の流れ

```
[一度だけ]
  ヒープ確保 → 資源の読み込み要求 → (完了まで毎フレーム待つ) → Setup
  → モデル検索 → モデルインスタンス生成
[毎フレーム]
  行列を設定 → ワールド更新 → シーンへ登録（番号 0）
[終了時]
  インスタンス破棄 → 資源解放 → ヒープ解放
```

### 3.1 シーン番号（IDA-unknown-F022）
`Scene_SubmitNode` の第 2 引数は画面ではなく描画パスの種類。

| 番号 | 中身 | 使うか |
|---|---|---|
| **0** | 通常の描画（`Render_DrawScene0`、`byte_94CA2C == 0` のとき） | **これを使う** |
| 1 | `byte_94CA2C == 1` のときだけ描く別モード（カタログ等のプレビューと推定、LOW） | 使わない |
| 2 | 影マップ（IDA-unknown-F008） | 使わない |

**訂正（2026-09-18、IDA-unknown-F024）**: 以前ここに「上画面パス（1024）と右目/下画面パス（1040）」と書いたのは誤り。
3 本の描画パスと画面の対応は次のとおりで、**下画面には 3D シーンが積まれない**。

| 関数 | VA | display | 画面 | `Render_DrawScene0/1` を呼ぶか |
|---|---|---|---|---|
| `Frame_DrawPass1024` | `0x001B71C4` | `0x400` | 上画面・左目 | **呼ぶ**（影 2 → 0 → 1） |
| `Frame_DrawPass1040` | `0x001B72E4` | `0x410` | 上画面・右目 | **呼ぶ**（0 → 1、末尾に `Render_FrameEnd`） |
| `Frame_DrawPass1025` | `0x001B7090` | `0x401` | 下画面 | **呼ばない**（`ssys_ma_lyt_LayoutMgr_RenderBottom` だけ） |

関数テーブルは `0x008E5854`（`…54`=1025 / `…58`=1024 / `…5C`=1040）、実測の実行順は `0x400 → 0x410 → 0x401`（旧 F-253、HIGH）。
したがって **番号 0 に積めば上画面の左右両目に出る。下画面には出ない。**
`Render_FrameEnd` は右目パスの末尾なので、**1 フレームにつき左目パスより前に 1 回 `Scene_SubmitNode` すれば両目に描かれる**。
旧 F-111 / F-112 の実機実例も番号 0。

### 3.2 非同期読み込みの待ち方
**訂正（2026-09-18、IDA-unknown-F025）**: 以前ここに「`holder+232` が状態」と書いたのは **28 バイトずれた誤り**。
`G3dResHolder_RequestLoad` は `FileRes_RequestLoadAligned(holder + 28, …)` と呼び、`FileRes_RequestLoadAligned` はそれを素通しするので、
**FileRes 部分は `holder+28` から始まる**。したがって FileRes 内の欄はすべて +28 を足して読むこと。

| FileRes 内 | holder 基準 | 中身 |
|---|---|---|
| +68 | **holder+96** | パス文字列 |
| +204 | **holder+232** | ヒープ |
| +228 | **holder+256** | アライン |
| +232 | **holder+260** | **状態**（0 未要求 / 1 要求済み / 2 同期読み / 3・4・5 完了） |
| +233 | **holder+261** | 非同期旗 |
| +208 | **holder+236** | 読み込んだ資源の先頭。完了時に `holder+4` と `holder+8` へ複写される |

「holder+232」は実際にはヒープの欄で、実機で読むと状態値ではありえない値が入っている（独立な 2 経路で確認）。
初回呼び出しでパス・ヒープ・アラインを記録し、以後は**完了するまで毎フレーム同じ引数で呼び直す**。
ゲーム自身（`ScStage_PrepareStep`）も毎フレーム呼んで待っている。完了したら Setup を 1 回だけ通す。

## 4. 状態機械（実装側）

| 状態 | やること | 次へ進む条件 |
|---|---|---|
| `Idle` | 何もしない | 利用者が ON |
| `HeapReady` | ヒープを作る | 確保できた |
| `Loading` | 毎フレーム `G3dResHolder_RequestLoad` | 戻り値が真 |
| `SetupDone` | `G3dResHolder_Setup` → モデル検索 → インスタンス生成 | すべて成功 |
| `Visible` | 毎フレーム 行列設定 → ワールド更新 → `Scene_SubmitNode(holder, 0)` | 利用者が OFF、または部屋が変わる |
| `Teardown` | インスタンス破棄 → 資源解放 → ヒープ解放 | 完了 |

部屋の切り替え・セーブ・通信の開始時は先に `Visible` を抜けて `Teardown` する（資源の寿命は `models3d.md` の「共通の入口と寿命」に従う）。

## 5. 実行文脈（重要）

- 生成・登録・破棄は**ゲームのスレッドから、描画の前**に行う。プラグインの別スレッドから直接触らない。
- `Scene_SubmitNode` は毎フレーム必要（`Render_FrameEnd` がフレーム末に全シーンを空にする）。
- 呼び出す位置（フック先）は §7.4 に候補を 2 つ挙げた（Base オブジェクトのリストに乗せる / 描画パスに 1 本フック）。

## 6. 見た目の扱い

- 資源のモデルは `UnitCursor` 1 つ。`UnitCursorLine` はその中のノード。マテリアルは `m_UnitCursor` 1 つだけ。
- アニメは 3 本。**3 本とも対象グループは `MaterialAnimation`**（`tools/bcres_anim_dump.py`）。

| 名前 | ループ | 尺 | 用途 |
|---|---|---|---|
| `UnitCursor` | ループ | 150 | 通常時の明滅 |
| `UnitCursorNG` | ループ | 150 | 置けないときの明滅 |
| `UnitCursorRotate` | ワンタイム | 3 | 家具の大きさ（0〜3 の 4 コマ）で止めて形を選ぶ（`0x00690B68` の `(v+2)>>2`） |

  3 本ともマテリアルアニメなので、動かすのは色や UV であって形ではない。アニメを使わなくてもモデルの形は出る。
- **第一段階ではアニメを使わず、モデルをそのまま出す。** 色や NG 表示が要るようになってから §10.2 の順で呼ぶ。

## 7. 解けた項目（2026-09-18 追記、IDA-unknown-F023）

### 7.1 資源ホルダの型と大きさ ✅
`ScStage` のコンストラクタ 0x007F195C（ScStage 全体は 3,504 B）から:

| 位置 | 中身 | 初期化 | 破棄 |
|---|---|---|---|
| `ScStage+0x418` | `ssys::ma::HeapAllocator`（8 B: vtable ＋ ヒープ） | `HeapAllocator_Ctor` 0x005667E8 | `HeapAllocator_Dtor` 0x00317CBC |
| `ScStage+0x420` | **G3D 資源ホルダ（`g3d::ResourceLoader` ＋ `ResourceSet`）、264 B**（0x420〜0x528） | `G3dResHolder_Ctor` 0x004ED860 | `G3dResHolder_Dtor` 0x00317CFC |

ホルダ内の **`+260`** が読み込み状態（§3.2 の訂正表）。自前で持つなら **264 B を確保して `G3dResHolder_Ctor` を通す**。

### 7.2 `ModelInstance_Create` の引数 ✅
`sub_48E350` → `sub_736158` → `nwgfx_Model_Create` と追った結果:

| 引数 | 行き先 | 意味 |
|---|---|---|
| a5（UnitCursor は `0x834`） | desc+0x10 → `model+0x188` | マテリアルのコピーマスク（どの欄を専用にするか） |
| a6（`1`） | desc+0x24 | フラグ（byte） |
| a7（`3`） | desc+0x1C → SceneNode+72 / +324、holder+8 | ノードに持たせる個数。木は 1、UnitCursor は 3 |

**実装ではゲームと同じ `(0x834, 1, 3)` をそのまま使う**のが安全（木の `(0, 0, 1)` とは別物）。

**a3 / a4（この表に載っていなかった、2026-09-18 追記）**: どちらも **`ssys::ma::HeapAllocator` のようなアロケータ物体**で、生ヒープではない
（IDA-unknown-F010。`sub_58EEC0` は自分の `a1+32` を 2 つとも渡す）。ここに渡したヒープからインスタンスが取られる。

**★成功判定（IDA-unknown-F025、実機で確認）**: この関数は **半分しか組み立てられていなくても 1 を返し、`holder+4` にもノードを入れる**。
ヒープが足りないと `sub_4A9A04` の内部ビルダが負を返して打ち切られ、**`MaterialActivator` を作るブロックに到達せず `model+0x1EC` が 0 のまま**になる。
そのインスタンスを描くと `0x00494C18` の `LDR R2,[R0]` で NULL 参照して止まる。

**この負の戻り値の原因は 1 つしかない（2026-09-18 に静的検証）**: `sub_4A9A04` が呼ぶ内部ビルダ 9 本の
`0x80000000` 設定箇所を全部（28 箇所）調べたところ、**すべてアロケータの `vtable+8`（Alloc）が null を返したとき**だった。
書式不正やデータ不正で失敗する経路は無い。ただし確保の多くは**整列 32** を要求するので、
**「総バイト数が足りない」とは限らず**、断片化や整列でも失敗する。
よって **戻り値と `holder+4` だけでは不十分で、`model+0x1EC` が非 0 であることまで確かめる**こと。
また **資源用ヒープとインスタンス用ヒープは分ける**。ゲームの `UnitCursorRes`（20,480 B）は**資源専用**で、
そこへ 16,256 B の bcres を読むと約 4 KB しか残らず、3,064 B のインスタンスは静かに半壊する。

### 7.3 マス座標 → ワールド座標 ✅
`Field_TileToWorld` 0x006A6364:

```
world.x = 32 * tileX + 16
world.z = 32 * tileY + 16
world.y = Field_GetGroundHeight(tileX, tileY, 0)   // 0x006C54AC
```

**1 マス = 32 単位、マスの中心は +16。** 高さは別関数なので、地形補正（`sub_58EEC0` の家具向けの上乗せ）とは切り離して使える。
実機で拾った描画中モデルの行列の平行移動が `x = 2607.82 ≒ 81×32+16 = 2608` とマスの中心に載っており、この式を独立に裏付けている（2026-09-18）。
屋内（部屋 43 やキャンプ場）では家具側が +16.0 の上乗せをしているが、屋外の素の配置には不要。

### 7.4 フック位置（候補まで確定）
`BaseObj_RunDrawPhase` 0x0051EE50 が Base オブジェクトの連結リストを回し、各オブジェクトの slot 11 → 12 → 13 を呼ぶ。
**旧 F-113 に「slot 12 が `Scene_SubmitNode` を呼ぶ場所。自前描画はこのリストに乗るのが最も自然」**と記録がある。

| 案 | 内容 | 評価 |
|---|---|---|
| A | Base オブジェクトのリストに自前オブジェクトを登録する | ゲームと同じ流儀。手数は多い |
| B | `Frame_DrawPass1024` 0x001B71C4 の `BaseObj_RunDrawPhase` 呼び出し直後（0x001B7218）にフックを 1 本置き、そこで自前の更新と登録を回す | 手数が少ない。まずこちらで試す |

注意: ここは**描画スレッド**。非同期読み込みの進行をこのスレッドから回してよいかは未確認（LOW）。
読み込みだけはゲーム側の準備段（`ScStage_PrepareStep` と同じ流れ）で回す案も残す。

## 10. 追記（2026-09-18、IDA-unknown-F024）: 描画順・描画状態・アニメ・ヒープ量・スレッド

### 10.1 描画順と描画状態は静的に確定する

**描画順を決めているのはマテリアルの「レイヤー」**。`Scene_DrawLayers 0x004EB840` は外側で `i = 0..3` を回し、
メッシュごとに `material → (+8 の元 ResMaterial) + 32` の下位バイトが `i` と一致するときだけ `sub_48D26C 0x0048D26C` で
GPU コマンドを積む。**同じレイヤーの中は配列 #0 の並び順＝`Scene_SubmitNode` で積んだ順**で、並べ替えは一切ない。

romfs 全体（`.bcres` 1,907 ファイル / 名前つきマテリアル 2,577 個）のレイヤー分布と、
各マテリアルに焼かれた PICA 描画状態の対応（`tools/models3d/dump_material_state.py --survey`、
出力は `work/evidence/unit_cursor/material_state.txt`）:

| レイヤー | 個数 | うち完全不透明（`ONE`/`ZERO`） | 性格 |
|---|---|---|---|
| 0 | 2,160 | 1,839（85%） | 不透明ジオメトリ |
| 1 | 401 | 27（7%） | **半透明・加算合成** |
| 2 | 4 | 0 | フェード（`idr_room_ChipTutorial:m_fade`） |
| 3 | 12 | 0 | レンズフレア（`esc_map:lens_flare_w` ほか。全部 `SRC_A + ONE` の加算） |

**`m_UnitCursor` はレイヤー 1** なので、不透明の地面・家具（レイヤー 0）を全部描いたあとに描かれる。

描画状態はコード側には無く、**MTOB に焼かれた PICA コマンド列**を `sub_48D26C` の末尾が
`Mem_CopyBytes(g_GpuCmdPtr, mesh+0x68, mesh+0x6C)` でそのまま GPU へ流している。だから romfs を読めば確定できる:

| レジスタ | 値 | 意味 |
|---|---|---|
| `0x0100` COLOR_OPERATION | `0x00E40100` | blend_mode = 1（ブレンド有効） |
| `0x0101` BLEND_FUNC | `0x01160000` | **RGB = src×SRC_ALPHA + dst×ONE（加算合成）**／A = src×ONE + dst×ZERO |
| `0x0104` FRAGOP_ALPHA_TEST | `0x00000010` | アルファテスト**無効** |
| `0x0105` / `0x0106` | `0xFF000000` / `0` | ステンシル**無効** |
| `0x0107` DEPTH_COLOR_MASK | `0x00000041`（byte mask = 1） | **深度テスト有効・比較 LESS**。書き込みバイトが最下位だけなので**深度書き込みビットは書き換えず直前の状態を引き継ぐ** |

ここから静的に言えること:

- **地面に埋まる部分は深度テスト（LESS）で隠れる。** 完全に地面と同一平面に置いたときだけ Z ファイトの恐れがあるので、少し浮かせる。
- **加算合成なので「地面より明るく光る」**。黒い画素は透明になり、下の地面を暗くすることはない。半透明の見え方はこれで説明できる。
- **影は落ちない。** 影マップはシーン番号 2（IDA-unknown-F008）で、そこに積まなければ影は生成されない。

残る実機確認は「実際にどう見えるか」だけで、**描画順・深度・ブレンド・影の有無は実機を待つ必要がない**。

### 10.2 アニメの割り当て API

呼び出し元（例: `sub_227020` の `0x002272B4 / 0x002272C4 / 0x002272DC / 0x002272D0`）では次の順で連続して呼ばれる。

| 順 | VA | 引数 | 中身 |
|---|---|---|---|
| 1 | `0x004EBC14` | `(anim, a2→anim+24, ResAnim(CANM), allocatorHolder, flag→anim+28)` | 資源に結び付けて作る。内部で `Heap_CreateNamed_0` が**名前 `MaterialAnim::build`** のヒープを作り、`sub_566700` で実使用量まで縮める。失敗時は 0 |
| 2 | `0x004F0300` | `(instance, anim, slot)` | `node[82]` が非 0 のときだけ、`node[10]` の表の `[slot + node[83]×行長]` へ `*(anim+8)` を書く。**範囲外は黙って無視**され、戻り値では判別できない |
| 3 | `0x004EDC74` | `(anim, value)`（value は **VFP s0**） | 内部オブジェクトの `+64` に float を 1 つ入れる |
| 4 | `0x004EDBD0` | `(anim, mode)` | mode 0/1 で毎フレームの評価関数（`sub_4D3EFC` / `sub_4D3E70`）を選び、どの値でも `anim+4` に mode を保存 |
| 5 | `0x004EDC98` | `(anim)` | `+76` の関数を `+80` を引数に呼び、`+60 = +56`（退避）・`+56 = +68`（次の値を現在値へ）・`+88 = 1`（更新済み印）。常に 1 を返す |

UnitCursor の 3 本は**すべて `MaterialAnimation`**（§6）なので、1 の作る `MaterialAnim::build` ヒープと整合する。

### 10.3 必要なヒープ量: インスタンス 3,064 B

`sub_736158` の第 9 引数を 1 にするとサイズ問い合わせだけが走る。この経路を Unicorn（ARM11MPCore）で回す
`tools/models3d/query_model_size.py` に、ゲームと同じ記述子（`+0` ResModel / `+4` = 1 / `+0x0C` = 4 /
`+0x10` = マテリアルコピーマスク / `+0x1C` = 個数 / `+0x24` = フラグ）を渡した結果:

| 資源 | マスク | 個数 | バイト数 | 最大アライン |
|---|---|---|---|---|
| `UnitCursor` | `0x834` | 3 | **3,064** | 32 |
| `fg_treeA_4`（検算） | `0` | 1 | 932 | — |
| `fg_treeA_4`（検算） | `0x10` | 1 | 1,664 | — |

下 2 行は IDA-unknown-F011 が別経路で出した値と一致するので、道具そのものの検算になっている。

**訂正（2026-09-18、IDA-unknown-F025）: この 3,064 B を「確保すべき量」として使ってはいけない。**
実機で 20,480 B のヒープに 16,256 B の bcres を読み、残り **4,224 B**（20,480 − 16,256）に 3,064 B のインスタンスを作ろうとしたところ、
数字の上では 1,160 B 余るのに**組み立てが途中で打ち切られた**（`model+0x1EC` が 0 のまま。§7.2 の成功判定を参照）。
理由は 2 つあり、どちらも上の数字には入っていない:

1. **`G3dResHolder_Setup` は同じアロケータから確保する。** 読み込んだファイルの大きさだけでなく、Setup が作る構造も同じヒープを食う。
2. 組み立ては多数の小さな確保に分かれるので、`sead::ExpHeap` のブロック管理領域とアラインの上乗せが積み上がる。

実務上は **資源用ヒープとインスタンス用ヒープを分け、どちらも余裕を持たせる**こと。
実機で通った構成は資源 0x40000・インスタンス 0x20000。ゲームの `UnitCursorRes`（20,480 B）は**資源専用**で、
`AcObjUnitCursor` の 64 枠のインスタンスはそこからは取っていない。

### 10.4 非同期読み込みとスレッド

`FileRes_RequestLoadAsync 0x00569BA0` は要求をロックで守られたキューへ繋ぐだけなので、
**データ構造の上では呼ぶスレッドを選ばない**。非同期フラグが 0 のときは `sub_569EFC` の同期経路に落ちるが、
そちらはその場で読み切るのでフレームを止める。よって描画パスにフックを置く案（§7.4 の B）でも
**要求だけ出して完了を毎フレーム確認する**形なら成立する。ただし**これは静的な結論**で、実機での可否は別に確かめること。

## 11. 実機確認（2026-09-18、屋外の村。**コード注入なし**）

道具は `tools/hw/unitcursor_hw.py`（IDA の GDB セッションで `py_exec_file`。MODE を書き換えて使う）。

**レジスタ注入でゲーム関数を直接呼ぶ**。`.text` へは 1 語も書いていない。

### 11.2 マテリアルは正常だった（仮説 2 件を棄却）

`MaterialActivator::Activate` 0x0049C08C を読むと、マテリアル `a3` の `a3[10]..a3[20]` が側面（色・テクスチャ・ブレンド等）を指し、
**コピーマスク 0x834 の側面だけインスタンス専用コピーを指す**（自前インスタンスでは `a3[12]/[14]/[15]/[20]`）。実機で読んだ結果:

- **色**: 専用コピーと ResMaterial が**完全に同値**（`0xFFFFFF` / `0xFF000000` ほか）。→ 「アニメ未結合で色 0、加算の黒で不可視」**は誤り**。
- **テクスチャ**: 両者同一。128x128、物理アドレス `0x20FCFA00`（reg 0x0085 = `0x041F9F40`）。正しく束縛されている。
- **ブレンド・深度**: 実機のバイト列が **romfs の静的解読と完全一致**（`0x0100=0x00E40100` / `0x0101=0x01160000` 加算 / `0x0107=0x41` 深度 LESS）。IDA-unknown-F024 の PICA 解読が実機で裏付けられた。

### 11.3 残る問題: ジオメトリが 1 枚もラスタライズされていない

自前インスタンスの**専用コピーだけ**を不透明（`0x0101` = ONE/ZERO）・深度 ALWAYS に書き換えて描かせても、画面は変化しない。
倍率 40 倍でも同じ。**フラグメントが 1 つも出ていない**と判断できる。

**訂正（2026-09-18、IDA-unknown-F025）**: ここで比べた `mesh+0x68` は**メッシュが持つ 2 本のコマンド列のうち 2 本目**にすぎない。
`sub_4957C4` 0x004957C4 を読んだ結果、`sub_48D26C` は描画コマンドを流す**前に**もう 1 本を流していた。

| メッシュの欄 | 中身 | 流す場所 |
|---|---|---|
| `mesh+0x2C` | フラグ（ビット 0/1 が描画コンテキスト +20 の 0x80 / 0x100 を上げ下げ） | `sub_4957C4` |
| `mesh+0x30` | 48 バイトの埋め込みコマンド列 | `sub_4957C4` |
| **`mesh+0x60` / `+0x64`** | **コマンド列へのポインタと大きさ。頂点属性・バッファ束縛はこちら** | **`sub_4957C4`** |
| `mesh+0x68` / `+0x6C` | 描画コマンド列 | `sub_48D26C` の末尾 |

したがって **`mesh+0x6C` の側だけを見て「ジオメトリは渡っている」と判断してはいけない**。当初そう判断したのは誤りだった。

さらに `UnitCursor.bcres` を走査すると **`0x0200`〜`0x0230`（属性バッファ系）のコマンドが 1 つも無い**。
つまり **1 本目のコマンド列はファイルに入っておらず、実行時に組み立てられる**。組み立てるのはモデル生成側
（`ModelInstance_Create` → `sub_48E350` → `sub_736158` → `sub_4A9A04` の内部ビルダ群）なので、
**インスタンスの組み立てが途中で打ち切られると、マテリアルは正常なのにジオメトリのコマンドだけが欠ける**という状態が起こりうる。
これは §11.2 で分かった「マテリアルは全部正常」と「画素が 1 つも出ない」が同居する理由として辻褄が合う。

次に確かめるべきは **自前インスタンスの `mesh+0x60` / `+0x64`** と、正常なモデルの同じ欄の比較。

### 11.4 道具の注意（同じ罠に二度はまらないため）

- **MCP プロキシは 30 秒で切れるが IDA 側のスクリプトは走り続ける。** 長いループを入れると `call()` のレジスタ復元前に中断され、
