# 実機手順の設計: IDA-unknown-F027 の決着（UnitCursor 屋外表示）

2026-09-18 作成。**設計 → 検証 → 実装 → 検査・逆アセンブル → 適用** の「設計」にあたる文書。
適用（実機での実行）は、この設計に対する検証（`tools/hw/verify_unitcursor_hw.py`）と
実装の検査が通ってから行う。

前回の実機作業でゲームを壊した。原因は**失敗した戻り値をそのまま次の関数へ渡したこと**で、
具体的には `Heap_CreateNamed_0` が 0 を返したのに `heap = 0` のまま `G3dResHolder_RequestLoad` を呼び、
描画スレッドが不正な番地へ飛んだ。この設計はそれを構造的に起こさないことを第一の要件にする。

## 1. 目的（測るのは一点だけ）

自前で作ったモデルインスタンスの **`mesh+52`（当時は頂点バッファの GPU 番地だと考えていた欄）が 0 かどうか**。

**※ 適用後の訂正（§8、IDA-unknown-F028）**: `mesh+52` は番地ではなく `sub_4A8B44` が書く定数 `0x000F02C0`（PICA のコマンドヘッダ）だった。
頂点バッファの束縛は属性コマンド列の中にあり、`ATTRIBBUFFERS_LOC`（基底）と `ATTRIBBUFFER0_OFFSET`（差分）の和で表される。
以下の §1〜§7 は適用時点の設計のまま残す。

| 結果 | 意味 | 次 |
|---|---|---|
| `mesh+52 == 0` | **IDA-unknown-F027 確定**。`sub_143B54`（→`sub_140C3C`）が対応外領域で 0 を返し、頂点バッファ基底が 0 になっている | 資源を線形（GPU 可視）領域へ置く設計に移る |
| `mesh+52 != 0` | **IDA-unknown-F027 棄却** | `desc[usage+76]` の属性番号対応（`sub_7E5710` は `>= 0` の除外判定を持たない）を疑う |

同時に取る補助測定: `mesh+0x60/+0x64`（属性列）、`mesh+0x68/+0x6C`（描画列）、`mesh+128`（アロケータ）、
`node+0x1EC`（活性化子）、`holder+12`、`holder+260`（読み込み状態。IDA-unknown-F025 で訂正した正しい位置）。
比較対象として、ゲームが実際に描いているモデルの `mesh+52` も 1 件取る。

**今回やらないこと**: 毎フレーム `Scene_SubmitNode` するコードケーブ。原因が確定するまで設計しない。
画面へ出す試み（`show`）も行わない。測るだけ。

## 3. 手順（各段に検査と中止条件）

`call(fn, args, stack)` は毎回 **RET_TRAP へ戻ったこと**を確認し、戻らなければ全レジスタを復元して中止する。

| # | 段 | 呼ぶもの | 成功条件（満たさなければ中止して後始末） |

| S2 | 作業領域の借用 | `sub_4B8CF0(0x200, 32)` | 戻り値が `0x10000000 < p < 0x40000000` |
| S3 | アロケータ A の構築 | `HeapAllocator_Ctor(p+0x10)` | **`*A == 0` のときだけ呼ぶ**。呼んだ後 `*A == 0x0090053C` かつ `A[1] == 0` |

## 4. 後始末（中止時も正常終了時も同じ手順）

作った順と逆に戻す。**作れなかったものは触らない。**

1. ヒープ B → `A`/`B` の `+4` が非 0 なら `(*(*(X+4)+16))(X+4)`（`Heap_CreateNamed_0` が古いヒープを壊すのと同じ呼び方）
2. ヒープ A → 同上
3. 作業領域 → `ssys_ma_Allocator_Free(*(0x0096F150), p)`（旧 F-296 で実機確認済みの対）

**アロケータを作り直してはいけない**: `HeapAllocator_Ctor` は `+4` を 0 にするので、既存ヒープの handle を失って漏れる。
前回はこれで実行のたびに 0x60000 漏らし、親ヒープが枯れた。

## 5. 安全規則（実装が守るべきこと）

- **戻り値を検査せずに次へ渡さない。** 各段は成功条件を満たしたときだけ次へ進む。
- **1 回の `py_exec_file` は 45 フレーム相当以内**に収める。MCP プロキシは 30 秒で切れるが IDA 側の
  スクリプトは走り続け、`call()` のレジスタ復元前に中断されると描画スレッドが宙吊りになる。
- **未マップ番地を読まない。** 参照前に `0x30000000 ≤ addr < 0x34000000` と 4 バイト整列を検査する
  （未マップの読みは 60 秒ブロックする）。
- **結果は必ずファイルへ書く**（`work/evidence/unit_cursor/hw_last_result.json`）。時間切れで標準出力が失われるため。
- ヒットしたソフト BP は再開前に必ず削除する。
- 復旧値: park の文脈は `PC=0x001B721C / SP=0x0FFFFE20 / R4=1 / R5=0x0096F350 / LR=0x00520008`。
  `R5` は `0x001B72D4` のリテラル。

## 9. 測定 2 の設計: 頂点シェーダへ届く行列（2026-09-19）

§8 で「資源・マテリアル・コマンド列・頂点バッファの束縛はすべて正常」と確認できたのに画素が出ない。
静的に追うと、**頂点が実際に置かれる場所を決めているのは行列プール**だと分かった。

- `sub_48D26C` の 3 本目 `sub_48D51C` と、その先の `sub_48D34C` が
  **`reg 0x02C0`（VSH_FLOATUNIFORM）へ 3x4 行列を積む**。行列は `model+544` の行列プールから、ボーン番号で引く。
- プールを更新するのは `UpdateWorldAndSkeleton` の後半 `sub_4EF624`。逆アセンブルすると

  ```
  4EF658  LDRB R0, [R4,#0x231]   ; node+561
  4EF65C  CMP  R0, #1
  4EF660  BEQ  locret            ; 1 なら何もせず帰る
  4EF664  LDR  R0, [R4,#0x220]   ; node+544 = 行列プール
  4EF668  STRB R6, [R0,#0x18]    ; プール+24 = 0
  4EF680  B    sub_7375A8        ; プール更新（末尾呼び出し）
  ```

  つまり **`node+561` が 1 なら、行列プールは一度も更新されない**。
  その場合シェーダには初期値のまま（単位行列か未初期化）が届き、**全部正常でも頂点がどこにも出ない**。

### 測る欄（すべて読み取り。副作用のある呼び出しはしない）

| 欄 | 期待 | 意味 |
|---|---|---|
| `node+561`（0x231） | **0 であってほしい** | 1 なら行列プールが更新されない |
| `node+544`（0x220） | 非 0 | 行列プールの本体 |
| プール `+24` | 0 | `sub_4EF624` が毎回 0 にする印 |
| `node+0xBC`（12 float） | 我々が設定した平行移動を含む | ワールド行列（`sub_4EF69C` が書く） |
| `model+200` 配列 → `mesh+24` 番目 → rel | 非 0 | このメッシュのボーン束縛（`sub_48D26C` の `v14`） |
| その `+44` / `+48` | 個数と配列 | `sub_48D51C` が回すボーン一覧 |

### 判定

| 結果 | 意味 |
|---|---|
| `node+561 == 1` | **確定**。行列プールが更新されないので、`UpdateWorldAndSkeleton` を呼んでも行列がシェーダへ届かない |
| `node+561 == 0` かつプールの行列が単位/ゼロ | プール更新は走るが中身が入っていない。`sub_7375A8` の前提を調べる |
| プールに我々の平行移動が入っている | 行列は届いている。残るは属性番号対応（§1 の (a)）とシェーダ束縛 |

### 安全性

測定 2 は**読み取りのみ**で、ゲームの関数を新たに呼ばない（§3 の S1..S12 で作った状態をそのまま見る）。
したがって §4 の後始末以外に副作用は無い。
