## 1. 答え（結論だけ）

### 1.1 case 5 の `0x00606D78`

`0x0094A6EC` の 8 バイトは **`BsSvMgr` の mode を指すメンバ関数ポインタ対 `{ptr, adj}`**。
`sub_606D78` はそこに `0x006066A0` を書く。

mode 表は **`0x00851B04`、20 バイト × 33、`{名前, enter{ptr,adj}, calc{ptr,adj}}`**。
`BsSvMgr::initialize` が同じ対に書く 3 定数と突き合わせて確定:

| 値 | mode | 名前 |
|---|---|---|
| `0x006064C4` | 0 | 待機 |
| `0x006064B0` | 19 | ソフトリセット用ロード処理 |
| **`0x006066A0`** | **31** | **セーブエラー用村作成処理** |

→ **case 5 はセーブデータ破損時の村再作成へ誘導するエラー復旧分岐。通常セーブではない。**

### 1.2 「準備しています」

- 文言の実体 = **`Script/Talk/SYS_Save.umsbt` の index 1 / ラベル `002`**。
  romfs 全 16,303 ファイル（830.8 MB）を走査し、さらに MSBT を解析してタグを除去した
  **全 3,297 本の本文**で照合しても、ここにしか無い。
- **BsSvMgr mode 7 ではない。** mode 7 の最初の状態「セーブメッセージ要求」(`sub_608930`) は
  ラベル **4**「セーブしています」。
- **出どころ = `ModulePlSelect.cro`（部屋 `0x63`＝しずえ画面）の case 0。**

```asm
00BE6B10  LDR R0,=0x0094A6D4   ; off_94A6D4（.data seg2 からの匿名インポート）
00BE6B14  ADD R3,R4,#632
00BE6B18  MOV R1,#2            ★ラベル番号 2
00BE6B1C  LDR R2,[R0]          ★"SYS_Save"
00BE6B20  MOV R0,R4
00BE6B24  BL  0x002388BC       ; sub_2388BC(this, 2, "SYS_Save", this+632)
```

## 2. ★引き継ぎで最も大事な話 — 私の前提が誤っていた

**「`sub_5DC940` はメッセージ 1 件ごとに必ず通る」は誤り。**
そこにトレースケーブを仕掛けて起動〜村で 0 件だったので
「起動経路はアーカイブ＋ラベルの仕組みを使っていない」と結論したが、これが間違い。

利用者の指摘「セーブ確認のあと住民にも話しかけたのに記録が 1 件しかないなら、
あなたが勘違いしている可能性が高い」が正しかった。

`"%03d"`（書式文字列 `0x0088EE30`）の**利用者は画像全体で 5 本ある**:

| 整形関数 | 役割 |
|---|---|
| `sub_5DC940` `0x005DC940` | フックしたもの。**システムメッセージ経路の 1 本にすぎない** |
| `sub_5E3704` `0x005E3704` | `*a1+8` にアーカイブ、`*a1+52` にラベル。番号は `a1[16]` |
| `sub_5E94E0` `0x005E94E0` | 汎用「番号 → 文字列」 |
| `sub_5F2954` `0x005F2954` | `a1[1]+52` にラベル、`a1[1]+8` にアーカイブ。**`sub_5DC940` を通らない** |
| `sub_75B914` `0x0075B914` | 別系統 |

さらに **`sub_6028A4` `0x006028A4`** という別の要求 API があり、これも `sub_5DC940` を通らない。
BsSvMgr 自身も `sub_60A118` の分岐でこちらを使う。

> **教訓（次に同じ轍を踏まないために）**
> 「この関数を通れば必ず捕まる」と決める前に、
> **その書式文字列・その定数の利用者を画像全体で数える。**
> トレース点は 1 本ではなく**合流点**（§3.3）を狙う。

## 3. 確定した構造（再開時はここを読む）

### 3.1 script/talk マネージャ

構築は **`sub_6032E4` `0x006032E4`**。`+820`〜`+900` に部品を並べる。

| 欄 | 中身 | 大きさ |
|---|---|---|
| +840 | `TalkSeq_Create` の産物 | |
| +848 | `sub_5D75C0` の産物 | 74,308 B |
| +852 | **`script::TalkPhrase`**（vtbl `0x00902FA8`） | 12 B |
| +856 | 小物体 | 16 B |
| **+860** | **表示スロット**（いま出ているメッセージの要求内容） | **124 B** |
| **+864** | **要求スロット**（誰かがここに書く） | **124 B** |
| +868 | 登録中のメッセージ物体（`sub_6014CC` が入れる） | |

★実機で mgr を同定する手順: ヒープを走査して `script::TalkPhrase` の vtable
（`0x00902FA8`）を持つ 12 バイト物体を探し、それを指す語を探すと `mgr+852` が見つかる。
**`mgr = そのアドレス − 852`**。この並びは `sub_6032E4` と 1 個も外れずに一致する。

### 3.2 124 バイトの要求／表示スロット

欄位置は `sub_6032E4` の構築順と `sub_60308C`（`0x0060308C`）のリセットで確定:

| offset | 内容 |
|---|---|
| +0 | 種別（0=無 / 1=索引指定 / 2=ラベル番号指定 / 4=ラベル文字列指定 …） |
| +4 | 解決後の**索引**（`sub_6012CC` が `sub_159D80(mgr+812, これ)` で本文を引く） |
| +8 | **ラベル番号** |
| +12 | `sead::FixedSafeString<8>`（vtbl `0x008FED94`）= ラベル文字列 `"002"` 等 |
| +32 | `sead::FixedSafeString<32>`（vtbl `0x008FECF4`）= アーカイブ名 `"SYS_Save"` 等 |
| +76 | `script::WordFix<9>`（vtbl `0x009047CC`）= 名前の差し込み |
| +120 / +121 | バイト |

`sead::FixedSafeString` は `{vtable, char* buf, s32 capacity, char chars[N]}`。

### 3.3 ★経路の合流点（トレースはここに仕掛ける）

```
（要求側：多数）
  sub_6028A4 0x006028A4  (mgr, ラベル番号, アーカイブ, WordFix, flag)   種別 2
  sub_5F2B1C 0x005F2B1C                                               種別 1 / 4
  sub_5F30F8 0x005F30F8  ← sub_236B40 0x00236B40 ← sub_2388BC 0x002388BC
        ↓  いずれも *(mgr+864) に書くだけ
  ★ sub_6019A4 0x006019A4  Msg_CommitRequestSlot
        要求スロット → 表示スロットへ複製し、要求側をリセットする【唯一の合流点】
        ↓
  sub_6012CC 0x006012CC  ラベル→索引を解決して本文を流す
  sub_601EBC / sub_602740 …  表示の進行
```

**次にトレースを仕掛けるなら `sub_6019A4` の入口で `*(mgr+864)` の
`{+0 種別, +4 索引, +8 ラベル番号, +12 ラベル文字列 8B, +32 アーカイブ 8B, LR}` を記録する。**
これで「どの種別で・何を要求したか」が全経路ぶん取れる。

### 3.4 ヒープの読み方（実機で物体を探すとき）

- アロケータのブロックヘッダは **`{u32 magic = 0x00000032, u32 size}` の 8 バイト**。
  ヘッダの `size` が `sub_139FF4(N, …)` の `N` と一致するので、
  **「124 バイトの物体」を探すだけで要求／表示スロットが特定できる。**
- 構造署名で探すのも有効。メッセージ物体は `+8` が `FixedSafeString<32>` の vtable、
  `+52` が `<8>` の vtable。0x33000000–0x33200000 を 0x20000 ずつ読めば 30 秒に収まる。

## 5.5 ★「準備中」の間、実際に何をしているか

§5 の表は「case 0 が呼ぶもの」の一覧だが、**表示中に走っている仕事**は別の層にある。

### 確定（HIGH。逆アセンブルで確認）

`sub_2388BC(this, 2, "SYS_Save", **this+632**)` の **第 4 引数がワーカー**で、
`sub_236B40` の状態機械 case 5 がこれを毎フレーム叩く:

```asm
00236EF4  LDR R7,=dword_94D8A0
00236EF8  STR R4,[R7,#4]      ; 実行中の talk driver を大域へ
00236EFC  LDR R1,[R0]         ; R0 = this+632
00236F00  LDR R1,[R1]
00236F04  BLX R1              ; ★ワーカーを 1 歩進める
00236F08  STRB R0,[R4,#528]   ; 戻り値が非 0 になるまで毎フレーム呼ぶ
```

- case 4 が **`*(a1+530) = 90`** を仕込み、case 5 が毎フレーム減らす。
  **90 フレーム = 実測 29.8 fps で約 3.0 秒が最低表示時間**（F-357 の実測値を使用）。
- 先へ進む条件は「ワーカーが非 0 を返した」**かつ**「タイマが 0 になった」の両方。

ワーカー `this+632` は同じ case 0 の初期化ブロックで **`sub_27EB34` `0x0027EB34`** が組む:

（疑似C を省略。原本は _local/legacy-src/…）

### 有力（MEDIUM。呼び出し鎖は追えたが「どの callback が叩かれるか」は未証明）

3 つの callback の中身:

| callback | 中身 |
|---|---|
| `sub_5254C0` `0x005254C0` | `sub_536200()` → **`sub_5CE84C()`**。さらに村セーブの `+465186` の bit1 が立っていれば `sub_605B24(off_948D5C, 8)` と `(…, 4)`。**戻り値は常に 1** |

**受信ボックス `dword_94D5FC` を開いて、受け取った記録を古い順に村のセーブへ取り込む**:
