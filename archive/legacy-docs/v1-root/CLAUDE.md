## IDA への反映と根拠

確度が十分なら rename（関数・局所/大域変数）、型修正、コメントを積極的に行う。

**RTTI で実名が取れるものは推測で名付けない。** vtable の 4 バイト手前が `TypeInfo`、
その `+4` がマングル名を指す。`rtti.py` で引ける（F-43）。

逆方向も使える。**「この機能のクラスはどこか」を探すときは、まずシンボルテーブル
（`0x8CD000`-`0x8E5000`）をマングル名で grep する。** 名前が見つかれば
`find_class.py` が TypeInfo と vtable まで辿る（F-50 で `Wipe` / `BsMenuItem` を特定）。

**`code.bin.i64` には全 2,895 クラスの名前が入っている（F-53）。**
`ti_<Class>` / `vtbl_<Class>` で引ける。
**継承関係は `xrefs_to ti_<Class>` で辿れる**（xref = そのクラスを基底に持つ TypeInfo）。
推測だけで名前や型を確定しない。仮説は仮説と明記する。
重要関数ほど早期に名前を固定しすぎない。

各結論に、何から判断したかを残す:
decompile / assembly / xref / caller・callee / register 値 / memory 値 / breakpoint 観測。

- Decompiler の結果だけで判断しない。不明瞭なら assembly を確認する。
- 数値・アドレス変換を暗算しない。`int_convert` 等を使う。
- **進数を取り違えない。** 資料が `0x71` と書いていて手元の記録が「71」でも、
  それは 113 と 71 で別物（F-57 で一度取り違えた）。**16 進なら必ず `0x` を付けて書く。**
- 解析済み関数を再解析しない。新証拠があるときだけ再訪。
- ライブラリ / SDK / コンパイラ生成コードと、対象固有ロジックを分離する。

`REFERENCES/` と `NCCH/` は**一次情報ではない**。裏取りするまで `LOW`。
採用するときは出典（`CHEATS/xxx.txt` の〈名前〉、`IDS/xxx.txt` など）を明記する。

- **対象は日本語版の無印**（TitleID `0x0004000000086200`）。**amiibo+ ではない**（F-54）。

  `REFERENCES/CTRPF PROJECTS/.../Addresses.hpp` に 8 地域 465 行の対応表があり、

- **FOXXY**（`REFERENCES/CTRPF PROJECTS/FOXXY/`）— **USA 専用**（`TID 0x0004000000086300` で判定）。

  本ビルドで使うには Vapecord の表で JPN へ変換すること（F-57）。

- **CTRPF プラグイン**（`REFERENCES/CTRPF PROJECTS/`）— 実機で動作するコードなので
  **アドレスの出発点としては強い**。ただし**ラベルは作者の用途名**であって関数の正体ではない
  （F-55: `TRAMPLE` が実際は汎用のパケット送信 `Net_SendPacket` だった）。
  **呼び出し元の数を数えると見分けられる** — 専用関数なら数箇所、汎用なら散らばる。

- **チートコード**（`REFERENCES/CHEATS/`）— 名前は作者の主観的ラベルで仕様書ではない。
  **1 チートに含まれるアドレス行がすべて必要・関連しているとも限らない**
  （試行錯誤の残骸、他チートからの流用、効いていない行が混ざる）。
  「このチートに入っているからこの機能に関係する」と即断せず、個々に確認する。
  逆に、**チートの「実装」を読むときはメニュー項目の全体を読む。**
  OSD やホットキーの処理だけ見ると、同時に当てているコードパッチを見落とす
  （F-58 で一度、機能の本体を見落として「そんな実装は無い」と誤答した）。
  **`Write32(addr, 0xE3A0xxxx)` は定数の差し替え。その定数が何の ID かを追うと入口が分かる。**
  **1 行が別の行を潰していて効いていない**ことすらある（F-49: 3 行のうち 1 行が死に、
  1 行が漢字とルビを消す原因だった）。`xrefs_to` で呼び出し元を数えると判別できる。
- **ID 一覧**（`REFERENCES/IDS/ACNL_ID_Lists-master/`）— Vapecord 作者によるもの。
  **アイテム ID / 部屋 ID / パーティクル ID は信頼できる**（F-56 で本解析の推定を確定させた）。
  **ただしアニメーション ID は誤りを含む。** `g_AnimNameTable` にゲーム自身の名前が
  あるので常にそちらが正（`scoop_swing1` を「Player vanishes」と取り違えている）。
  **一次情報（ゲーム内のテーブル・文字列）が取れるものは常にそちらが上。**
  資料は一次情報が取れない領域でこそ効く。

# 解析上の原則

## 推測を確定に昇格させない

- 仮説には確認手段をセットで用意する。手段がないなら仮説のまま置く。
- 名前・変数名・分岐の見た目から意味を決めない。定義元まで辿って裏を取る。

## 「値を使う側」ではなく「値を決める側」を疑う

出てくるものがおかしいとき、**それを生成している関数の中を掘っても直らないことがある。**
関数が引数として受け取った値がそもそも間違っている場合、
**呼び出し元まで遡らないと手が出せない。**

同じ関数でも**経路によって呼び出し元が違う**ことがある。
正常な経路と異常な経路の**両方で breakpoint を張り、引数を全部並べて差分を取る。**
「1 つの引数だけ確認して正しかったから他も正しい」とはならない（F-40）。

**逆に、1 つの関数が複数の入口から共有されていることもある。**
「この関数をフックすれば目的の操作だけを捕まえられる」と決めつけない。
別の操作からも同じ関数に入ってくる（F-42: 木にぶつかる／A ボタンで揺する）。
**フックする前に、その関数が他の経路からも呼ばれないかを実測で確かめる。**

## 大量の機械的作業は MCP のバッチで殴らずスクリプトにする

生成できる作業を MCP ツールのバッチに手で書き写すと、**取りこぼす**（F-53: 5,451 件を
300 件ずつ流そうとして 1 バッチ目で 11 件落とした）。

**「ツールで殴れるか」ではなく「スクリプトにできるか」を先に考える。**
IDA なら `py_exec_file`（ida-pro-mcp）か、GUI の `File > Script file...` で
一度に流せる。idalib にはスクリプト実行がないので、その場合は GUI を使う。

## 「それらしい定数」を見つけても到達可能か確かめる

`this+8 = 20` のように**いかにもその機能の尺に見える定数**が、
派生クラスに上書きされて一度も読まれないことがある（F-51）。

- **vtable の該当スロットを派生が上書きしていないか**を全派生について確認する
- 派生の列挙は `TypeInfo` の `+8`（基底へのポインタ）を全走査すれば取れる
- その関数への参照が vtable の 1 件だけなら、実際には呼ばれていない疑いが強い

## 「初期化時にコピーされる値」と「毎回読まれる値」を区別する

グローバルなリテラルを書き換えるチートは、**その値が毎フレーム読まれる場合にしか効かない。**
初期化時にオブジェクトへコピーされる設計だと、
**起動時に作られたものには後から当てても届かない**（F-51: フェードだけ速くならなかった）。

「一部にだけ効かない」ときは、**効いた側と効かない側の生成タイミングを比べる。**

## 「動いた／動かない」ではなく役割分担で切り分ける

1 つの結果が**複数の処理の合成**であることがある。
片方だけ実装すると「一部だけ動く」状態になり、原因を取り違える（F-42）。

構成を変えるたびに**何が動いて何が動かなかったかを表にする。**
版ごとの差分を並べれば、どの処理がどの結果を担っているかが確定する。
表を作らずに次の版へ進むと、同じところを往復する。

## テーブル・列挙値

- **基準アドレスとエントリサイズは、必ずインデックス計算コードから読む。**
  ポインタの間隔、中身のパターン、「最初の有効なエントリ」からの逆算はいずれも誤る。
  `RSB`/`ADD`/`LSL` の組み合わせと基準レジスタのロード元を特定する。
- **即値がどのテーブルの ID かは、渡す先の関数で決まる。**
  同じ `MOV R1,#imm` でも `Actor_PlayAnim` ならアニメ ID (`g_AnimNameTable`)、
  `Actor_SetState` なら状態 ID (`g_ActorStateTable`) で引くテーブルが違う（F-59）。
  **即値を見つけたら「何番目の引数として、どの関数に渡るか」を先に確認する。**
- 列挙値（状態ID・アクションID・カテゴリ）の意味はテーブルを引いて確定する。
  分岐の並び順や条件の向きから割り当てを推測しない。
- テーブル先頭に無効・番兵エントリがある前提で境界を疑う。
- ある解釈が正しいなら別経路の値とも整合するはず。**独立に得た 2 つの結果を突き合わせる。**

## 命令・関数境界

- 関数先頭の後方走査は誤検出する前提で使う。
  末尾 `POP` のレジスタセットが `PUSH` と一致するか、
  直前が関数終端（`POP{..,PC}` / `BX LR` / 無条件 `B`）かを必ず検証する。
- 命令デコードのマスクで方向ビット・レジスタ上位ビットを落とさない。
  符号やレジスタ番号を取り違えると、静かに別のものを拾う。
- 走査窓は広めに取る。**「見つからない」を結論にする前に窓を広げて再確認する。**
- 逆コンパイラが破綻している箇所（不自然な `JUMPOUT`、意味不明な inline asm）は
  関数境界の誤りを疑い、その経路の結論を採用しない。

## 動的解析

- 「パッチが効かない」ときは、まず **breakpoint で実際の経路を観測する。**
  キャッシュ・タイミング・ハードウェア要因を疑うのはその後。
  多くの場合、原因は未解析の別経路。
- 一度の観測を一般化しない。入力やゲーム状態で分岐しうる。
  成功ケースと失敗ケースの両方を取って差分で判断する。
- 想定より整い過ぎた観測結果（全て同じ値、綺麗に一致など）はツール側の不具合を疑う。
- **breakpoint が使いにくい場面ではトレース用ケーブを書く。**
  ハードウェア bp は効かず、ソフトウェア bp は
  「設置→停止→観測→削除→再開→Suspend→再設置」で 1 サイクルなので、
  1 回の観測につきユーザーとの往復が要る。
  **観測したいのが「誰が呼んだか」なら bp、「何が積まれたか」なら
  メモリ直読みのほうが速い**（F-103 / F-104）。
  代わりに**引数をリングバッファへ追記するだけのケーブ**を仕込めば、
  ユーザーに複数の操作を続けてやってもらってから一度に読み出せる。
  素の挙動を変えないので、比較したい操作を並べて差分が取れる（F-42 で経路を分離）。
  ひな型: `scratchpad/trace_bump.py`（`0x59BAC4` の呼び出し元記録）。
  **呼び出し元の LR をスタックから読むときは、SP の移動量を線形走査で
  合計してはいけない。** 別経路（早期リターン側）の `ADD SP` を数えて誤る。
  到達する経路の `PUSH` と `SUB SP` だけを辿ること。
- 動的に得たアドレスは起動ごとに変わる。静的な入口からのポインタチェーンで記録する。

## コード注入・パッチ

- **最小構成で検証してから広げる。** ループや複数対象をいきなり書かない。
- 呼び出し規約の引数を根拠なく 0 で埋めない。本来の値と役割を先に調べる。
- 既存関数を直接呼ぶ場合、その関数が前提とする初期化・呼び出し文脈を確認する。
- 適用・復元は `PATCHES/apply_patches.py` に集約し、単独で revert できる形を保つ。
- **★走らせる前に、全 `LDR` のリテラル参照先と分岐先を逆アセンブラで辿って確認する。**
  F-180 で `LDR R3,=VALS` がリテラル自身を指してフォルトした。
  この手順を入れてからは 1 度もフォルトしていない。
- **★ケーブの番地は「この boot で実行済みの範囲」と機械的に突き合わせる。**
  使い回すと別ケーブの定数を上書きする。実際に一度、索引定数が潰されていた。
- **★同じ数値を 2 箇所に書いたら、片方から生成するか検査で突き合わせる**（F-287）。
  観測リングの大きさが「重なり検査 `0x80` / 実装 `0x200` / デバッガ初期化 `0x200`」と
  3 通りあり、**リングが自前 TEV を毎フレーム潰していた**のに検査をすり抜けた。
  `.bss` の配置を動かすときは**各領域の実際の使用量を実装から読む**こと。
- **★「巻き戻す」ときは、戻り先の値を記録から取る。推定で埋めない**（F-286/F-287）。
  F-286 で `NODE_TOP` 以降の内訳を新しい版の相対間隔から推定し、バグごと復元した。
- **★`.bss` の番地も同じように突き合わせる**（F-227）。
  観測用のリングが動作中のスプライト表と重なってクラッシュさせた。
  「前に使えたから安全」ではない。**同時に何が生きているかで変わる。**
- **★リテラルを持つケーブは、コード部とリテラル部の境界を明示して検証する。**
  リテラル参照がコード領域を指していたら誤り。
- **★★ケーブの逆アセンブル検証に idalib は使えない**（F-339）。
  静的 IDB（`code.bin.i64`）の segment は **`0x00838020` より手前で終わっており**、
  ケーブ置き場（`0x00838100` 以降）は `patch` が「Address not mapped」で拒否する。
  **`get_bytes` は読めてしまうので紛らわしい。** 正しい手順は 3 本立て:
    1. 生成側の `audit()`（全 LDR のリテラル参照先・全分岐先）
    2. **objdump**（`arm-none-eabi-objdump -D -b binary -m arm --adjust-vma=<ケーブの番地>`）
    3. **実機へ書いたあと、輪へ繋ぐ前に IDA（ida-pro-mcp）で実バイトを逆アセンブル**
- **I-cache は実測では問題にならなかった。** F-155a の「同一 boot で再適用しない」は予防。
  同じ番地のフック語やリテラルを何度も書き換えて毎回正しく反映された。
  未実行の番地を優先する方針は維持してよいが、空きが無いことを理由に諦めなくてよい。

# 環境固有の制約

## 2 つの IDB を使い分ける (F-48)

| 用途 | どちら |
|---|---|
| 逆アセンブル・`xrefs_to`・広域走査・関数境界 | **静的 IDB（idalib-mcp、セッション `acnl`）** |
| 実行時の値・パッチの効果・breakpoint | デバッグ IDB（ida-pro-mcp） |

静的 IDB は **`code.bin.i64`（セッション `acnl_code`）**。実機と同一ビルドで、
**我々の実行時 VA がそのまま使える**（`imagebase` は `0x0` と表示されるが実際は `0x100000` 起点）。
`idb_open(input_path="A:/Disassemble/acnl/code.bin.i64", mode="force_headless",
preferred_session_id="acnl_code", run_auto_analysis=true)` で開き、`idb_save` で保存する。

- **`run_auto_analysis=true` を必ず渡す。** false だと関数が定義されない（F-52）
- **【重要】idalib でセッションを開いている間、同じ IDB を IDA GUI で開いてはいけない。**
  idalib は `.id0` / `.id1` / `.nam` / `.til` のルースファイルを掴んだままで、
  `idb_save` はそれを消さない。GUI から開くと 2 プロセスが同じ DB を書いて壊れる。
  GUI で作業してもらう前に**必ず `idb_close` する**こと。
  それでもルースファイルは残るので、GUI 側には
  「IDA did not close properly」の確認ダイアログが出る。
  **パック済みの `.i64` が最新なら「Restore packed base」を選ぶのが安全。**
  GUI 側の作業が終わって IDA を閉じた（＝パックされた）あとに、こちらが開き直す。
- **`NCCH/exefs/code.bin` は別ビルドで使えない**（F-45）。同名なので混同しないこと
- `NCCH/exefs/code_runtime.elf.i64` は実機ダンプ由来の予備（F-46/F-48）

- **デバッグ IDB の `xrefs_to` は空を返す。** 呼び出し元を探すなら静的 IDB を使う。
- **自前の BL ブルートスキャンは Thumb を取りこぼす。** `xrefs_to` を使うこと（F-48）。
- **`xrefs_to` の結果を全部読まない。** 数百件あるものは `limit` で絞る。
- 名前の反映: ida-pro-mcp 側は `ida_restore.py`、
  idalib 側は `rename` / `type_apply_batch` / `set_comments` のバッチ。
  **`rename` の `data` はアドレスを受け付けない**（`old` は現在の名前）。
  グローバルは `type_apply_batch` に `addr` + `name` + `ty` を渡す（`ty` は必須）。
  集約データは `scratchpad/symbols.json` / `comments.json` / `protos.json`（F-52）。

## ida-pro-mcp / py_eval

- exec の globals/locals が分離しており、`def` の中や内包表記・ジェネレータ式から
  モジュール階層の変数・import が見えない。エラーにならず誤った値を返すことがある。
  → **フラットな while ループのみで書く。** `def`・内包表記・genexp を使わない。
- **★生成用スクリプトを IDA の中で `import` / `py_exec_file` しない**（F-340）。
  `export_gui_v2` など 8 本は IDA 無しで動かすために
  **`sys.modules["ida_bytes"]` などを空のモジュールに差し替える**細工を持つ。
  `export_gui_v2.py` は末尾で `main()` を呼ぶので**取り込んだだけでこれが走り**、
  以後 `ida_bytes.get_bytes` も `ida_dbg.write_dbg_memory` も**黙って消える**。
  対象は `compare_q_baseline` / `dump_q_ref` / `export_gui` / `export_gui_v2` /
  `preview_layout` / `verify_literals` / `verify_plugin_port` / `verify_plugin_port_v2`。
  **これらは `python.exe` で動かす。**
  （F-340 で 9 箇所すべてに「本物があるなら差し替えない」守りを入れたが、
   そもそも IDA の中で走らせないのが正しい。壊れたら
   `del sys.modules[k]` してから import し直せば戻る）
- **スクリプト内で `SystemExit` を投げない。** `py_exec_file` から `raise SystemExit`
  すると ida-pro-mcp のリクエストハンドラごと落ち、以後 IDA が一切応答しなくなる
  （セッション2で発生。IDA の再起動が必要になった）。
  早期終了は `main()` からの `return`、または通常の例外（`RuntimeError` 等）で行う。
- MCP プロキシは **30 秒タイムアウト**。GDB 経由のメモリ読みは約 77KB/s
  （キャッシュ後 ~150KB/s）。1 回のスキャンは **1.5MB 以下**に分割する。
  **そもそも広域走査は静的 IDB かローカルのダンプファイルでやる。**
  デバッグ IDB で 7MB を走査してタイムアウトさせた事故が 2 回ある。
- メモリ操作の前に必ず Suspend（実行中の値は不安定・キャッシュも効かない）。

### ★MCP 側からの Suspend — 使えるが条件がある（実機で 3 回検証）

**判定基準は「フリーズかどうか」ではなく
「その `py_eval` 呼び出しが始まった時点でデバッガが RUNNING か」。**

| 呼び出し開始時点 | 結果 |
|---|---|
| 停止中 (`state == -1`) | 処理される。呼び出しの中で `continue` → `suspend` まで可能 |
| **RUNNING**（正常走行でもフリーズでも同じ） | **届かない。30 秒でタイムアウト** |

したがって **`suspend_process()` 単独では走行中の対象を止められない。**
止めたいなら **`continue_process()` と `suspend_process()` を 1 回の `py_eval` に束ね、
走らせる長さを事前に決めておく**。これなら往復なしで観測できる。

**★対象が走り出したあとに止める手段は無い**（F-116 で 4 通り試して確定）。
`server_health`（デバッガに触らない疎通確認）すらタイムアウトする。
要求はキューに積まれ、**対象が停止した時点で処理される**。
30 秒以内に停止しなければ MCP プロキシのタイムアウトに当たる。

### ★★`run_timed.py` — 走らせる前に「止まる予約」を入れる（F-116）

これで**手動 Suspend 依頼は原則不要**になる。

```
py_exec_file("A:/Disassemble/acnl/run_timed.py")   # RUN_MS を編集して使う
→ register_timer(RUN_MS, cb) で予約してから continue_process()
→ cb は IDA のイベントループ上で走るので suspend できる
次の py_eval で state == -1 を確認してから読み出す
```

- **bp が先にヒットすればそこで、しなければ時間切れで必ず停止する。**
  待ちぼうけにもフリーズ時の手詰まりにもならない
- **`RUN_MS` は 30 秒より十分短くする**（次の呼び出しは対象が止まるまで待つため）
- 1 フレームに 1 回しか通らない場所に bp を張るときは `RUN_MS` を大きめに
  （1500ms で未ヒット、5000ms でヒットした実例がある）

| 呼び方 | 走行中の戻り値 | 停止中の戻り値 |
|---|---|---|
| `ida_dbg.suspend_process()` | `True` | `False` |
| `ida_dbg.request_suspend_process()` + `run_requests()` | `True` / `run_requests` は `False` | — |

**どちらでも止まる。`run_requests()` が `False` を返しても失敗ではない。**

**★決定的な注意点: 同じ `py_eval` の中では止まらない。**
停止が反映されるのは **`py_eval` のハンドラが返って
IDA のイベントループが回ったあと**。だから:

```
呼び出し1: suspend_process() を呼んで、そのまま返る
呼び出し2: get_process_state() で -1 を確認 → 読み出し
```

同じ呼び出しの中で `time.sleep` して待っても**止まらない**（実測）。
**必ずツール呼び出しを分ける。**

`suspend_process()` の戻り値は状態判定に使える
（走行中に呼べば `True`、既に停止していれば `False`）。

**★これは「走行中に外から止められる」という意味ではない**（F-110 / F-116）。
上の表のとおり、呼び出しが RUNNING 中に始まると届かない。束ねる形だけが使える。

- `py_eval` の中で `time.sleep` を長く回さない（30 秒タイムアウトに当たる）。
- **タイムアウトが起きても「フリーズ」と即断しない。** 原因は少なくとも 4 つある:
  - **対象がまだ走っているだけ**（最も多い。bp が未ヒット、または bp を置いていない）
  - **bp がヒットして正常に停止したが、こちらの呼び出しは RUNNING 中に始まっていた**
    （F-116 で実際に「パッチがフリーズさせた」と誤読した）
  - IDA 側でモーダルダイアログ（設定画面など）がメインスレッドを塞いでいる
  - 実際に対象がフリーズしている

  **タイムアウトからは何も分からない。** 手動 Suspend して `PC` を見るまで断定しない。
  `PC` が bp の位置なら正常停止、まったく別の場所なら本当のフリーズ。

## デバッガ

- `write_dbg_memory` 後の読み戻しは `ida_dbg.invalidate_dbgmem_contents()` を挟む。
  挟まないとキャッシュの古い値が返る。
- 一時 IDB（`ida*.tmp.i64`）は接続ごとに破棄される。`ida_restore.py` で復元する。
- 新規デバッグ IDB は未解析のため `xrefs_to` は空を返す。
  呼び出し元を探すには BL のエンコードを直接ブルートスキャンする。

### breakpoint の扱い（実機で検証済み）

- **`BPT_SOFT` がヒットしたら、その位置の bp を削除してから再開する。**
  **削除せずに再開するとゲームがフリーズする。** これが唯一のフリーズ条件。
- **★頻度は関係ない。** 高頻度実行箇所（毎フレーム 8 回 ≈ 秒 480 回の
  `GpuCmd_SplitAndSubmit` で実測）でも、削除してから再開すれば問題ない。
- **フリーズしても復帰できる。**
  IDA から Suspend でき、その bp を削除して再開すれば普通に動く。
  **致命的ではないので、フリーズを過度に恐れて breakpoint を避けなくてよい。**
- **★削除して即座に置き直すだけでは恐らく意味がない。**
  効くのは **「bp を削除 → ゲームを再開 → Suspend → 同じ位置に再設置」**の順。
  同じ場所を繰り返し観測したいときはこのサイクルで回す。
- **走行中は MCP がブロックしてタイムアウトする。これはフリーズではない。**
  区別できないので、判断する前に手動 Suspend で切り分けること。
  「MCP が応答しない」だけを根拠にフリーズと結論しない。
- **`Use stepping support` の ON/OFF は関係ない（F-110 で検証済み）。**
  OFF にしても**ヒットした bp の削除は必要**。
- **★「フリーズ」の正体は「bp 位置での永久停止」**（F-110）。
  削除せずに再開した後で手動 Suspend すると、`PC` は **bp 位置のまま**だった。
  暴走しているのではなく、trap に再突入し続けて一歩も進んでいない。
  （`BPT_SOFT` は元命令を trap に差し替える。そこから再開するには一旦 bp を外して
  1 命令実行してから戻す step-over-breakpoint が要るが、Luma3DS のスタブがそれをしない。）
  **だから bp を削除するだけで何事もなく復帰する。**

- **ハードウェア breakpoint (`BPT_EXEC`) は使えない。**
  `add_bpt(ea, 4, BPT_EXEC)` は成功を返し `type=8` として登録され、
  元命令も書き換わらないが、**実機では一度もヒットしない**（セッション3 で検証）。
  Luma3DS の GDB スタブが設置要求を受け付けるだけで実装していない。
  実行 breakpoint はソフトウェア (`BPT_SOFT`) 一択。

## 3DS / ARM

- ロードベースは `0x00100000`。それ未満は未マップ（読むと `0xFF`）。
- **`VA = PA + 0x10000000` は「リニア FCRAM」専用の規則**（F-124 / F-166 / F-185）。
  **VRAM（PA `0x18000000`-`0x18600000`）には効かない。** UI のテクスチャは VRAM にある。
  「読むと全部 `0xFF`」は未マップの徴候。範囲を広げて 1 バイトも非 `0xFF` が無いなら未マップと見る。
- `.code` のファイルオフセット = 仮想アドレス − `0x100000`。
- `.data` / `.rodata` は実行不可。コードケーブは `.text` 内から取る。
  ゼロ埋め領域が無い場合、パッチで到達不能になった死にコードを流用できる。
  使用前に外部からの分岐が 0 件であることを走査で確認する。
- メモリパッチはゲーム再起動で消える。恒久化は `code.ips`。
