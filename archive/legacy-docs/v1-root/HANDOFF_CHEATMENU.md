## 3. フレーム制御（F-356 / F-357）— メニューとは別の系統

**文書は `DOCS/frame_pacing.md`。** 利用者から渡された「ゲームスピード」チートの解析から派生。

- `0x0054C6E8` は **`Framework_WaitAndPresentFrame`（`0x0054C684`）内の 1 命令**。
  素は `LDR R0,[R4,#0xA0]`。チートは `MVN R0,#0xFF000000` にして**フレーム待ちを消す**。
- **`this+0x70 = 2` を実機で確定**（2 VBlank 待ち = 30fps）。
- **FPS だけ上げて進行速度を据え置くのは不可能。**
  メインループ `Framework_MainLoop` が 1 反復 = Calc 1 回 = 提示 1 回で、
  Calc へ dt が渡らない（`MethodTree_WalkAndInvoke(node)` のみ）。
  実測 `+0x70` 2->1 で周期 33.751 -> 17.770 ms（**1.899 倍速**、56.3fps 止まり）。
- ★逆（遅くする）は綺麗にできる: `+0x70` = 3 で 20fps / 4 で 15fps。**データ 1 語**。
- ★`calc+draw` の実作業は 15.28 ms（1 VBlank 予算の 91.4%）。**ある 1 場面での値**。

# ★次に触る人が踏みやすいところ

## 1. 文字ペインの座標に `/2` を残さない（F-311 / F-322。両方 実機で踏んだ）

| 軸 | いつ壊れたか | 見え方 | 直し |
|---|---|---|---|
| 縦 | ペイン高 7 と文字高 8 が食い違った | 字形の**上 1 行**が落ちた | ペイン高を**行送り 8** にした |
| 横 | 文字列の**画素幅が奇数**（`0.7` = 15px） | 字形の**列**が落ち、余分な画素が出た | 横を**左アンカー + 左寄せ**にした |

```
pane[0xFC] = 3     横 0（左）+ 縦 1（中央）
pane[0xB6] = 0x13  同上。★PaneCommon は 0x14 を入れるので BuildSlot で上書きする
cx         = x - 画面幅/2      （ペイン幅に依存しない）
```

★整列だけ左にしてもアンカー（`0x0073B5C4`）が `-幅/2` を出す。**両方**必要。

## 2. `Controller::IsKeyPressed()` を別スレッドから見ない（F-321）

CTRPF の `_keysDown` は `Controller::Update()` の周期で作られる立ち上がりフラグ。
16ms の自前スレッドから見ると**取りこぼし**と**二重入力**が出る。
**水準（`GetKeysDown(true)`）を 1 フレームに 1 回読み、立ち上がりは自分で作る。**

## 3. plugin ready の直後にチートを ON にしない（F-320）

`GuiMenu::Initialize()` の `threadCreate()` が、TLS を無検査で読む
`__createThread`（`0x070058A0`）に当たって落ちる。一呼吸おけば問題ない。
恒久対策は `RE/TODO.md`。

## 4. 取り外しの順序を変えない（F-317）

```
detach → 記録長 0 を待つ → ★フックを外す → 100ms → コマンドリスト削除 → Free → ゼロ埋め
```

フックを外す前に削除すると A1/A2 が次のフレームで作り直す。
削除を省くと **1 回の ON/OFF ごとに 132,192 B** が nngx ヒープに残る。

## 5. 同じ数値を 2 箇所に書かない

`GuiV2::kBorrowBytes` が `0x50000` なのに `OwnGui` が `BorrowHeap(0x30000)` を
直書きしていて、**検証器が前者しか見ていないので素通りしていた**（F-321 で発見）。
いまは `GuiV2::BorrowBytes()` に一本化し、群 4 が直書きを禁じている。

## 7. 空リストに登録するときは陳旧リンクを疑う（F-375。実機で踏んだ）

`build_a` の見送り条件 (b)(c) は「外れたら prev/next は 0 に戻る」が前提。
死んだリストに残った stale では永遠に見送り、対象 head=0 のまま残る。
`LayoutMgr_RenderTop` の +0x00〜+0x14 に空検査は無いので即クラッシュする。
村（詰まったリスト）では起きず、タイトル（空）初回で発覚した。
対策： head==0 なら stale を消して挿入へ直行（非空は従来通り）。
ケーブを伸ばしたら `audit_node_cave.py` が重なりを検出する。
A2/N の置き場を見直すこと（A1 は動かさない）。

## 6. 実機へ入れる前に必ず

- `verify_plugin_port_v2.py` / `verify_spec_v2.py` が **0 件**
- ケーブを触ったら `audit_node_cave.py`（全 LDR のリテラル参照先・全分岐先）

# 設計の要点（以下すべて静的解析で確定し、実機で裏付け済み）

## 1 フレームで何が起きるか

```
RenderTop        (0x566DF8) [A1 フック] RecordChildren(mgr+4)    → SetDisplaySize(400,240) → SetDisplay(mgr+4,    0x400)
RenderTopRightEye(0x5692B0)                                      → SetDisplaySize(400,240) → SetDisplay(mgr+4,    0x410) → UnlinkAll
RenderBottom     (0x568F98) [A2 フック] RecordChildren(mgr+0x10) → SetDisplaySize(320,240) → SetDisplay(mgr+0x10, 0x401) → UnlinkAll
```

- `RecordChildren`（`0x566EA0`）は各 Layout の **vtable +0x14** を呼ぶ（＝我々の記録スロット）
- `SetDisplay`（`0x566E30`）は `+0x134` に display を書いてから **vtable +0x08** を呼ぶ（＝再生）
- **ゲームが自前ノードに呼ぶのはこの 2 スロットだけ**（F-275）
- リストは毎フレーム `sead_List_UnlinkAll` で空になり、各ノードの prev/next も 0 に戻る
- `AddLayout` は `+0x0C` の昇順挿入。**`0xFF` なら必ず末尾＝最前面**

## 1 レイアウトぶんの、フレーム上の実際の並び（★F-276）

```
reg 0x06F mask2 = 0                       ← テクスチャ座標出力 OFF
reg 0x080 mask2 = 0 / maskB = 0x00001000  ← テクスチャユニット 0/1/2 全 OFF
既定 begin ブロック（頂点シェーダ・属性・0x100/0x101/0x104）
投影 uniform index 0（24 語。ノード +0x34 の 16 語から）
────── 記録した内容をそのまま memcpy ──────
既定 end ブロック
```

**`DrawBegin1(drawer, 1)` / `DrawEnd1(drawer, 1)`（記録時）は 1 語も出さない。**
既定ブロックが出るのは**再生時**（フラグ 0）である。`sub_4D72C4` の `TST R2,#1 / BNE` が決め手。

→ **記録内容の先頭で `0x06F` と `0x080` を立て直さないと、テクスチャは絶対に読まれない。**
→ 記録内容にシェーダは含まれないので、自前リストは約 2.3KB しか使わない（`LIST_SIZE = 0x4000`）。

## 実機で分かった制約（次に触る人が踏みやすいところ）

- **拡大率は元テクセル 8px の整数倍にすること**（F-281）。
  1.75 倍だと元 1 画素が出力 1px と 2px に割れ、線幅が不揃いになり
  1px のノイズが点々と走る。16px（2 倍）か 24px（3 倍）にする。**送りは自由でよい**

  **枚数を増やすなら `LIST_SIZE` も上げること**
- **座標は 1 単位 = 1px、原点は画面中央。**
  上 x=±200 / 下 x=±160 / y=±120 が画面端

## 2026-09-04 F-259 時点の記録

**`REFERENCES/TEXTS/render.txt` は本作と 1:1 で完全一致する。仕様として扱ってよい。**
`ssys::ma::lyt::Layout::RenderFrame` は `Layout_RecordPaneTree`（`0x5686D4`）そのものだった。
全対応表・Layout の全フィールド・マネージャ構造は `RE/FINDINGS.md` の F-259 にある。

### これまでの失敗の理由が一言で説明できる

**GPU 状態（テクスチャ結び付き・頂点属性の構成・TEV・投影）は
`DrawBegin1` が「記録の先頭」で確立し、`DrawEnd1` が締める。**

我々は replay の列に後から積んでいたので、
記録が走ったフレームは直前の記録内容が replay されて状態が残り描けたが、
記録が走らないフレームは状態が無く GPU が止まった（F-256 / F-257）。
作業配列を自前にしても `DrawBegin1` を通らないので直らない（F-258）。

**正しいやり方は「replay に積む」ではなく「自分で記録する」。**

### 実装すべき設計

自前ノードを**本物の Layout と同じ契約**にする。

1. **自前のコマンドリスト**: 未使用 id（例 100）で `GpuCmd_SelectList` を一度呼び、
   マネージャの `+0x04`（base）と `+0x08`（size）に `g_GfxAllocator` の
   バッファを入れる。**未知 id はヘッダを作るだけで base/size は 0 のまま**なので必須。
2. **記録スロット（自前 vtable `+0x14`）** で `Layout_RecordPaneTree` と同じ順に:
   `GetProperty(519)` → `SelectList(自前 id)` → `sub_7B01CC` → `sub_7B05B0` →
   `DrawBegin1` → 自前スプライト → `DrawEnd1` →
   `GpuCmd_CommitListAndCaptureDelta(node+0x104, +0x108, +0x10C, +0x110)` → `SelectList(save)`
3. **再生スロット（自前 vtable `+0x08`）はゲームの `Layout_ReplayRecordedList`（`0x5682DC`）を
   そのまま使う。** Commit が `+0x100`〜`+0x110` を埋めるので毎フレーム再生される。
4. 順序は `LayoutMgr_AddLayout` の優先度 `0xFF`（F-253 / F-254）。

gokiro 氏の 3 要素がそのまま揃う。
**描画コマンドを追加するフック**＝記録スロット、**順番を変えるフック**＝優先度 `0xFF`、
**コマンドバッファ拡張**＝自前 id への base/size 設定。

## ★最優先更新（2026-09-04、F-257）— 次担当はここから読む

**F-256 のゲートの解釈は誤りだった。** `DrawCtx_FlushBatch` は
**記録（record）のときにしか呼ばれない**。レイアウトは変化したときしか記録し直さない（F-226）ので、
ゲートの実際の意味は「**そのフレームでどれかのレイアウトが記録し直したときだけ描く**」だった。

実機の見え方がそれを裏付けている（利用者の観察）:
時計のコロンが点滅する瞬間だけ 1 フレーム表示／フェード中はずっと表示／フェード後は非表示。

### 残っている 2 つの不具合は同じ根

| 症状 | 借りているもの |
|---|---|
| 記録し直したフレームしか描けない | `drawctx+1640/1644/1648` の頂点・行列・索引の**作業配列** |
| 下画面だけ横幅が縮む（0.8 倍） | Drawer の変換。`Layout_ReplayRecordedList` は replay 前に `sub_4B8C34(mgr+0x364, Layout+0x30, 0)` で設定するが、我々は呼んでいない |

`LayoutMgr_SetDisplaySize` を自前で呼んでも横幅は変わらなかった（実機で確認）。
つまり倍率を決めているのはそちらの uniform ではない。

### 次の設計 — 借り物をやめる

1. **頂点・行列・索引の配列を自前で持つ。** `g_GfxAllocator` で確保し、
   描く直前に `drawctx+1640/1644/1648` を差し替え → `DrawCtx_FlushBatch` → 直後に戻す。
   これで記録の有無に関係なく毎フレーム描ける（ゲートを外せる）。
2. **変換を自前で設定する。** `sub_4B8C34(mgr+0x364, 行列, 0)` を自前の行列で呼ぶ。
   画面ごとに 400x240 / 320x240 の等倍にする。

どちらも「ゲームの関数を自前のデータで呼ぶ」形。手でコマンド列を組むより安全。

## 3. ★★現方式の限界 — ここが再開の出発点

いまは **レイアウトの記録リストへ追記**している

|---|---|---|

### ★第一候補（2026-09-03、F-253）— 自前 Layout ノードを毎フレーム登録する

詳細はこの文書の先頭（F-253）。`LayoutMgr_AddLayout(mgr, layout, screen)` で
優先度 `0xFF` の自前ノードを入れれば、その画面の末尾＝最前面になる。

### 旧・第二候補（F-252）— `LayoutList_SetDisplay` の出口へ積む

> こちらでも 3 問題は消えるが、ノード登録方式のほうがゲーム自身の API に乗れる分安全。
> なお、ここの `R5` は `0x400`/`0x410`/`0x401` の 3 値を取る（F-253）。

```
0x566E30 PUSH {R4-R6,LR}          R5 = display（0x400=上 / 0x410=下）
0x566E44 loop: STR R5,[R4,#0x134]
               LDR R0,[R4] / LDR R1,[R0,#8] / BLX R1   ← Layout_ReplayRecordedList
0x566E58       LDR R4,[R4,#8] / CMP R4,#0 / BNE loop
0x566E64 POP  {R4-R6,PC}          ★唯一の出口。ここをフックする
```

| 3 つの限界 | この位置でどうなるか |
|---|---|
| 容量が小さい（F-232） | 積む先が主リスト。F-234 実測で容量 `0x100000` / 使用 `0x12B0` |
| 候補ごとに座標系が違う（F-230） | 直前の `SetDisplaySize(400,240)` で固定。下画面は 0.8 倍（F-252 / F-208） |
| 最終提出位置を制御できない（F-234） | その画面の**全 Layout の後**。ロード画像 id 10 の後になる |

上下の区別は `R5`（callee-saved、入口以降不変）をそのまま読めばよい。
`mgr+4` のリストは下画面パスの最後に `sead_List_UnlinkAll` で空にされるため、
Layout ノードはフレームごとの一時登録である。固定 id / 固定 heap ポインタを使わない設計にできる。

**未確定・先に確かめること**

- 巻き戻すときは戻り先の値を**記録から取る**。推定で埋めない（F-286）

## 2. このセッションで確定したこと

### F-287 … 明滅・「文字が板」の真因

**観測リング（16 件 x 32 バイト = `0x200`）が `MATCMD`（自前 TEV 36 語）を毎フレーム潰していた。**
F-283 で `.bss` を詰めたとき `RING` と `MATCMD` を `0x100` 間隔にしたのが原因。
正しくは **`RING 0x9B5800`（0x200） / `MATCMD 0x9B5A00`（0x400）**。
`_check_layout()` が RING を `0x80` と登録していたため重なりを検出できなかった（いまは `0x200`）。

**壊れたときの判定手順**: `LOG+0xD0`(`LOG_CURIN`) が最後の記録の開始カーソル。
そこから `ノード+0x108`（記録長）ぶんを読み、**先頭が `00300030 804F00C0` で始まっていなければ TEV が潰れている。**

### F-288 … 画面を AI が直接見られる

`PATCHES/grab_screen.ps1`（`powershell.exe`(5.1) で実行。**UTF-8 BOM 付き必須**）。
クライアント領域 `400x480` ＝ 上 `400x240` ＋ 下 `320x240`（中央寄せ）。
`-Screen top/bottom` / `-Shots n` で連写して**画素差 %** も出る。
細部は `PATCHES/zoom_png.ps1` で拡大。

**★撮り方**: `continue_process(); time.sleep(3.0); suspend_process()` で **3 秒走らせてから** Suspend し、
**別の呼び出し**で撮る。短いと転送が追いつかず、タイトル画面はロードの瞬間を撮ると真っ暗に見える。

### F-289 … ゲーム自身の描画関数を自前オブジェクトで使える

`0x73CB58 nwlyt_Picture_DrawToCommandList(picture, cursor, a3, drawctx)` は
「UI を 1 枚描く」本体。**自前 Picture を渡して描けることを実機で確認した。**

| 項目 | 結果 |
|---|---|
| 自前 Picture を渡して描く | **できる** |
| 位置・大きさ | できる（`+0x48` 幅 / `+0x4C` 高さ / `+0x80` の 3x4 行列） |
| 自前テクスチャ | できる（記述子の欄は下表） |
| UV | **その場で計算し直せる**（`*(pic+212)=0` / `*(mat+77)&=~4`） |
| 色 | できる（`*(mat+16)`。書式 `0xAABBGGRR`） |
| 外部オブジェクトへの依存 | **無い**（外部参照 5 語を 0 にしても動く） |
| **ロードを跨いだ生存** | **生きる**（A ボタンでロードを跨いで実測） |
| 文字だけ色を付ける | **未検証**（借り物 TEV はアルファ 0 の画素まで不透明にする） |

**Picture の構造**（実体は約 `0x320` バイト。マテリアルは `+0x1A0` に**埋め込み**）

```
+0x048 幅       +0x04C 高さ
+0x080 行列 3 行 x 4 列（[0][3] = X 平行移動、[1][3] = Y）
+0x0B5 色の数   +0x0D4 UV 計算済み   +0x0D8 UV セット数   +0x0DC UV(4 float)
+0x13C マテリアル（= pic+0x1A0）      +0x140 頂点カラー x4    +0x154 = pic+0x16C
```

**マテリアル**

```
*(mat+16) -> reg 0x0DB（モード1）      *(mat+20) -> reg 0x0F3（モード1）/ 0x0DB（モード0）
*(mat+44) フラグ                       *(mat+48) ★2 ビット欄の詰め合わせ
    bits 0-1 = テクスチャのユニット数 ＝ 色のモード
    bits 4-5 = UV の組数
*(mat+52) テクスチャ記述子の先頭（1 ユニット 32 バイト）
*(mat+77) bit2 = UV 計算済みの印
```

**★テクスチャ記述子の全欄（確定）**

| オフセット | 読む関数 | 意味 |
|---|---|---|
| `+0x04` | `TextBox_UpdateDrawState` | reg 0x085（**物理番地**。`>>3` されて積まれる） |
| `+0x08` | `sub_73B650` | 実寸。**UV 倍率の分子** |
| `+0x0C` | `sub_73B650` | テクスチャの大きさ。**UV 倍率の分母** |
| `+0x14` | `TextBox_UpdateDrawState` | reg 0x083（ラップ／フィルタ） |
| `+0x18` | `TextBox_UpdateDrawState` | reg 0x082（大きさ 高<<16 \| 幅） |
| `+0x1C` | `TextBox_UpdateDrawState` | reg 0x08E（書式。LA4 = 9） |

裏取りは 2 系統: `TextBox_UpdateDrawState` の逆コンパイルと、
実機の状態キャッシュ `unk_97B74C` のヘッダ（ユニット0 = `0x082`/`0x085`/`0x08E`/`0x083`）。

### F-289 段 5 … 「ロードで消えた」の正体

**寿命の問題ではなかった。** ロード後もクローンは健在で、関数も呼ばれ、BL も完走していた。
見えなかったのは**乗り込む位置**が原因。
実験は「フレーム最初の `Picture_DrawToCommandList` の直前」に割り込むので、
ファイル選択画面ではそれが**下画面の全画面背景**（352x272・45 度回転・16x16 テクスチャ）で、
自前の 1 枚が丸ごと上塗りされていた。
タイトル画面で見えたのは、そこでの最初の Picture がたまたま上画面のロゴだったから。

## 3. 次にやること（設計）

**`nwlyt_Picture_DrawToCommandList` の呼び出しを CAVE_Q（自前ノードの記録スロット）へ移す。**

- 自前ノードは優先度 `0xFF` で**必ず最後に再生される**ので、順序を自分で握れる
- CAVE_Q は drawctx とカーソルを既に持っている（`LOG+0x04` と R5）
- 置き換えられるのは、いま手書きしている
  **テクスチャ 7 組 14 語 ＋ 自前 TEV 36 語 ＋ スプライトループ ＋ 色 ＋ カウンタ**
- **チャンク 7 枚・色はチャンク単位という制約（F-280）も外れる**
  （この関数は溢れ判定 `+36` が 0x1A 超 / `+37`,`+38` が 0x20 超 まで面倒を見る）
- Picture は 1 枚ごとに持つと重い（約 `0x320` バイト）ので、
  **1 個を使い回して行列・幅・高さ・UV・色だけ差し替える**

**先に潰しておくこと**: 借り物 TEV の合成（アルファ 0 の画素まで不透明になる）。
直せないなら自前 TEV を併用する設計にする。
