# 実機での解析の安全手順

実機の操作は、依頼文か利用者が許可した範囲で行う。実行中の状態を推測して書き換えず、停止確認、変更前の保存、復元の準備を済ませてから試験する。短い実行と観測を繰り返し、試験後に何を戻したかまで証拠に残す。

作業時の要点は [dynamic-analysis スキル](../skills/dynamic-analysis/SKILL.md) にある。この文書では各手順の理由と確認方法を説明する。

## 試験前に停止を確認する

1. 対象タイトルとビルド、接続先のプロセス、今回の起動を確認する。再起動前のアドレスや保存値を、そのまま現在のプロセスへ使わない。
2. IDA のデバッガで停止状態を読む。既に Suspend なら、利用者に停止を頼み直さない。実行中なら、許可された停止手段で止め、別の呼び出しで状態を読み直す。
3. PC・SP・LR・CPSR、選択中のスレッド、ブレークポイントの一覧と種類を保存する。例外停止か、ブレークポイントか、手動停止かも区別する。
4. PC が変更する命令列や一時コード内にないか、復帰先が変更対象に入らないかを確認する。確認できなければ書き換えない。

メモリの読み書きは停止確認後に行う。実行中は値が変わり、複数回の読み取りが同じ時点の状態を表すとは限らない。ソフトウェアブレークポイントは命令を書き換えるため、元の命令の保存や復元との干渉も確認する。旧資料の対象環境では再開前にソフトウェアブレークポイントを除去していた。除去したものも記録し、予期しない停止や書き戻しを避ける。

## 元の値を保存し、戻し方を決める

変更する前に、次の情報を `_local/evidence/<Issue番号>/` に保存する。

- 変更前の上下画面と取得時刻。
- 変更する各範囲のアドレス、長さ、実機から読んだ元のバイト列、予定する変更値。
- 必要なレジスタ、スタック、カウンタ、ポインタ、周辺メモリ。レジスタを操作する試験では、その復元に必要な値も含める。
- 一時コードへの入口と復帰先、既存の変更やブレークポイント、試験の停止条件と復元順序。

ファイルには試験名や前後の区別を付け、前の証拠を上書きしない。記録から参照するときは、作業場からの相対パスと SHA256 を書く。逆アセンブルや過去のダンプの値だけでなく、今回の停止時に読み出した値を保存する。既存の変更を誤って消さないためである。

試験前に「どの値をどの順序で戻すか」「復元できないときはどう終了するか」を作業メモに書く。実行によりゲームの状態が変わった場合、変更前のバイト列を戻すだけで全状態が巻き戻るとは限らない。

## 時間を区切って再開する

1. 実行時間を決める。既定は **3000ms**、上限は **25000ms** とし、まず必要な短い区間を観測する。
2. IDA 側の停止タイマーを、Resume より先に登録する。タイマー登録に失敗したら再開しない。再開に失敗したら予約を解除する。
3. タイマーの処理では、既にブレークポイントなどで止まっていれば再開せず終了し、実行中なら停止を要求する。
4. Resume 後は予約した時間の経過を待つ。IDA の一つの要求内で sleep しない。実行中は IDA への要求を処理できない場合があるため、繰り返し要求を送って停止させようとしない。
5. 自動停止後、**別の呼び出しで停止状態を確認してから**メモリを読み書きする。タイマーを登録できたことや、指定時間が過ぎたことだけを停止の証拠にしない。

旧資料の `tools/dynamic/run_timed.py` はこの順序のための道具だったが、この作業ツリーには収録されていない。旧環境の絶対パスをそのまま実行せず、使用する道具が登録順、停止済みの場合の処理、失敗時の解除を満たすことを確認する。上限を超える実行はこの手順の対象にせず、必要性と停止手段を見直す。

## 画面と値を記録する

画面表示が結論に関わる場合は、IDA の値と Chokistream の画像を両方保存する。デスクトップの切り抜きは、手前の別ウィンドウを実機画面として保存するおそれがある。

1. Chokistream の `Output Format = Image Sequence` を使い、保存先を今回の証拠用ディレクトリ、prefix を試験名にする。上下を分ける場合は `Layout = Separate` にする。
2. 旧資料で確認されたファイル名は、上画面が `<prefix><連番>_top.png`、下画面が `<prefix><連番>_bototm.png`。下画面の綴りは `bototm` なので、`bottom` だけを検索しない。使用中の版でも実際の出力名を確認する。
3. 再開前後で別名の画像を保存し、取得時刻、更新時刻、上下の区別、寸法、SHA256 を記録する。PNG を画像表示ツールで開き、実際の内容を確認する。
4. 試験操作と画像の変化を対応させ、同じ区間のレジスタ・メモリ・カウンタ・ログと照合する。可能なら成功例と失敗例を同じ方法で採る。
5. 必要区間の取得が終わったら Image Sequence を止める。連続取得はフレームごとにファイルを増やす。

停止直後にも転送中だった古いフレームが届くことがある。保存時刻が新しいだけでは、停止後の状態を写した証拠にならない。また、上下を合成した画像は、保持していた片側の画像と最新の片側の画像を組み合わせる場合があり、同時刻とは限らない。

同じ SHA256 が続いても、ゲーム停止、低い更新頻度、単なる静止画を区別できない。黒い画面だけでクラッシュとせず、PC、例外状態、カウンタやログを照合する。

Image Sequence を使えずウィンドウから取得する場合は、対象ウィンドウ自身の描画を取得する経路を使い、対象名、前面のウィンドウ、切り出し範囲と取得方法も残す。取得失敗、均一な画像、不確かな切り出しは証拠に採用しない。未検証の取得経路は、同時刻の Image Sequence と目視で照合してから使う。

## 試験を終えて復元する

1. 停止状態を改めて確認し、試験後の画像・レジスタ・対象メモリを保存する。
2. 現在の PC、スタック内の復帰先などから、一時コードがまだ実行に必要か確認する。実行中の命令や復帰予定の領域を先に消さない。
3. 事前に決めた順序で入口の変更を戻し、一時コードへ再び入らないようにする。書き戻した各範囲を実機から読み直し、保存した元のバイト列と照合する。
4. 一時コードや作業領域は、実行・参照されないことを確認してから元の内容へ戻す。元がゼロだったことを確認せず、単にゼロで埋めない。
5. 試験用ブレークポイントや未処理のタイマーも整理し、残っている変更と最終停止状態を記録する。

読み戻しが一致しない、復帰先を確認できない、ゲーム内部の状態破壊が疑われる場合は、復元済みと扱わない。証拠を残し、原因の確認またはタイトルの再起動に進む。復元後の動作確認も、許可された範囲で停止タイマー付きの短い再開として行う。

## タイムアウト・例外・フリーズからの復旧

### IDA への要求がタイムアウトしたとき

1. 再送や推測より先に IDA のダイアログを確認する。例外通知のモーダルダイアログが IDA の処理を塞いでいる場合があり、自動停止も必ず働くとは限らない。
2. ボタンを押す前に、題名、文面、ボタン名、画像を保存する。例外なら番地・例外の種類・スレッド ID を記録する。
3. 内容を確認して通知を閉じ、再びダイアログを確認する。複数ある場合も、未確認のまままとめて閉じない。
4. 通知がなくなったら、別の要求で停止状態と PC・LR・SP・全レジスタを読む。タイムアウトした書き込みや実行要求は、未実行と決め付けて二重送信しない。
5. ダイアログがない場合に、対象がまだ実行中なのか、接続や IDA に問題があるのかを切り分ける。画面だけで判断しない。

### SIGSEGV とフリーズを区別する

| 呼び方 | 確認する状態 | 次に保存・調査するもの |
| --- | --- | --- |
| SIGSEGV | CPU の例外で停止し、IDA に「got SIGSEGV signal」の通知が出る | 通知、例外時レジスタ、スタック、例外命令と参照先 |
| フリーズ | 例外はなく、画面の更新が止まっている | 停止後の全スレッドの PC・LR・SP、同期の待ち先と相手のスレッド |

利用者の報告の言葉を混ぜずに記録し、調査で確かめた状態を添える。例外命令の確認は対象ビルドの全関数の書き出しを使い、バイトの確認は `tools/codebytes.py` を使う。

### 例外で停止した対象を再開する前に

例外で止まった対象をそのまま Resume しない。同じ命令で再び例外になるおそれがある。まず例外時の状態を保存し、一時変更を復元できるか、ゲーム本体への副作用がないかを調べる。

旧資料のレジスタ・SP・PC の書き戻しによる復旧は、既知の一時コードと例外フレームに限定された事例である。同じ方法を使えるのは、対象ビルド、例外位置、保存レジスタの並び、スタックの復帰先、元の命令、書き込みの副作用の有無を今回の停止状態で照合でき、個別の復旧手順が成立する場合だけとする。

一時コードへの入口を先に戻して読み戻し確認し、復帰後に削除済みのコードへ戻らないことを確かめる。保存レジスタなどは今回のスタックから読み、過去の値を定数として流用しない。スタックのオフセットも、保存するレジスタや呼び出しの深さが変われば使い回せない。

原因不明、例外位置やスタックが不一致、ゲーム本体まで書き込みが進んだ疑い、復元値の不一致がある場合は、この種の復旧を行わずタイトルを再起動する。再起動後はプロセス、ビルド、停止状態、元の値の確認からやり直す。以前の起動のポインタやスタック値は再利用しない。
