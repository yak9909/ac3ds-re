## 結論

再解析で確認。TexMap の幅・高さ・フィルタ・書式から `+0x14/+0x18/+0x1C` を再生成し、状態送出はそれらを読む。Picture の UV は別の計算結果で、`Picture+0xD4==0` または `Material+0x4D bit2==0` なら再計算する。CPU上の派生値更新、UV計算、GPU状態キャッシュとの差分送出は三つの別処理である。

確度 MEDIUM：派生値の生産命令・switch表データ、独立した送出側、UV再計算の分岐と入力消費、アニメ更新側が整合する。実機なし。

| TexMap欄 | 意味・使用 |
|---|---|
| +0x04 | GPUテクスチャアドレス入力。状態送出では右3bitシフト |
| +0x08/+0x0A | UV計算用の使用幅/高さ |
| +0x0C/+0x0E | テクスチャ全体幅/高さ |
| +0x10 bits0–1 / 2–3 / 4–6 / 7 / 8–11 | wrapS / wrapT / minFilter / magFilter / nw::lyt書式 |
| +0x14 | フィルタ・wrap等から組むGPUパラメータ |
| +0x18 | ROR32(*(u32*)(tex+0x0C),16) = 幅を上位16bit、高さを下位16bitに置く値 |
| +0x1C | nw::lyt書式から写像したGPU書式（有効な0..0xDの場合） |

GPU書式の写像は `0→7,1→8,2→9,3→5,4→6,5→3,6→1,7→2,8→4,9→0,A→12,B→13,C→10,D→11`。範囲外0xE/0xFの経路は+0x1Cを更新しない。`+0x14` の生成時にはその既存値も使う。

## 根拠

一次証拠：`_local/evidence/28/ida-primary.txt`、`ida-final.txt`、`ida-followup.txt`、`ida-data.txt`、`ida-rtti.txt`。計算は `calculation.json`、主要関数のoriginal byte照合は `ida-verification.json`。

- `0x4B9834..0x4B9848` は+0x10 bits8–11を抽出し14要素switchへ。実ジャンプ表 `0x4B9850..0x4B9884` と各MOV即値、`0x4B98F4` の+0x1C保存を照合。defaultは保存を飛ばす。
- `0x4B98F8..0x4B9904` は+0x0CをROR#16して+0x18へ保存。`0x4B9920..0x4B99A0` は+0x10の各フィールドを抽出し、`0x89CDCC` のfilter/wrap写像と+0x1Cを用いて+0x14を保存。+0x04はこの再生成関数では使わない。
- `0x4B7E44..0x4B7E94` は `mat+0x34+32*unit` を読み、+0x18/+0x04>>3/+0x1C/+0x14を global のテクスチャ状態へ並べる。ユニット0の対応ヘッダは `0x97B750=0x000F0082` / `0x97B758=0x000F0085` / `0x97B760=0x000F008E` / `0x97B768=0x000F0083`。unit1/2にも各32バイト。
- この送出側の差分比較 `0x4B7E54..70` はアドレスの符号化値と+0x14だけ。幅高・書式だけを変えても、その時点で必ず再送されるという契約ではない。`0x4B7F18..30` は差分フラグが立つ場合に32*unit数バイトをコマンド列へコピーする。
- `0x73CB88..0x73CBA4` は二つのUV有効条件、`0x73CBAC..0x73CBD4` は座標配列+0x154を渡し、結果数を+0xD8、計算済み結果を+0xDCに置いて両フラグを立てる。両方有効なら再計算を飛ばす。
- `0x73B668..80` は mat+0x30 bits4–5の使用TexCoordGen数（上限3）を取る。`0x73B6EC` はGen配列、`0x73B6F8` はGenの第2バイトを座標セット索引として読む。`0x73B708..3C` は使用幅/全体幅、使用高さ/全体高さのfloat比を計算。`0x73B740` はSRTを取り、`0x73B78C` 等は32バイト単位の入力座標、出力は16バイト単位で保持する。単なるアドレス差し替えではUVを再生成しない。
- `0x73B954..0x73BAB8` は計算した四隅の成分を比較し、短い表現で表せるならGen数（0..3）、比較が一致しなければ `0x73BA7C MOV R0,#6` を返す。従って+0xD8は単なる材質のUVセット数ではなく、描画側が16倍してコピーする出力エントリ数である。Picture+0xDCから+0x13C手前までの結果領域は6×16バイト。
- `0x4B55AC..0x4B55B8` はSRTアニメ結果を書いた後Material bit2を落とす。テクスチャアニメ側 `0x4B56B0` は再生成関数を呼び、`0x4B56BC` はbit2を落とす。`0x4BA910..18` の座標/テクスチャ追加側にもbit2無効化がある。

## 訂正

+0xD8を材質のUVセット数そのものと同一視しない。書式や寸法を直したこと、UV再計算したこと、GPUへ新状態を送ったことを同一視しない。共有Materialのbit2だけを落としても全PictureのUV無効化にはならない [ACNL-F0708]。

## 反証条件・未確認点

- 旧アトラスのLA4表示、UV値、ノイズ・不発・ロード時の特定原因は実機未確認。数字9との写像は確認したが各書式の実画面を採取していない。
- キャッシュ差分検査はこの関数の経路。別の初期化/リセット/強制送出経路を網羅しない。全フィールドの直書きが単独で再送される保証はない。
