## 結論

再解析で確認。Layout オブジェクトの寿命、`+0x100` の記録 ID、manager と記録領域の寿命は区別する。基底 ctor は ID を0にし、Build が ID と記録領域を作る。破棄は非ゼロ ID を削除し、削除関数は次のID候補を戻すため ID は再利用可能である。ポインタにも世代情報はなく、過去のID・アドレスを現在の表示物の識別子とする根拠はない。

「ID 欄0の Layout」は ctor の初期状態として存在する。一方、旧F0256の「有効な記録ID0を持つ表示中の Layout が衝突した」という実機上の因果は確認できない。0は各APIで扱いが異なる。

確度 MEDIUM：ctor、Build、二つの破棄経路、独立したID生成・削除・選択の命令が一致。実機なし。

## 根拠

一次証拠：`_local/evidence/24/ida-followup.txt`、`ida-lifetime.txt`、`ida-storage.txt`、`ida-calls.txt`、`ida-final.txt`。

- `0x12D30C/314/32C` は `Layout+0x100`（ID）、`+0x108`（保存長）、`+0x11D`（記録要求）を0にする。
- `0x5685B4..0x5685C4` は既存 root `+0x20` があれば成功を返し、ID・記録領域を作り直さない。通常の構築経路 `0x568620` は `0x121B34(1,Layout+0x100)`、`0x568628` はその ID の選択、`0x568638` は `0x121988(capacity,1)`。capacity は第4引数で `+0x118` にも保存する。
- vtable実データ `0x900608/60C` は in-place破棄 `0x5688A0` と削除破棄 `0x568854` を指す。前者 `0x5688A4..C4`、後者 `0x56885C..78` は非ゼロIDなら `0x127D98(1,Layout+0x100)` を呼ぶ。後者は内部 nw::lyt の破棄後 `0x568898` からオブジェクト解放 `0x2FFA58` へ進む。
- `0x127D98` は非ゼロIDだけ処理し、該当 manager を bucket の鎖から外す。選択中なら `0x127E28..38` で global manager/cursor/end を0にし、buffer解放 callback（kind `0x105`）と manager header解放 callback（kind `0x100`）を呼ぶ。callback登録・確保成功を前提とする通常経路であり、OOM時の安全性は保証しない。
- `0x127E64..6C` は削除IDが次候補 `0x96EAAC` より小さければ候補を削除IDに戻す。`0x121B90..0x121C5C` はそこから bucket の既存IDを避け、空いた候補を採用し、次候補を1増やす。IDに世代番号は付かない。
- `0x96EAAC` のIDB初期データは0。生成関数は0を飛ばす特別分岐を持たず、候補が空けば0も生成可能。ただし起動時の全生成順を追跡して特定 Layout のID0割当を示したものではない。
- `GpuCmd_SelectList` は既存ID0の検索を先に行うが、見つからない0には `0x121700/704` で新 header を作らない。削除関数と基底 Layout の破棄は0を無視する。従って「0はすべてのAPIで一律に有効」または「一律に無効」とは言えない。
- [ACNL-F0693] のパス末尾の UnlinkAll はリンクを外すだけであり、上記の記録領域・オブジェクト破棄とは異なる。空のheadなら記録・再生巡回を呼ばない経路はあるが、その場面の画面表示を静的に断定しない。
