## IDA-opus-5-F012: アニメのフレームは実機で進んだ（適用段は IDA-opus-5-F013 で解決）（2026-09-21、HIGH、実機）

解析ソフト: IDA / 解析モデル: opus-5。**自前資源のマテリアルアニメのフレームを実機で進めた。**
**ただし画面のマテリアルは変わっていない**（後述）。駆動の仕組みと計器は確定した。
計器: runs 45 / advances 45 / submits 90（2体）、**アニメの現在フレーム 45.0・前フレーム 44.0**、
長さ 150.0。蓄積器を 147.0 に置いて走らせると **193.0 に対しフレーム 43.0 = 193 − 150** で、
**ループの折り返しはゲーム側が行う**ことも確認。

### 駆動方法の選定（3gx で同モデル十数体を描く前提）

**採用: ゲーム自身の毎フレーム契約をそのままケーブで回す。** 1体につき
`sub_4EDC98(anim, s0=要求フレーム)` → `0x4ED630(holder, 0)`。

- **却下A「call guard に VFP 引数を足す」**: 不要。ケーブの中なら `vldr s0` で自分で置ける。
  監査済み 72 B の guard を触らずに済む。
- **却下B「AnimFrameController の欄を直接書く」**: ゲームのロジックを再実装することになり、
  折り返し・速度・評価関数の選択を自前で正しく保ち続ける負債が残る。利点が無い。
- **12体への拡張**: ケーブを**表駆動**にした。1エントリ16 B（holder / 期待 vtable / anim / 予約）、
  最大16体。ループ添字は**レジスタではなく制御ブロック**に置き、表は毎回メモリから読み直すので、
  ゲーム側の関数が何を壊しても影響を受けない。`count` はケーブ内で `[0,16]` に**クランプ**するので、
  制御ブロックが壊れても描画スレッドで暴走しない。

### s0 は差分ではなく「要求フレーム」（実機で訂正）

`sub_4EDC98` は `0x004EDCA0` の `vmov.f32 s16, s0` で**呼び出し元の s0 を保持**し、
`0x004EDCC0` で step 関数へ `s2` として渡す（`s0 = [inner+68]`、`s1 = [inner+72] = 長さ`）。
step 関数 `sub_4D3E70 0x004D3E70` は**引数を全て VFP で取り R0 を一切見ない**
（decompiler の `(*(v1+76))(*(v1+80))` は誤解を招く表記）。

**毎フレーム 1.0 を渡すとフレーム1に留まる**（実測）。呼び出し側が時刻を持つ設計なので、
ケーブは制御ブロックに float の時刻を持ち、**エントリ走査の前に1回だけ** step を足す。

### 制御ブロック（40 B）とエントリ（16 B×16）

| off | 内容 |
|---|---|
| `+0x00` enable / `+0x04` runs / `+0x08` count / `+0x0C` entries | |
| `+0x10` submits / `+0x14` advances / `+0x18` index（ケーブ用） | |
| `+0x1C` time（float。ケーブが毎フレーム step を加算し s0 で渡す） | |
| `+0x20` step（float。1.0 = 1フレーム） | |
| entry: `+0` holder（0で飛ばす） / `+4` 期待 node vtable / `+8` anim（0なら描くだけ） / `+12` 予約 | |

ケーブは 404 B @ `0x838600`（`0x83877C` まで）。実機に書いたバイトを逆アセンブルし、
監査済み 95 命令と**完全一致**を確認してから輪へ繋いだ。Unicorn 12ケース PASS
（disabled / 所有者2種 / anim有無 / **12体** / holder null / node null / vtable不一致 /
count 0・999→16・−5→0 のクランプ）。全ケースで core/VFP/PSR 保存と、
設定した float が**全ての advance 呼び出しへ届く**ことを検査。

生成・監査 `tools/models3d/build_anim_hook.py`。
根拠: `events.jsonl` の `anim_hook_installed` / `anim_enable` / `anim_enable2`、
`sub_4EDC98` / `sub_4D3E70` / `0x4F18FC` の逆アセンブル、実機の計器とアニメ欄の読み出し。

### 見た目は変わらなかった（2026-09-21、実測）

`step = 0` にして要求フレームを 0 / 50 / 100 に固定し3枚撮った（`anim_f000/f050/f100_top.png`）。
そのフレームが evaluator の `+56` に入っていることは毎回確認している。**画素は動かない**:

| 領域 | f000→f050 | f000→f100 |
|---|---|---|
| カーソルの縞（右） | 0.05% | 0.36% |
| カーソルの縞（左） | 0.00% | 1.00% |
| 本（アニメ無し・対照） | 0.00% | **2.89%** |
| 空の芝生（対照） | 2.33% | **2.76%** |

**カーソルの変化は静止物や空き地より小さい**ので、差は環境ノイズであって
マテリアルはフレームに追従していない。数値 `anim_frame_diff.json`。

**したがって「フレームは進むが、適用されていない」。** 欠けているのは
評価結果をマテリアルへ書き込む段で、**IDA-opus-5-F013 で `sub_48A844` と特定し、実機で解決した**。

分かっている範囲:

- `nw::gfx::AnimBinding` の vtable（`0x008FB648`）は**2スロット（破棄のみ）**で、適用は持たない。
- `g3d::MaterialAnim` の vtable 残りスロットは破棄・再接続系（slot4 `0x4F1970`、slot5 `0x4EBDF8`、
  slot7 `0x4EBBCC`）で、適用ではない。
- `sub_4A9440 0x004A9440` は `+0x148` を読むが**生成側**（104 B を確保し `a1[92]`＝`+0x170` へ入れる）。
- **次の手掛かり**: `0x004CF460`〜`0x004D1054` の一群が `node+0x228` を読み書きしている
  （`+0x148` 側にも対応物があるはず）。ここがアニメの評価・適用系と見られる。

**未着手**: 骨アニメ（`g3d::SkeletalAnim 0x008FCC9C` ＋ `ModelInstance_BindSkeletalAnim`）、
12体の実機同時描画（ケーブと監査は対応済み）、解放。
