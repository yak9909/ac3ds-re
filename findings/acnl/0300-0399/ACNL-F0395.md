## F-368（2026-09-08）: クラッシュ点の特定（実機デバッグ。ida-pro-mcp 直読み）

F-367 の静的監査に続き、ライブセッションへ接続して PC・レジスタ・
メモリを読んだ。confidence: HIGH（実機値）。

### 停止状態

state=-1（停止中）、bp 0 件。PC=`0x0054C438`（フック+0x14）、
SP=`0x0FFFFE98`、LR=`0x00136488`。

### クラッシュ命令と根拠

PC は `LDR R0,[R4,#0x148]` で R4=`0x18`。
`[0x160]` は未マップのためデータアボートで確定。
R0=1 / R1=0 / R2=0xFFFFFFFF / R3=1 / R5=heap / R6=データ / R7=スタック付近。
部屋バイト `0x0095133A` = `0x63`（しずえ画面だった）。

R4@+0x14 == 入口R0 の証明： +0x04 `MOV R4,R0` 以降 +0x14 までに
R4 を書くのは +0x10 の `BL 0x0050A518` だけだが、実体は
SUB/CMP/BGT/ADD/CMP の 5 語（ライブ・ダンプ一致）で R4 に触らない。
自前コールバックは +0x04 より前に走り、ラッパが復元する（F-367）。
よって入口 R0 が `0x18` だった。呼び出し元がゴミを渡した。

### 突き合わせ（ライブ vs code_runtime.bin。全語一致を確認）

- `0x0054C424` だけが違う： 素 `PUSH` → フックの `B 0x01E80030`。
  飛び先は `LDR PC,[PC,#-4]` → `0x062B2BBC`（プラグイン内）。
  フックは正しく入っている。
- `+0x04〜+0x1C`・callee 5 語・LR-4 の `BL 0x00130728` は全部一致。
  callee 改変・呼び出し側改変の線は消えた。
- ★例外： `0x0054C420` だけダンプ `MOV R0,R0` に対し実機 `AND R0,R10,R0`。
  NOP 等価でもなく、出所は不明（当セッションは他エージェントと共有中で、
  別セッションの `py_eval` 結果（`00BE6Bxx` 列）が混ざった実績あり）。
  本クラッシュ（R4=0x18）との因果は未確定。要確認。
