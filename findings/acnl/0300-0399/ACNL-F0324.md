## F-300 (HIGH・静的＋実機) — ゲーム内フォントを流用しても **TextBox は自前で要る**。ただしフォント側の合成は丸ごと不要になる

### 問い

「ゲーム内フォントを流用する形でも、同様に TextBox を独自で用意する必要があるか？」

### 答え — 要る。Font と TextBox は独立している

`TextBox` は**我々のペイン木に置くペインそのもの**で、位置・寸法・文字列・色・整列・
Material・バッチを持つ。`Font` はそこから参照されるだけの外部資源。
**フォントを借りても、描く場所と文字列を決めるオブジェクトは自前で要る。**

★`TextBox+0xE0`（Font）は**デストラクタ（`0x4BB504`）が解放しない**
（解放するのは `+0x100` Material / `+0xD4` 文字列 / `+0x104` バッチの 3 つだけ）。
したがって **ゲームのフォントを指しても二重解放にならない。** 借用は安全。

### 流用で「要らなくなる」もの

| | |
|---|---|
| `ResFont` オブジェクト / FINF / TGLP / CWDH / CMAP の合成 | **不要** |
| シート記述子 20 バイト（`ResFont+0x0C`） | **不要**（フォントに付いてくる） |
| **自前アトラスと、そのための GPU 可視リニア領域** | **不要** ← ★ここが一番効く |
| `make_font_atlas.py` の作り直し（1 画素余白への対応） | **不要** |
| 日本語 | **そのまま出る** |

`g_GfxAllocator` の `0x4000` 上限（F-221）に縛られなくなるのが実利。

### 流用でも「変わらない」もの

| | 1 個あたり |
|---|---|
| TextBox 本体 | `0x108` = 264 バイト |
| **バッチ（`+0x104`）** | **1 文字あたり約 356〜377 バイト** ← 容量の支配項 |
| Material（`+0x100`） | 80 バイト |

**つまり容量は改善しない。** F-299 の結論（TextBox は Picture の 1.10 倍で、
省メモリなら従来のスプライト表 80 B/文字が最軽量）はフォントを借りても変わらない。

### 実機にあるフォント（`0x3302ABE0` から `0x198` 刻みで 5 個）

| # | 番地 | セル | 枚数 | 字形数 | 書式 | CMAP の範囲 |
|---|---|---|---|---|---|---|
| 0 | `0x3302ABE0` | 17x24 | 154 | **5390** | 11 | 14 個。`0020-007E` `00A0-0107` `3041-3093` `30A1-30F6` `3131-318E` `E000-E07E` `FF01-FF5E` `010A-0192` `0335-03CE` `0401-0451` `2460-2592` `3336-33DD` `FF61-FFE6` `0000-FFFF` |
| 1 | `0x3302AD78` | 7x7 | 3 | 192 | 11 | かな のみ（**ASCII が無い**） |
| 2 | `0x3302AF10` | 22x29 | 3 | 15 | 11 | 記号・ボタン絵 |
| 3 | `0x3302B0A8` | 15x21 | 1 | 16 | **9 = LA4** | 記号・ボタン絵 |
| 4 | `0x3302B240` | — | — | — | — | 未初期化（FINF = 0） |

**#0 が本命**（ASCII も日本語も入る）。シートは 154 x `0x2000` ≈ 1.2 MB。
セルが 17x24 なので、いまの 8px 表示に合わせるなら TextBox の
文字サイズ（`+0xE4`/`+0xE8`）で縮小する。

### ★未確認 — 寿命

**静的領域 `0x900000`-`0x9C0000` を走査したが、これらを指す大域変数は 0 件だった。**
ヒープ上の管理構造から保持されている。したがって
**場面転換やロードを跨いで同じ番地に居続けるかは未検証。**

- 番地 `0x3302ABE0` は F-139 の記録と一致しており、少なくとも決まった位置に確保される
- 1.2 MB の常駐資源で、タイトル画面でも読み込まれている
- しかし「大域から指されていない = 誰かが解放しうる」ので、**番地を焼き込まない**こと。
  使うなら実行時に取り直す経路（レイアウトの ResourceAccessor 経由）を用意するか、
  場面を跨いで不変であることを実測してから採用する。
