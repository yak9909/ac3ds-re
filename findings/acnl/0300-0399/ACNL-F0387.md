## F-359（2026-09-08）: ★起動シーケンスと「しずえ画面 → 村へ出る」経路（＋未知のコード領域の発見）

confidence: **HIGH**（静的 + 実機 bp で確定）。詳細は `scratchpad/MEMO_f359_boot_sequence.md`。

### 1. ★★静的 IDB にもランタイムダンプにも無いコード領域がある

`Room_RequestChange` に bp を置いたら呼び出し元が `0x00BF7BA8` — **`.text`（〜`0x839000`）の外**だった。

| | |
|---|---|
| 範囲 | 約 `0x00B00000` 〜 `0x00C50000`（約 1.5MB） |
| 中身 | 本物の ARM コード。`AcStrcBoat` / `AcStrcTrain` / `BsVrboxSky` / `Strc/sobj/*.bcres` など**本作固有の文字列**を含む |
| 下位への呼び出し | **ベニア表**（`0x00BE3xxx`）。`LDR PC,[PC,#-4]` + 絶対番地。例 `0x00BE3A90` -> `vc_ROOMFUNC` |
| ダンプ | **`NCCH/exefs/code_hi.bin`**（`0x00B00000` 起点 0x180000 B）。取得は `scratchpad/dump_hi_code.py` |
| 逆アセンブル | `scratchpad/code_hi.asm`（objdump `--adjust-vma=0x00B00000`） |

★**`code_runtime.bin` は 10MB（`0x100000`〜`0x00B00000`）しかなく、その外側**。
これまでの静的解析が丸ごと見落としていた。★何のセグメントかは**未確定**（オーバーレイか、単にコード節が大きいのか）。

### 2. タイトル画面の 32 段ステートマシン

| | |
|---|---|
| ディスパッチャ | `0x00BF720C`。`段階 = byte[this+0xD1D]` を表 `0x00C013F4`（8B/entry、28 段）で引いて `BLX` |
| 段階 19 | `0x00BF7AFC` = **部屋ワープ要求**。行き先は `byte[this+0x2000]`、`vc_ROOMFUNC(部屋,1,1,1,1)` |
| 実測 | プレイヤー選択の確定で `this=0x330BADD4`（この起動限り）/ `this+0x2000=0x63` / 段階 19 |
| 遷移 | `0->1 / 1->4,2 / 2->4 / 3->16 / 4->5,{18,23,21,10} / 5->6 / 7->8 / 10->26 / 11->{12,13,21,22} / 12->15 / 13->20 / 14->12 / ★15,17,18->19 / 21->{15,11} / 22->15 / 23->2 / 25->12 / 26->{0,9}` |

★**このマシンはタイトル画面の場面専用**。部屋 `0x63` の中は別の主体が回している
（`0x00BF0794`（段階 19 へ）に bp を置いても村へ行く瞬間には当たらなかった）。

### 3. ★「しずえ画面 -> 村へ出る」経路（実機で確定）

`Room_RequestChange` に**条件付き bp（`R1 == 0`）**を置いて捕獲。呼び出しの鎖:

```
? （部屋 0x63 の進行役。未特定）
 -> sub_5B464C   0x005B464C  Room_UseExit(mgr, 出口番号, …) = sub_5B5798(mgr, 現在部屋, 出口番号, …)
 -> sub_5B5798   0x005B5798  出口テーブル（off_95135C[部屋]、36B/entry）で分岐
                             ★行き先コード 170..173 -> vc_PRELOAD(mgr, コード+86, …)
                               (コード+86)&0xFF = コード-170 = プレイヤー番号 0..3
 -> vc_PRELOAD   0x005B5034  ★「村（部屋 0 決め打ち）へ行き、そのプレイヤーの家の前に出る」
                             座標は sub_3072F4(pos, 番号) = 家の玄関。高さ +32.0
 -> vc_RELOADFUNC 0x005B4F98 ★「座標つき部屋変更」。mgr+72..80 座標 / +84..88 角度 / +92 種別
 -> Room_RequestChange 0x005B419C   byte_95133B = 0 / word_94A3D0 = 1
```

捕獲値: `R0 = 0x00ABB948`（**固定グローバルの遷移マネージャ**）/ `R1 = 0`（村）/ `LR = 0x005B5014`。
停止時のマネージャ: `+0x48/+0x50` = 出現座標 (2640.0, 0.0, 1632.0)、`+0x5C` = 70。
→ **家の玄関の座標が入っている**ことまで確認。

### 4. チートの当て先（案。★未実装・未検証）

部屋 `0x63` に入ったら **`vc_PRELOAD(0x00ABB948, プレイヤー番号, 0, 0, 1, 1.0f)` を 1 回呼ぶ**。
ゲーム自身がこの経路を使うので座標も向きも正しい。`0x00ABB948` は固定。

**未解決 3 点**:
1. 選択されたプレイヤー番号を持つグローバルが未特定（ゲームは出口テーブルのコードから得ている）
2. **★いつ呼べば安全か。** 会話の段階にセーブ読み込み・プレイヤー生成が混ざっている可能性。
   早すぎると壊れる。部屋 0x63 に入って何フレーム後なら安全かを実機で詰める必要がある
3. 二重発火を防ぐ旗（`Room_RequestChange` 側にガードはある）

### F-359 追記（2026-09-08）: 判断点の確定と★高位領域の非固定性

**`sub_5B464C`（`Room_UseExit`）に bp。村への遷移で 1 回だけヒット。**

```
R0 = 0x00ABB948（= vc_ROOMDAT() の戻り値）/ R1 = 0（★出口番号 = プレイヤー番号）
R2 = 1  R3 = 0  [sp] = 1  [sp+4] = 1 / LR = 0x00BE6BB4
-> 実引数は Room_UseExit(vc_ROOMDAT(), プレイヤー番号, 1, 0, 1, 1.0f)
```

呼び出し元 `0x00BE6A34` は**イベント ID による 13 分岐**で、**ID 1 が「村へ行く」**。
手前に `"SYS_Start"` / `"ENT_SS_SELLCANCEL"` の文字列があり、
**しずえ画面の UI がイベントを投げる構造**だと分かる。

#### ★★高位領域（0x00B00000〜0x00C50000）は起動ごとに配置が変わる

2 回目の起動でダンプした `code_hi.bin` では `0x00BE6BB0` は `LDR` だったが、
3 回目の起動の実機では同じ番地が **`BL`** だった。
→ **この領域は動的にロードされる。番地をチートに焼き込んではいけない。**
`NCCH/exefs/code_hi.bin` / `scratchpad/code_hi.asm` は**その起動限りの資料**。

安定しているのは下位の番地だけ:
`Room_UseExit 0x005B464C` / `vc_ROOMDAT 0x00308110` / `vc_PRELOAD 0x005B5034` /
`vc_RELOADFUNC 0x005B4F98` / `Room_RequestChange 0x005B419C` / `g_CurrentRoomId 0x0095133A` /
`遷移マネージャ 0x00ABB948` / 部屋 0x63 の出口表 `0x00953C78`（4 本・コード 170..173）。

#### チートの形（安定番地だけで書ける）

```
if (*(u8*)0x0095133A == 0x63 && !済み旗 && 【安全条件】) {
    Room_UseExit(vc_ROOMDAT(), プレイヤー番号, 1, 0, 1, 1.0f);   // 0x005B464C
    済み旗 = 1;
}
```

★**【安全条件】が唯一の未確定**。会話の段階にセーブ読み込み・プレイヤー生成が
混ざっている可能性があり、早すぎると壊れる。
**部屋 0x63 に入って N フレーム後**の N を大きい方から下げて詰めるのが安全。
