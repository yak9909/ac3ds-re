## F-313: 「実測でないと決められない」は誤り。静的に決着した — HIGH

> F-312 D で `LIST_SIZE` を上げられるか・1 文字あたり何バイトかを
> 「実機で測る」と書いたが、**どちらも静的解析だけで決まった。**
> 測る前に静的に詰める、という原則を自分で破りかけた。

### A. `LIST_SIZE` は上げられる — ゲーム自身が 0x18000 を使っている

`sub_121988`（= `nngxCmdlistStorage`）の大きさは呼び出し元が決める。
`Layout` の初期化 `sub_5685A4(this, ?, ?, size)` が `sub_121988(size, 1)` を呼ぶので、
**`BL 0x5685A4` の直前で R3 に入る値を全部拾えば、ゲームが実際に使う値が分かる。**

`.text` 全域を走査して **`BL 0x5685A4` は 129 箇所**。R3 の即値／リテラルを機械で拾った結果:

| size | 箇所 |
|---|---|
| `0x1000` | 23 |
| `0x2000` | 12 |
| `0x3000` | 9 |
| … | … |
| **`0x8000`（我々の現行）** | **3** |
| `0x9000` | 4 |
| `0xF000` | 2 |
| **`0x10000`** | **3**（`0x23EEC4` / `0x27BB3C` / `0x2F2768`） |
| `0x11000` | 1（`0x6AF220`） |
| **`0x18000`（98,304 B）** | **1**（`0x196EEC`） |

★1 件だけ `0xEB0B5520` が出たが、**リテラルの位置がコードを指していた**＝走査の誤検出。
  呼び出し元の番地まで出して確認し、除外した（**外れ値を黙って捨てない**）。

→ **`LIST_SIZE` を `0x10000` にするのはゲーム自身がやっていること。実測は要らない。**

### B. 記録される 1 文字あたりのバイト数も式で出る

`sub_4D6570`（バッチ→コマンド列の組み立て）は**字形を直接コマンドへ書かない**。
`a1+1640/1648/1652` の配列へ溜め、上限（`a1+36` > 25 / `a1+38` > 30 / `a1+39` > 24）で
`sub_4D6CE0` がまとめ書きする。その 1 回ぶんの語数を数えると:

```
Q = この束の字形数（<= 25。ただし UV が 2Q <= 30 なので実質 Q <= 15）
C = 色欄の数（4 から始まり色替えごとに +4。<= 24）

幾何   (16Q+16)/4 = 4Q+4 語
色     初回 4C+4 語 / 以降 4C-12 語
UV     U=2Q なので (16U+16)/4 = 8Q+4 語
末尾   4 語 + 固定 0x40 バイト = 16 語
先頭に 1 バッチあたり定型 0x60 バイト = 24 語
```

**独立した 2 つの結果の突き合わせ**（CLAUDE.md の要求）:

| | |
|---|---|
| この式で 17 文字・1 色 | **338 語** |
| F-308 の実機実測 | **306 語** |
| 差 | +32 語（+10.5%。**式が安全側に多め**） |

→ **1 文字あたり約 61 バイト**（同じ色が続く場合）。
  色を 1 字ごとに変える最悪でも `12*6 + 4*24 + 16 = 184 語 / 6 字 ≒ 123 B/字`。
  ライブラリの予約 `78 語/字 = 312 B/字` はさらに 2.5 倍の余裕を見た値。

### C. 1 本のバッチに複数の文字列を積めることも静的に確定

`sub_4D6570` は `v7 = min(batch+0x04 件数, batch+0x06 上限)` の**全件**を走査し、
マテリアルごとにまとめる。**複数文字列を 1 本に積むのはこの関数の設計そのもの。**
F-308 の `0x004D4F78`（件数が単調増加）と合わせて、実機で確かめるまでもない。

### D. 決まった構成

| | 値 | 根拠 |
|---|---|---|
| `LIST_SIZE` 上画面 | **`0x10000`** | ゲーム自身が 3 箇所で使用 |
| `LIST_SIZE` 下画面 | `0x8000` | 下画面は表示物が少ない |
| 借用 | **`0x50000`（327,680 B）** | 下の配置が 87% で収まる |
| バッチ | 上 512 字 / 下 128 字（共有 1 本ずつ） | 上画面の同時表示は **502 字**（数え上げ） |
| Picture | 48 枚 | |

| | |
|---|---|
| 上画面 502 字の記録量 | 27,864 B = `LIST_SIZE 0x10000` の 8 割の **53%** |

★参考: TextBox を 1 文字列 1 個で持つ案は 476,160 B で、これだけで予算を食い潰していた。

★★**この節にあった「自前の取り分の合計 426,032 B / ゲームへ残る 312,844 B」は誤り。**
  `LIST_SIZE` を nw::lyt ヒープの予算から引いていたが、**別のヒープだった**。
  **F-314 で訂正した。**

### E. 教訓

**「実機で測らないと決められない」と言う前に、値を決めているコードを探す。**
今回は `size` が呼び出し元の即値だったので、`.text` を走査するだけで答えが出た。
1 文字あたりのコストも、溜めてまとめ書きする関数の語数を数えれば式になった。
