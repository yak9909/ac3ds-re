## F-299 (HIGH・静的＋実機の実データ照合) — ★F-298 の検証と**訂正 2 件**。バッチの確保元を特定（残件 1）

### A. 検証 — 別経路で裏が取れたもの

| 主張 | 裏取り |
|---|---|
| TextBox vtable = `0x008FC07C` | **`nwlyt_TextBox_Ctor`(`0x4BB2A4`) がこの値を書き込む** |
| `DrawSelf` = `0x0073CF48`（スロット 26） | **`0x73CF48` への唯一のデータ参照が `0x8FC0E4` = `0x8FC07C + 0x68`** |
| ResFont vtable = `0x008FCAAC` | **`nwfont_ResFont_Create`(`0x4D82B8`) がこの値を書き込む** |
| `+0x100` = Material | Ctor が `AllocMemory(80,4)` して `v9[64]` へ入れる（Picture と同じ 80 バイト） |
| `+0xE0` = Font | Ctor が ResourceAccessor から引いて `v9[56]` へ |
| `+0xD4`=文字列 / `+0xF8`=容量 / `+0xFA`=文字数 / `+0x104`=バッチ | **デストラクタ(`0x4BB504`) が解放する 3 つ**から確定 |

**実機の本物の `ResFont` と全欄を突き合わせた**（`0x3302ABE0`。F-139 の記録と同一番地。ほかに 4 個）:

```
ResFont  +0x08=FINF 0x3187CA1C  +0x0C=記述子 0x319BE954  +0x10=6  +0x14/16=0x0035/0x0015
FINF     代替字形=0x140B 既定CWDH=00,11,11 TGLP=0x3187CA3C CWDH=0x319B0A88 CMAP=0x319B4974
TGLP     cellW=17 cellH=24 baseline=18 maxCharW=16 sheetSize=0x2000 枚数=154
         書式=11 列=7 行=5 シート 128x128 データ=0x3187CA80
CMAP[0]  0x0020〜0x007E 方式=0 先頭字形=0x0000     ← ★ASCII が方式 0（直接写像）で実使用
CMAP[1]  0x00A0〜0x0107 方式=0 先頭字形=0x005F
CMAP[2]  0x3041〜0x3093 方式=0 先頭字形=0x0323（ひらがな）
CMAP[3]  0x30A1〜0x30F6 方式=0 先頭字形=0x037A（カタカナ）
記述子   +0x00=0  +0x04=0x3302ABE0  +0x08=0x0430F950  +0x0C=0x00800080  +0x10=0x0B
```

- **F-298 の構造モデルは全欄が実物と一致した。**
- 記述子 `+0x08` = `0x0430F950`、シートデータ `0x3187CA80` の
  **`(VA − 0x10000000) >> 3` と完全一致**。リニア FCRAM の規則どおり。
- セルの詰め方も検算できる: `(17+1)×7+1 = 127 ≤ 128`、`(24+1)×5+1 = 126 ≤ 128`。
  **`(cellW+1)×列+1` の 1 画素余白が実データで裏付けられた。**

### B. ★訂正 1 — 「記述子 `+0x04` に 2 命令のスタブが要る」は**誤り**

実機の記述子 `+0x04` は **`ResFont` 自身**を指していた。
そのスロット 25（+0x64 = `0x743A10`）は `LDR R0,[R0,#0x10] / BX LR` で
**`ResFont+0x10` を返すだけ**。つまり `+0x04` に自前 ResFont を指させれば、
reg `0x083` の値は `ResFont+0x10`（実機では `6`）という**ただのデータ**で決まる。

**自前コードは 1 命令も要らない。**

### C. ★★訂正 2 — 「TextBox は容量が桁違いに軽い」は**誤り**

F-294 / F-298 は **TextBox 本体 264 バイトだけ**を数えていた。
実際には **TextBox 1 個ごとに専用のバッチ領域**が要り、そちらが支配的だった。

`sub_4D5480(n)`（n = 最大文字数）が要求するバイト数:

```
align16( 44n + 0x28 + align4(ceil(n/8)) )  +  4 × ((78n + 57) & ~3)
   ↑グリフ記録 44 バイト×n              ↑コマンド語数の上限 78 語/文字
```

**1 文字あたり約 356〜377 バイト。**

| | 文字 196 字 / 文字列 12 本 |
|---|---|
| Picture 方式（1 文字 = 1 Picture、352 B） | 68,992 バイト |
| **TextBox 方式（本体 0x108 + バッチ）** | **76,144 バイト（1.10 倍）** |

**TextBox は容量で勝たない。むしろ 1 割重い。**
利点は容量ではなく **整列・折り返し・行送り・字送りをライブラリがやること**、
そして**文字列の差し替えがペイン木の作り直しを伴わないこと**。

### D. 残件 1 の答え — バッチの確保元と全欄

**TextBox vtable スロット 28（+0x70）= `0x0013B9A8`** が確保する。
`nwlyt_TextBox_AllocStringBuffer`（`0x4BB084`）が各欄を 0 にしたあと、
`(vtable+0x70)(textbox, 最大文字数, フラグ)` を尾呼びする。

```
sub_13B9A8(textbox, n, flags):
    既存バッチのフラグが違えば vtable+0x74 で解放
    2(n+1) > *(u16*)(textbox+0xF8) なら:
        文字列 = AllocMemory(2(n+1), 4)   → 0 埋め、+0xD4 と +0xF8 を設定
        バッチ = flags&8 ? sub_4B8F58(align16(sz)+cmd, 16) : AllocMemory(sz, 4)
        *(textbox+0x104) = sub_4D5470(バッチ, n)      ← 初期化
        flags&8 なら *(バッチ+0x18) = 二枚目のコマンドバッファ
```

初期化 `sub_4D5470` → `sub_4D76BC(buf, n)` が組む欄:

| オフセット | 中身 |
|---|---|
| `+0x00` u32 | 最大文字数 n |
| `+0x04` u16 | 現在の件数（`EmitGlyphQuad` が増やす。n で頭打ち） |
| `+0x06` u16 | 描く上限（`0xFFFF` = 無制限） |
| `+0x08` u8 | 構築済みフラグ |
| **`+0x09` u8** | **フラグ。bit1 = GPU が直読み＋キャッシュ処理 / bit2 = 二枚目を使う / bit3 = デバイスメモリ・二重化** |
| `+0x0C` | 済みビット列 = `buf + 44n + 0x28` |
| `+0x10` | 現在のコマンドバッファ |
| `+0x14` | コマンドバッファ基準 = `align16(ビット列の後)` |
| `+0x18` | 二枚目（bit3 のときだけ） |
| `+0x1C` | コマンド語数（`BuildCommandStream` が書く） |
| `+0x20` | コマンド語数の上限 = `(78n+57)&~3` |
| `+0x28`〜 | **グリフ記録 44 バイト × n** |

★`sub_4D5480` の大きさ計算と `sub_4D76BC` の配置は**独立に導いて一致した**
（記録 44n → ビット列 → 16 境界 → コマンドバッファ）。

### E. ★バッチは普通のメモリでよい（`+0x09` = 0 にする）

`TextBatch_CopyToCommandBuffer`（`0x4D520C`）は `batch+9` の bit1 で分岐する。

- **bit1 が 0**: `Mem_Copy(cursor, *(batch+0x10), 4 × *(batch+0x1C))`
  — **CPU が記録列へ複製するだけ。GPU 可視である必要がない**
- bit1 が 1: `sub_348BEC` で GPU に直読みさせる（`BuildCommandStream` 末尾の
  `RangeCacheOp` も `batch+9 & 2` で守られている）→ リニア領域とキャッシュ処理が要る

**したがって `+0x09 = 0` にすれば、バッチは借りたヒープに置ける。**
デバイスメモリも二重化もキャッシュ処理も要らない。

### 判定

**TextBox 方式は実装できる。自前コードは 1 命令も要らず、全部データで組める。**
ただし **容量の利点は無い**（Picture 方式の 1.10 倍）。
選ぶ理由があるとすれば、**整列・折り返し・行送りをライブラリに任せられること**と
**文字列の差し替えが軽いこと**であって、省メモリではない。

省メモリを狙うなら **F-297 で選んだ「文字は従来のスプライト表（80 B/文字）」が
依然として最も軽い**（Picture の 4.4 分の 1、TextBox の 4.5 分の 1）。
