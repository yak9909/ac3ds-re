## F-307 (HIGH) — ★基準仕様 v2 を改訂し、**仕様書そのものを機械で検証**した

### A. 改訂の内容

制定時（2026-09-05）の §3 は「文字だけ v1 のスプライト表 + 自前ケーブ（`CAVE_TXT`）」だった。
これを **「自前フォント資源 + 標準の TextWriter/TextBatch 経路」** に置き換えた。
あわせてアトラスの置き場を `g_GfxAllocator` から借りたヒープへ移した。

**測定した差**（`own_font_data.batch_size` と F-297/F-299 の実測から計算）

| | 制定時（自前スプライト表） | 改訂 1（標準の文字経路） |
|---|---|---|
| 実機実績 | **無し**（未実装） | **有り**（F-305 / F-306 の 2 経路） |
| 自前 GPU コード | `CAVE_TXT` を手書き | **0 語**（TextBox）／ 75 語（TextWriter。GPU コマンドは書かない） |
| 文字 174・矩形 10 の容量 | 35,680 B（27%） | 97,124 B（74%） |
| 1 文字あたり | 91 B | 443 B |
| アトラス用リニア確保 | `g_GfxAllocator` 0x4000 | **不要** |

**改訂の理由**: 制定時の仕様は**核が未実装のまま**で「戻り先」にならない。
手書きの GPU 状態確立は **F-287 の事故の型そのもの**で、標準経路に寄せると構造的に消える。

**悪くなった点**: 容量が 4.9 倍。緩和は借り直し（F-296）。
省メモリ最優先なら v1 を参照し、この文書を書き換えない。

### B. ★仕様書を機械で検証する（`PATCHES/verify_spec_v2.py`）

仕様書は「戻り先」なので、番地・オフセット・式が 1 つでも違うと後で事故になる。
**人の目で読み直すのではなく機械で突き合わせる。** 8 群:

| 群 | 内容 | 結果 |
|---|---|---|
| 1 | 関数 21 本の中身を `code_runtime.bin` と 1 語ずつ照合 | 0 |
| 2 | vtable スロット 11 件 | 0 |
| 3 | 個別の命令 12 件 | 0 |
| 4 | データの値 2 件（読み取り器の表） | 0 |
| 5 | 仕様書に出てくる番地 32 個がイメージの範囲内か | 0 |
| 6 | 式と数値（バッチの式・UV・倍率・記述子・致命的 2 条件） | 0 |
| 7 | 仕様書と実装スクリプトの定数 13 件の突き合わせ | 0 |
| 8 | 「必ず書く」と決めた記述 12 項目の欠け | 0 |

**総異常 0 件。**

### C. ★検証器を書くときも「記憶で期待値を書かない」

最初の実行で 9 件の不一致が出たが、**8 件は仕様書ではなく検証器の期待値が誤り**だった。
私が命令語を記憶で書いたためで、CLAUDE.md が禁じている習慣そのもの。

idalib で該当箇所を逆アセンブルして確かめた結果、**仕様書の主張はすべて正しかった**:

| 番地 | 実際 | 仕様書の主張 |
|---|---|---|
| `0x5686D4` | `PUSH {R3-R5,LR}` | RecordPaneTree ✔ |
| `0x73BAC4` / `0x73BACC` | `FLDS S3,[R1,#0x18]` / `S1,[R1,#0x1C]` | layout+0x28 / +0x2C ✔ |
| `0x4D6570` | `PUSH {R0,R1,R4-R11,LR}` | R0=drawctx R1=writer ✔ |
| `0x73CE64` | `PUSH{R4-R6,LR}/MOV R4,R1/MOV R5,R0` | BuildMatrix(pane, mtx) ✔ |
| `0x73B57C` | `SUB R0,R4,#4` | 実体 = 節−4 ✔ |
| `0x4D7190` | `LDRNE R0,[R4,#0x10]` | root = *(a2+0x10) ✔ |
| `0x4D51F4` / `0x4D5200` | `FSTS S18,[R4,#0x24]` / `S0,[R4,#0x28]` | scaleX / scaleY ✔ |

残り 1 件は仕様書の文字列照合が飾り記号（`` ` ``）で外れていただけ。

> ★教訓: **検証器の期待値も逆アセンブルから取る。**
> 記憶で書くと「正しいものを誤りと判定する」偽陽性になり、
> 直さなくてよい文書を直しにいく事故につながる。

### D. 実機に対する照合（★完了）

**独立した 2 つ目の結果**として、静的イメージではなく**実機**に対しても照合した。

★途中で全番地が `0xFFFFFFFF`（`dbg_read_memory` が `None`）になり
「デバッガの不調」と判断したが、**真因は 3DS の電源が落ちていた**こと。
`0xFF` はマップされていない領域の徴候であり、対象が消えた場合も同じに見える。
`state = -1` / `PC` が読める / 画面が止まったまま、でも**対象は存在しない**。
Chokistream はゲームの切断を検知しないので画面は最後のフレームのまま残る。
**「レジスタは読めるがメモリが全部 0xFF」なら、まず対象の生死を疑うこと。**

再起動・再アタッチ後、素の実機で仕様書 §5.1 の手順を**最初から実行**して照合した。

| 群 | 件数 | 不一致 |
|---|---|---|
| ゲーム側（vtable 11 / 関数 11 / 読み取り器の表 / LayoutMgr / TagProcessor） | 24 | **0** |
| GUI 側（ノードの寸法・優先度・射影・記録長 / VTBL 3 / アトラスの境界 / バッチの式と状態 / TextBox の欄 / `node+0xB0`） | 26 | **0**（※） |
| フォント資源（ResFont / FINF / TGLP / CMAP / 記述子） | 13 | **0** |

※ 1 度 `FINF[0x07] = 0` と出たが、**照合スクリプトが FINF の番地を記憶で書いていた**
（正しくは `OFF_FINF = 0x103A0`。`0x10300` を読んでいた）。
**番地はスクリプトの定数から取る**ように直したら一致した。C 節と同じ型の偽陽性。

**手順書としても検証できた**: 素の実機に §5.1 の 5 段を順に適用し、
最後に「OWN FONT 0123 ABC」が自前フォントで描画されるところまで再現した。
