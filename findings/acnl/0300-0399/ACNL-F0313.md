## F-289 (HIGH・実機) — ★`nwlyt_Picture_DrawToCommandList` に**自前 Picture** を渡して 1 枚描けた

`0x73CB58 nwlyt_Picture_DrawToCommandList(picture, cursor, a3, drawctx)` は
ゲーム自身の「UI を 1 枚描く」関数（内側で `Material_EmitState` /
`TextBox_UpdateDrawState` / `DrawCtx_FlushBatch` を呼ぶ）。
**`.bss` に置いた自前の Picture を引数に取り、位置も大きさも自前の値で描けた。**

道具: `PATCHES/probe_picture_draw.py`（捕獲）/ `PATCHES/exp_picture_call.py`（実験本体）。
**自前 GUI のケーブには一切触っていない**（フックは `0x73CB58` の 1 本だけ、ケーブは `0x838D00`）。

### やりかた

1. 入口にケーブを置き、最初の 1 回だけ picture / material / drawctx を控える
2. 実物を `0x9B6000` へ複製し、**自己参照ポインタ 25 個を張り替える**
3. 引数が捕獲したのと同じ Picture のときだけ、**クローンで同じ関数を 1 回呼ぶ**（再入は `BUSY` で止める）
4. 返ったカーソルを `[SP,#4]`（元の R1）へ書き戻して**コマンド列を繋ぐ**

### 実機の結果

| 設定 | 画面 |
|---|---|
| 200x120 / T=(40,40) | 上画面に**大きな余分な 1 枚**が出た |
| 96x48 / T=(-120,80) | 消えた（自前 GUI パネルの下。パネルは優先度 0xFF） |
| 120x80 / T=(100,0) | 右側に**単一の矩形**。大きさ・位置とも指定どおり |

自前 GUI は終始無事、明滅なし。**カーソルの繋ぎ替えが正しい証拠でもある。**

### Picture の構造（実測。実体は約 `0x320` バイト）

```
+0x000 vtable 0x008FBFFC
+0x048 幅      +0x04C 高さ
+0x080 行列 3 行 x 4 列（[0][3],[1][3] が平行移動）
+0x0B5 色の数  +0x0D4 UV 計算済み  +0x0D8 UV セット数  +0x0DC UV(4 float)
+0x13C マテリアル = pic+0x1A0   ★**埋め込み**
+0x140 頂点カラー x4
+0x154 = pic+0x16C
```

### ★これが意味すること

- **マテリアルを別途こしらえる必要が無い。Picture を複製すれば材質も自分のものになる。**
  F-269 で借り物のマテリアルをやめた理由（場面切替で解放される）は、複製すれば起きない。
- 置き換えられるのは CAVE_Q（388 語）のうち
  **テクスチャ 7 組 14 語 + 自前 TEV 36 語 + スプライトループ + 色 + カウンタ**。
  この関数は溢れ判定まで面倒を見るので、
  **チャンク 7 枚・色はチャンク単位という制約（F-280）も外れる。**

### まだ解けていないこと

複製したマテリアルには外部への参照が残る。
`+0x208`/`+0x300` = テクスチャ番地（VRAM `0x180C1900`）、
`+0x254`/`+0x258`/`+0x274`/`+0x278`/`+0x318` = 他のゲームオブジェクト（`0x32E3xxxx`）。

`+0x208`/`+0x300` を自前アトラスの物理番地 `0x229D8500`、大きさ `0x00800080`、
`+0x218` を 9 にしたところ **絵は変わった（ロゴ→縞状のノイズ）**。
→ **番地の差し替えは効く。書式の欄が特定できていない**（`+0x218` は書式ではない疑い）。
次は `Material_EmitState`(`0x4B7864`) を読んで
**マテリアル内オフセット → PICA レジスタ（0x082/0x083/0x085/0x08E）**の対応表を作る。

詳細は `scratchpad/MEMO_f289_picture_call.md`。

### F-289 段 2 — ★自前アトラスまで貼れた。テクスチャ記述子 → PICA レジスタの対応表を確定

`TextBox_UpdateDrawState`(`0x4B7DEC`) の逆コンパイルから:

```c
v10  = *(material + 48) & 3;                 // ユニット数
desc = *(material + 52) + 32 * unit;         // 記述子の先頭
cache[0] = *(desc + 24);
cache[2] = *(desc + 4) >> 3;                 // ★ここだけ >>3
cache[4] = *(desc + 28);
cache[6] = *(desc + 20);
// 差があれば cache（32 バイト = [値,ヘッダ] x 4）をそのままコマンド列へ Mem_Copy
```

実機の `unk_97B74C` のヘッダを読んで、枠とレジスタの対応を裏取りした。

```
ユニット0 @0x0097B74C : 0x000F0082 / 0x000F0085 / 0x000F008E / 0x000F0083
ユニット1 @0x0097B76C : 0x092 / 0x095 / 0x096 / 0x093
ユニット2 @0x0097B78C : 0x09A / 0x09D / 0x09E / 0x09B
```

**★テクスチャ記述子の中身（確定）**

| 記述子オフセット | PICA レジスタ | 意味 |
|---|---|---|
| `+0x04` | **0x085**（`>>3` される） | テクスチャの**物理番地** |
| `+0x14` | **0x083** | ラップ／フィルタ |
| `+0x18` | **0x082** | 大きさ（高 << 16 \| 幅） |
| `+0x1C` | **0x08E** | 書式 |

ユニット数 = `*(material + 48) & 3`、記述子の先頭 = `*(material + 52)`。

**段 1 で「番地は効くのにノイズ」になったのは書式の欄の取り違え**（`+0x14` は
ラップ／フィルタ。書式は `+0x1C`）。`+0x20C`/`+0x210` はこの関数が読まない欄だった。

### 実機で確認（成功）

クローンの記述子を `番地=0x229D8500 / ラップ=0 / 大きさ=0x00800080 / 書式=9` に変えたところ、
**自前アトラスがそのまま画面に出た**（拡大すると `GHIJKLMNO` / `WXYZ01234` / `:;!?-+*/=` が読める）。

→ **自前 Picture ＋ 自前の位置・大きさ ＋ 自前のテクスチャ を、
ゲーム自身の `nwlyt_Picture_DrawToCommandList` が描く**ところまで一気通貫で実証できた。

裏取りは独立に 2 つ: (1) `TextBox_UpdateDrawState` の静的読み、
(2) `unk_97B74C` の実測ヘッダ。加えてクローンの `+0x1C` の値 `0x0D` が
キャッシュの reg 0x08E の値と一致し、`reg 0x085` に積まれる `0x0453B0A0` は
**自前ケーブが使っている値と同一**だった。

### 残る課題

- **色が薄い。** `Material_EmitState` より色は `*(material+48) & 3` で分岐し、
  0 なら reg 0x0DB = `*(material+20)`、1 なら 0x0DB = `*(material+16)` / 0x0F3 = `*(material+20)`。
  **状態キャッシュ `0x97B6FC` / `0x97B714` / `0x97B72C` を潰さないと後続へ色が漏れる**（F-157）。
- 自前の 1 枚は元の呼び出しより**前**に積まれるのでゲームの絵の下になる。
  最前面に出すなら自前ノードの記録内で呼ぶ。
- `+0x254` 系の外部参照が実際に読まれるかは**未確認**。

### F-289 段 3 — ★色も自前で決められた。**外部オブジェクトへの依存は無い**

**色**（`Material_EmitState` 0x4B7864 より）。分岐は **`*(material + 48) & 3`** で、
**この欄はテクスチャのユニット数と同じ欄**（捕獲した素材は 1）。

| モード | 積まれるもの |
|---|---|
| 0 | reg `0x0DB` = `*(material + 20)` |
| **1** | reg `0x0DB` = `*(material + 16)`、reg `0x0F3` = `*(material + 20)` |
| 2 / 3 | `sub_4B84C0` / `sub_4B85D8` の別形式 |

`0x0DB` = TexEnv3 の定数色、`0x0F3` = TexEnv4 の定数色。
実測値は `*(mat+16)=0`、`*(mat+20)=0xFFFFFFFF`、`*(mat+44)=0x15`。

**実機**: `*(mat+16)` を `0xFF0000FF` にしたら**矩形の地色が赤くなった**（文字は白のまま）。
→ **色は自前で決められる。書式は `0xAABBGGRR`**（自前ケーブと同じ）。
★ただしアルファ 0 の画素まで不透明になる。借り物 TEV は自前 TEV（F-269）と合成が違う。
**「文字だけ色を付ける」は未検証。**

**★外部参照は読まれない。** クローン内でゲームのオブジェクトを指していた 5 語
（`+0x254` `+0x258` `+0x274` `+0x278` `+0x318`）を**全部 0 にしても正常に描画継続**。
さらに **12 秒走らせても描画が続いた**。
★訂正(2026-09-06): 当初ここに「場面が切り替わっても」と書いていたが**根拠が無い**。
  放置しただけでは場面もゲーム状態も変わらない。**耐性は未検証**。

→ **クローンは自前で持てる。F-269 で借り物マテリアルをやめた理由（解放済み参照で
GPU が止まる）は、複製すれば起きないことを実機で確認した。**

### ★未解決 — 世代依存

古い世代の Picture から作ったクローンは**描かれなくなった**（作り直したら鮮明に出た）。
外部参照は読まれないと分かったので原因は別で、
`*(pic+212)` / `*(pic+216)`（UV セット数）や `*(mat+77)` bit2 まわりが怪しい。
`sub_73B650(drawctx, material, *(pic+340), pic+220)` を読む必要がある。**原因未特定。**
当面は**その場で生きている Picture から作る**運用にする。

### ★py_eval の落とし穴（実測）

`continue_process(); time.sleep(3); suspend_process()` の**同じ呼び出しの中で
メモリを読むと、まだ止まっていないので `0xFFFFFFFF` が返る**。
一度これで「プロセスが死んだ」と誤読しかけた。
**走らせる呼び出しと読む呼び出しは必ず分ける。**

### F-289 段 4 — ★UV の再計算を強制できる。テクスチャ記述子の全欄が判明

`nwlyt_Picture_DrawToCommandList` は UV を**一度だけ計算して抱え込む**。

```c
if (!*(pic+212) || (*(mat+77) & 4) == 0) {
    *(pic+216) = sub_73B650(drawctx, mat, *(pic+340), pic+220);
    *(pic+212) = 1;  *(mat+77) |= 4;
}
```

`*(pic+212)` = 計算済みの印、`*(mat+77)` bit2 = マテリアル側の印、
`*(pic+216)` = **UV セット数**、`pic+220` = 計算結果（1 組 16 バイト）。

`sub_73B650`(`0x73B650`) は
`v7 = *(material+48) << 26 >> 30`（**bits 4-5** = UV の組数）でループし、
`*(u16*)(desc+0x08) / *(u16*)(desc+0x0C)` を **UV の倍率**に使う。

**★テクスチャ記述子の全欄（確定）**

| オフセット | 読む関数 | 意味 |
|---|---|---|
| `+0x04` | `TextBox_UpdateDrawState` | reg 0x085（物理番地。`>>3`） |
| **`+0x08`** | **`sub_73B650`** | **実寸。UV 倍率の分子** |
| **`+0x0C`** | **`sub_73B650`** | **テクスチャの大きさ。UV 倍率の分母** |
| `+0x14` | `TextBox_UpdateDrawState` | reg 0x083 |
| `+0x18` | `TextBox_UpdateDrawState` | reg 0x082 |
| `+0x1C` | `TextBox_UpdateDrawState` | reg 0x08E |

**段 1 で「読まれない欄」と書いた `+0x08`/`+0x0C` は誤りだった**（読むのは別関数）。
`*(material+48)` は 2 ビット欄を複数詰めた語で、
**bits 0-1 = テクスチャのユニット数 ＝ 色のモード、bits 4-5 = UV の組数**。

### 打った手と実機の結果

クローン作成時に `*(pic+212)=0` / `*(mat+77) &= ~4` とし、記述子の `+0x08`/`+0x0C` も
自前アトラスの大きさにして、**その場で UV を計算し直させた**。

- 描画は正常。**15 秒走らせても崩れない**（★場面変化への耐性は未検証。放置しただけでは場面は変わらない）
- 読み戻すと `*(pic+212)=1` / `*(mat+77)=0x04` に戻り、UV は `0,1,1,0` に再計算済み

→ **複製した UV に依存しなくなった。**
★ただし「段 3 の不発の原因がこれだった」とは**断定しない**（不発を再現していない）。
再発したときにこの手が効くかで確かめる。

#### ★F-289 段 4 の記述の訂正（2026-09-04）

「**場面変化を跨いでも崩れない**」と書いたが、**この表現は裏付けが足りない**。

実際に観測したのは次だけである。

- 15 秒連続で走らせ、その前後で**上画面のデモの絵が変わっていた**
  （背景・カメラ位置・登場キャラが違う）
- その間ずっと自前のクローンは描かれ続けていた

**確認していないこと**

- その 15 秒の間に**ロードが挟まったか**
- Layout / Picture のオブジェクトが**解放・再生成されたか**
- 元にした Picture が生きていたかどうか

したがって正しくは「**15 秒連続で描画が途切れず、その間に上画面の絵は変化していた**」まで。
**「解放・再生成に耐える」ことは示せていない。**

なお別の観測として、実験を入れ直すたびに捕獲される Picture の番地が
`0x32E3B50C` / `0x32E32590` と**変わっていた**ので、
Picture オブジェクト自体は何らかの境界で作り直されている。
ただしそれが 15 秒の走行中に起きたかは未確認。

### F-289 段 5 — ★ロードを跨いでもクローンは生きる。見えないのは**乗り込む位置**が原因（寿命問題ではない）

判定を「元の Picture と同じか」から「**フレームが変わったか**」（自前 GUI の `LOG+0xD4` の変化）へ
変更し、**元のオブジェクトに一切依存しない**形にしたうえで、
A ボタンでタイトル → ファイル選択へ**ロードを跨いだ**。

| 調べたこと | 結果 |
|---|---|
| Picture フック `0x73CB58` | 生きている |
| 呼ばれた回数 | 3 秒で **+1452**。呼ばれ続けている |
| 判定・`BUSY` | 毎回発火し、BL も完走している |
| クローン（vtable / 行列 / 幅高 / UV / 記述子） | **すべて健在・意図どおり** |
| 自前 GUI | 上下とも正常。ゲームも落ちない |
| **画面** | **出ない**（2000x2000 でも不透明な赤でも出ない） |

**原因を実測で特定した。** 捕獲をやり直して「いま相乗りしている Picture」を測ると

```
幅 352.0 / 高さ 272.0 / 行列 [1.061 1.061 ... ] [-1.061 1.061 ... ] / テクスチャ 16x16
```

＝ **下画面の斜めチェック柄の全画面背景**だった。
この実験は「フレーム最初の `Picture_DrawToCommandList` の**直前**」に割り込むので、
**自前の 1 枚はその全画面背景に丸ごと上塗りされる**。
タイトル画面で見えていたのは、そこでの最初の Picture がたまたま
**上画面のタイトルロゴ**（3D の上）だったから。

**★結論: 寿命の問題ではない。** クローンは**外部参照を全部 0 にした状態でロードを跨いでも
完全に生きていた**。見えなかったのは**描く順序を自分で握っていない**ため。

→ 本筋は **`nwlyt_Picture_DrawToCommandList` を CAVE_Q（自前ノードの記録スロット）の中で呼ぶ**こと。
自前ノードは優先度 `0xFF` で必ず最後に再生されるので、順序を自分で決められる。
