## F-308: 大量の文字を登録したときの天井（TextWriter 直呼び方式の評価） — HIGH

> 問い: 自前チートメニューで**自前フォントの文字を大量に登録**する可能性がある。
> TextWriter 直呼び式はそれに関して問題がある設計か。
>
> 答え: **TextWriter 直呼びのほうが有利**（バッチを共有できる）。ただし
> **本当の天井は方式に依存しない場所にあり、しかも片方は無検査**。そちらが本題。

### A. 1 本のバッチに何件でも積める（静的に確定）

`nwfont_CharWriter_EmitGlyphQuad 0x4D4EAC` のバッチ枝:

```
4D4F50  LDR  R3, [R2]        ; batch+0x00 = 最大文字数
4D4F54  LDRH R0, [R2,#4]     ; batch+0x04 = 現在の件数
4D4F60  CMP  R3, R0
4D4F6C  BLS  loc_4D4FC4      ; ★満杯なら何も書かずに POP（後述 C）
4D4F70  ADD  R1, R0, #1
4D4F78  STRH R1, [R2,#4]     ; ★件数を +1 して**追記**
4D4F74/7C  ADD R3,R0,R0,LSL#1 / ADD R1,R3,R0,LSL#3   ; 44 * 件数
4D4F88  ADD  R0, R0, #0x28
```

件数は**書き込みごとに単調増加する**だけで、`DrawString` の呼び出し境界を見ていない。
したがって **1 本のバッチに複数の文字列を続けて積める**。
色も 1 字ごとに `TextDraw_BuildFourCornerColors`(`0x4D6ABC`) を通るので、
**同じバッチの中で文字列ごと・文字ごとに色を変えられる**。

TextBox 方式は**文字列 1 本につき TextBox 0x108 + Material 0x50 + 専用バッチ + 提出**が要る。
ケーブが writer とバッチを自分で持つ TextWriter 直呼びには、この per-string の付随物が無い。

### B. ただし節約は 1.06〜1.10 倍しかない（実測）

バッチの大きさ `sub_4D5480` は `align16(44n + 0x28 + align4(ceil(n/8))) + 4*((78n+57)&~3)` で、
**87.6% がコマンド予約**、つまり**ほぼ全部が文字数に比例**する。
共有して浮くのは頭部の固定分だけなので:

| 文字数 | 文字列ごとに別バッチ | 1 本に共有 | 比 |
|---|---|---|---|
| 192 | 75,744 | 69,084 | 1.10x |
| 480 | 183,200 | 171,660 | 1.07x |
| 1200 | 452,160 | 428,060 | 1.06x |

**「まとめれば劇的に安くなる」わけではない。** A は設計の素直さの利点であって、容量の利点ではない。

### C. 満杯のときの挙動 — バッチは安全、記録リストは無検査（★最重要）

| 溢れる先 | 検査 | 起きること |
|---|---|---|
| **バッチ**（最大文字数） | **有り** `0x4D4F60` `CMP R3,R0` / `BLS` | **その字を捨てて静かに戻る**。落ちない |
| **記録コマンドリスト**（`LIST_SIZE`） | **無し** | **バッファ外へ書き続ける。静かに壊れる** |

記録側に検査が無いことの根拠:

- `DrawCtx_FlushBatch 0x4B8364` — カーソル `a2` へ `Mem_Copy` して進めるだけ。
  `g_GpuCmdEnd` との比較が **1 つも無い**。
- `GpuCmd_CommitListAndCaptureDelta 0x7B0694` — 長さを
  `g_GpuCmdPtr - mgr[1] - 開始` で**測るだけ**。溢れを検出しない。
  溢れた長さがそのまま記録長になり、**バッファ外がそのまま再生される**。
- （`GpuCmd_SplitAndSubmit 0x1280CC` は `< g_GpuCmdEnd` を見るが、これは
  提出時の末尾 4 コマンドだけで、描画本体の追記経路には効かない。）

**つまり危ないのは「文字が多すぎる」ことではなく「記録リストが足りない」こと。**
そしてこれは **Picture でも文字でも同じ**＝方式に依存しない。

### D. 天井の実測値

1 文字あたりの記録ストリームは **83 バイト**、Picture 1 枚は **199 バイト**（実測）。
`LIST_SIZE = 0x8000`（`cave_node_record.py:913`）を空から使うと:

| Picture 枚数 | 入る文字数 |
|---|---|
| 0 | 394 |
| 10 | 370 |
| 40 | 298 |
| 110 | 131 |

`LIST_SIZE` を上げれば素直に伸びる（Picture 40 枚と同居の場合）:

| `LIST_SIZE` | 文字数 |
|---|---|
| 0x8000 | 298 |
| 0x10000 | 693 |
| 0x20000 | 1,483 |
| 0x40000 | 3,062 |

現状（2026-09-06 実機）: 上 `0x38D0/0x8000` (44%)、下 `0x5B00/0x8000` (71%)。
**下画面は残り 9,472 バイト = あと約 114 文字しか無い。**

### E. 借りたヒープ側の天井

バッチの予約は **1 文字 356 バイト**（実使用は 72 バイト＝予約の 22%、実機 n=17 で確認）。
固定分 0x400 + アトラス 0x4000 を引くと、**借用 0x20000 に入るのは 318 文字**。

| 文字数 | 必要量 | 借用 0x20000 比 |
|---|---|---|
| 174 | 79,648 | 61% |
| 318 | 130,880 | 100%（上限） |
| 400 | 160,128 | 122% ★超過 |
| 1200 | 445,024 | 340% ★超過 |

1,200 文字なら **0x6CA60（約 435KB）**を借りることになる。
F-296 で確保→解放→再確保の往復は実機で確認済みなので、**借り直しで対応できる**。

### F. 結論

- **TextWriter 直呼びは大量登録に対して問題のある設計ではない。** むしろ TextBox より向く。
- **ただし利点は「素直さ」であって容量ではない**（節約は 1.06〜1.10 倍）。
- **先に当たるのは記録コマンドリストで、しかも無検査で壊れる。**
  文字を増やす前に `LIST_SIZE` を上げること。これは方式と無関係の作業。
- バッチ満杯は安全側（字が消えるだけ）なので、**最大文字数は多めに取ってよい**。
  ただしその分だけ 356 バイト/字でヒープを食う。

### 残件 → **F-309 で解決**

当初「`heap+0x20 = 0x3B0000` を総量と解釈すると破綻する」と書いたが、**これは誤り**だった。
破綻したのは領域の先頭を `heap+0x04 = 0x32992270` だと**推測**したせいで、
`+0x20` の解釈は正しい。**F-309 で `+0x1C = 先頭`・`+0x20 = 総量` と確定した**
（先頭はヒープ自身の番地 `0x32C45F78`＝ヘッダが自分の領域の先頭に載っている）。
`heap+0x3C = 0x32FF69D8` を領域末尾とした推測も**外れ**（真の末尾は `0x32FF5F78`）。

★教訓: **構造体の欄を「値の見た目」から当てない。** 取得子を逆アセンブルして読む。
ここでは `sead::ExpHeap` の vtable slot 12/13/14 が先頭・末尾・総量をそのまま返していた。
