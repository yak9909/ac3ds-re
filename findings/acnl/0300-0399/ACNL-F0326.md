## F-302 (HIGH・実機) — ★★TextBox が実機で描けた。**作業オブジェクト = `LayoutMgr + 0x1C`**。コードケーブ 0 語

F-301 の結論を実機で検証し、残っていた「作業オブジェクト」を解明した。
道具は `PATCHES/add_textbox.py`。

### A. 作業オブジェクトの正体

`TextBox_EmitBatchToGpuCommands`（`0x4B7CE0`）が読む `*(DrawInfo + 0x80)` は
**`LayoutMgr + 0x1C`**（シングルトン）だった。

**追い方**（実機・読み取りのみ）:

1. `0x32C00000`-`0x32D00000` を TextBox vtable `0x008FC07C` で走査 → **13 個**見つかる
2. `0x32C9AF14` の親を `+0x0C` で 4 段たどる → root Pane `0x32C9806C`
3. その値を指す語を走査 → `0x32C85458` = **Layout `0x32C85438`**（下画面・320x240・display `0x401`）
4. その `DrawInfo+0x80`（= Layout+0xB0）= **`0x32FF5FA4`**
5. `LayoutMgr = *(0x0096FC38) = 0x32FF5F88` → **`0x32FF5FA4 = mgr + 0x1C`**

★タイトル画面のレイアウトは同じ場所が `0x1C`（ポインタでない）。
**TextBox を持たないレイアウトでは設定されない。** F-301 で「障壁」と書いたのは正しいが、
**解決は 1 語の書き込みで済む**ので、障壁の見積もりは過大だった。

### B. 実機の本物との照合（F-299 / F-301 の裏取り）

TextBox `0x32C9AF14` の全欄が模型どおりだった:

```
vtable +0x00 = 0x008FC07C          寸法 +0x48 = 72.0 x 22.0
alpha +0xB5 = 0xFF  基準点 +0xB6 = 0x14  可視 +0xB7 = 0x01
文字列 +0xD4 = 0x32CA3A20   色 +0xD8/+0xDC = 0xFFFFFFFF / 0xFFFFFFFF
★Font +0xE0 = 0x3302ABE0   （＝ゲームのフォント #0。F-300 の同定と一致）
文字の大きさ +0xE4/+0xE8 = 16.20 / 21.60     行間/字間 +0xEC/+0xF0 = 0 / 0
TagProcessor +0xF4 = 0x32C86A00
+0xF8 = 24   +0xFA = 2   整列 +0xFC/+0xFD = 4/0   dirty +0xFE = 1
★Material +0x100 = 0x32C9B030   ★バッチ +0x104 = 0x32CA3A4C
```

**バッチの実物（n = 11）で 3 式すべてが一致:**

| | 実物 | 式 |
|---|---|---|
| ビット列 `+0x0C` | `0x32CA3C58` | `buf + 44n + 0x28` ✔ |
| コマンド基準 `+0x14` | `0x32CA3C60` | `align16(ビット列 + ceil(n/8))` ✔ |
| 語数上限 `+0x20` | 912 | `(78n + 57) & ~3` ✔ |

★**フラグ `+0x09` = `0x00`、`+0x18`（二枚目）= 0。**
ゲーム自身が普通のメモリ経路（`Mem_Copy`）を使っている。F-299 の E 節を裏付ける。

### C. ★訂正 — `+0xF8` は文字数ではなく**バイト数**

`sub_13B9A8` は `v8 = 2*(n+1)` を `*(u16*)(textbox+0xF8)` へ入れる。
実物も `+0xF8 = 24`（= 11 文字ぶん）、`+0xFA = 2`（実際の文字数）だった。
F-299 で「容量」と書いたのは**文字列バッファのバイト数**が正しい。

### D. 文字列は UTF-16 **LE**

実物の生バイト `30 5E 8B 30` → LE で `U+5E30 U+308B` = **「帰る」**。
（BE で読むと意味を成さない。）

### E. TextBox の Material は**テクスチャ不要**

実物 `0x32C9B030`: vtable `0x008FC18C`（Picture と同じ）、
`+0x10` = `0x00000000`、`+0x14` = `0xFF854C1E`、
**`+0x2C`/`+0x30`/`+0x34` は全部 0**（texMap も TEV も無い）。
TextBox 経路は Material から**色 2 つしか読まない**（`0x4B7DA8` の `*(a4+16)`/`*(a4+20)`）。
テクスチャはグリフの記述子から出るので Material に要らない。

### F. 実機で組んだもの（`PATCHES/add_textbox.py MODE="add"`）

借りたヒープの `+0x10000` 以降に**データだけ**で置いた。**コードケーブ 0 語。**

| | 番地 | 大きさ |
|---|---|---|
| TextBox | `0x32EC0F60` | `0x108` |
| Material | `0x32EC1160` | `0x50`（vtable と色 2 つだけ） |
| 文字列（UTF-16LE） | `0x32EC11E0` | 14 文字 |
| バッチ | `0x32EC1260` | **`0x1490`**（= 376 バイト/文字。予測どおり） |
| フォント | `0x3302ABE0` | ゲームのものを借用 |

加えて **`NODE_BOT + 0xB0`（= DrawInfo+0x80）に `LayoutMgr + 0x1C` を書いた 1 語だけ。**
下画面 root の輪の**末尾**へ繋いだ（子 110 → 111）。

### G. 結果

| | |
|---|---|
| バッチ 件数 | **14 / 14**（全文字が積まれた） |
| 構築済み `+0x08` | 1 |
| コマンド語数 | 494 / 上限 1148 |
| dirty `+0xFE` | 1 → **0**（処理された） |
| 下画面の記録長 | `0x5580` → **`0x5DF0`**（+0x870） |
| PC | `0x00463E24`（正常。フォルト無し） |

**画面に「TEXTBOX 日本語も出る」がゲームのフォントで描画された。**
上白 → 下緑の諧調（`+0xD8`/`+0xDC`）も効いている。整列 `+0xFC = 4` で中央揃え。

### H. 結論の更新

- **TextBox は必須ではない**（F-301 のとおり。TextWriter 直呼びも成立する）
- **しかし TextBox 方式は「コードケーブ 0 語」で動く。**
  必要なのは TextBox / Material / バッチ / 文字列 の 4 つのデータと、
  **`DrawInfo+0x80 = LayoutMgr+0x1C` の 1 語**だけ
- **ゲームのフォントを借りれば日本語がそのまま出る。** 自前アトラスもリニア領域も不要
- 容量は **376 バイト/文字**（F-299 の予測 356〜377 と一致）。Picture 方式（352）と同等

★実機はこの状態のまま。外すなら `add_textbox.py MODE="remove"`。

### 2026-09-06 補足 — 軽量性は容量・CPU・GPUを分ける

F-299の省メモリ比較は保持データの比較であり、描画速度の比較ではない。
`0x73CF98`〜`0x73CFCC`の逆アセンブルとdecompileを照合し、dirty=0かつbatch+8が非0なら
再構築を省略する分岐を確認。`0x4D520C`の普通メモリ経路は既存コマンドをMem_Copyする。
旧表ケーブは記録時に行列/UV/索引を積み直すため、CPU時間の優劣は測定が必要。
標準TextBatchの約356B/文字は最大文字数に対する予約容量で、低解像度化では減らない。
またGPU送出量とも異なる（F-302の使用494語=1976Bに対し、予約コマンド部は4592B）。
TextWriter直呼びも同じバッチを使えばこの比例項は残る。バッチ無し即時経路は別の未検証案。
このセッションでは時間測定も自前フォントの適用も行っていない。
根拠・計算・現状の差分: `scratchpad/MEMO_20260906_font_cost.md`。

### 2026-09-06 TextWriter直呼び設計の静的照合（MEDIUM・実機未検証）

ユーザーはTextWriter＋自前フォントで上下画面へ描く方針を選択した。
`TextBox_RebuildBatchWriter 0x4BAFB0`と提出経路`0x4B7CE0`のassemblyを読み、
本体側のdecompileと突き合わせて引数・状態設定を確認した。

- `0x7E8488`はR0=writerを入力する（decompilerは引数を落とす）。
- `0x7E7F48`の有効引数はwriter/UTF-16LE/文字数の3つ。
  `0x4D6570`の有効入力はdrawctx/writerの2つ。余分なdecompiler引数を根拠なく埋めない。
- TextBoxを省いても提出行列・状態prefix/suffixは必要。
  標準提出はdrawctx+0x6A2=4、+0x6A0/+0x6A1=1、行列12語、+0x25=3を設定して
  `0x4D5CB0`→`0x4D520C`→`0x4B7DEC(drawctx,cursor,0,1)`と進む。
- `0x4D5CB0`は行列配列の先頭語をヘッダに置き換えるため、再提出時は行列全体を再設定する。
- writerの整列0でもYにFont由来の値×scaleYを足し、描字前にはbaselineを引く。
  `sub_743600`のfloat戻りはS0（assembly確認）。decompilerのint戻り表示だけで座標を決めない。
- 自前フォントはResFont vtableを流用してFINF/TGLP/CMAP/記述子をデータで構築する案。
  既存5x7字形を1画素余白つきアトラスへ並べる。生成・適用はまだしていない。
