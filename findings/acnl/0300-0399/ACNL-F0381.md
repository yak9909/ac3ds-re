## F-355（2026-09-07）: ★★ゲームは SELECT を START に読み替えている — 真因と正しい直し方

**confidence: HIGH（逆アセンブル + 実機で確認。利用者「START が効き、SELECT が効きません。成功です」）**

### 発端

「SELECT を落としたら START まで無効になった」。実機で測ると
**SELECT でも START でも生 HID が bit3、hold が `0x800`** になり、区別できなかった。
利用者の指摘「本当に区別できないのか。それなら何のために 2 つあるのか」を受けて
静的解析をやり直した。

### ★真因（`sub_483020`）

パッドを読む `sub_3533D0` は、最後に `sub_483020(パッド構造体)` を呼ぶ。

```c
// sub_483020。a1 = { +0 hold, +4 trig, +8 release }
if ( (*a1 & 4) != 0 )                 // SELECT(bit2) が押されていたら
    *a1 = *a1 & 0xFFFFFFF3 | 8;       //   bit2 を消して bit3(START) を立てる
*(a1+4) &= ~4;                        // trig からも SELECT を消す
*(a1+8) &= ~4;                        // release からも SELECT を消す
```

**ゲームは「SELECT は START の別名」として扱い、SELECT のビットを完全に消す。**
だから sead 層（`sub_540870` 以降）では原理的に区別できない。
`sub_540870` の対応表（HID bit2 -> `0x1000` / bit3 -> `0x800`）自体は正しく、
**bit2 がそこへ届く前に消えていた**のが答え。

★私の当初の誤り「SELECT は `0x800`」は、この読み替えの結果を見ていたためだった。
  libctru の並び（bit2=SELECT / bit3=START）は正しい。

### 正しい直し方 — 読み替えの手前に入る

```
003534DC  MOVEQ R0, R4          R4 = パッド構造体
003534E0  BLEQ  sub_483020      ← ここを差し替える（★条件 EQ のまま）
```

ケーブ B（15 語）が、読み替え関数へ渡す**直前**に
`hold` / `trig` / `release` の 3 語から **bit2 だけ**を落とす。

| | 結果 |
|---|---|
| SELECT | bit2 が無いので START へ読み替えられない -> **ゲームには届かない** |
| START | bit3 はそのまま -> **通常どおり効く** |
| CTRPF | 自前で HID を読むので影響なし -> **メニューの開閉は生きる** |

★CTRPF に判定させて旗を立てる案は、**メニューを開く 1 フレームだけ SELECT が通る**
  （CTRPF の処理はゲームの入力読み取りより後）。この方式なら穴が無い。
  利用者の指摘で気づいた。

### 構成（2 本立てになった）

| | 場所 | 役割 |
|---|---|---|
| ケーブ A | フック `0x0053CDF4`（27 語） | ボタン一括遮断（メニュー中）+ タッチ遮断 |
| ケーブ B | フック `0x003534E0`（15 語） | **SELECT を読み替えの手前で消す** |

制御ブロック `0x009B7010`: `+0` ボタン / `+1` タッチ / **`+2` SELECT（導入時に 1）**。
ケーブ A から SELECT 専用の処理は削除した（残すと START を巻き添えにする）。

### ★教訓

- **「区別できない」と結論する前に、上流をもう一段掘る。**
  読み替え・正規化を挟む層があると、下流の観測だけでは真相に届かない。
- 利用者の「それなら何のために 2 つあるのか」という素朴な疑問が正しかった。
  観測が不合理なら、観測ではなく**前提**を疑う。

### 検査と状態

検証器に 5 検査を追加（語列一致・フックが BLEQ のまま・`BIC #4` が 3 つ・
ケーブ A に SELECT 処理が残っていない・A と B が重ならない）。8 群 異常 0 件、ビルド成功。
