## F-362（2026-09-08）: case 5 の `0x00606D78` と「準備しています」の出どころ

詳細は `scratchpad/MEMO_f362_savemsg.md`。

### 1. ★case 5 の `0x00606D78` — 確定（HIGH）

`0x0094A6EC` の 8 バイトは **`BsSvMgr` の mode を指すメンバ関数ポインタ `{ptr, adj}`**。
`sub_606D78` はそこに `0x006066A0` を入れる。

mode 表は **`0x00851B04`、20 バイト x33、`{名前, enter{ptr,adj}, calc{ptr,adj}}`**。
`BsSvMgr::initialize` が同じ対に入れる 3 定数と突き合わせて確定:

| 値 | mode | 名前 |
|---|---|---|
| `0x006064C4` | 0 | 待機 |
| `0x006064B0` | 19 | ソフトリセット用ロード処理 |
| **`0x006066A0`** | **31** | **セーブエラー用村作成処理** |

→ **case 5 はセーブデータ破損時の村再作成へ誘導するエラー復旧分岐**。通常のセーブではない。
### 2. 「準備しています」= BsSvMgr mode 7 ではない — 確定（HIGH、否定）

文言は **`SYS_Save.umsbt` の index 1 / ラベル `002`**。
romfs 全 16,303 ファイル（830.8 MB）を走査し、さらに **MSBT を解析してタグを除去した
全 3,297 本のメッセージ本文**で照合しても、この文言はここにしか無い。

| 証拠 | 結果 |
|---|---|
| 静的: mode 7 の最初の状態「セーブメッセージ要求」(`sub_608930`) | ラベル **4**「セーブしています」 |
| 静的: `sub_6063B8` の 9 呼び出し元（BsSvMgr の step 表）の定数 | 34 / 4 / 15 / 4 / 9 とフィールド。**2 は無い** |
| 実機: `sub_5DC940` にトレースケーブ（起動〜村） | **記録 0 件** |

→ **「準備しています」は BsSvMgr のメッセージではない。**

### 3. ★私の前提が誤っていた — 利用者の指摘は正しかった

利用者の指摘:「セーブ確認のあと住民にも話しかけたのに記録が 1 件しかないなら、
あなたが勘違いしている可能性が高い」。**そのとおりだった。**

私は「`sub_5DC940` はメッセージ 1 件ごとに必ず通る」と考えたが、
**`"%03d"`（書式 `0x0088EE30`）の利用者は 5 本ある**（`.code` 全走査）:

| 整形関数 | 役割 |
|---|---|
| `sub_5DC940` `0x005DC940` | 私がフックしたもの。**システムメッセージ経路の 1 本にすぎない** |
| `sub_5E3704` `0x005E3704` | `*a1+8` にアーカイブ、`*a1+52` にラベル。番号は `a1[16]` |
| `sub_5E94E0` `0x005E94E0` | 汎用「番号 → 文字列」 |
| `sub_5F2954` `0x005F2954` | `a1[1]+52` にラベル、`a1[1]+8` にアーカイブ。**`sub_5DC940` を通らない** |
| `sub_75B914` `0x0075B914` | 別系統 |

さらに **`sub_6028A4(mgr, ラベル番号, アーカイブ, …)` `0x006028A4`** という
別の要求 API があり、これも `sub_5DC940` を通らない。
BsSvMgr 自身も `sub_60A118` の分岐でこちらを使う。

→ **「記録 0 件」は「メッセージが出ていない」ことを意味しない。** 住民会話が
   記録されなかったのは別経路だからで、矛盾はしていなかった。
   **教訓**: 「この関数を通れば必ず捕まる」と決める前に、
   **その書式文字列・その定数の利用者を画像全体で数える。**

### 4. ★「準備しています」の出どころ — 確定（HIGH）

**`ModulePlSelect.cro`（部屋 `0x63`＝しずえ画面）のイベントハンドラ case 0。**

ジャンプ表 `0x00BE6A7C`（13 分岐、実行時番地はこの boot のもの）:

| case | 番地 | 役割 |
|---|---|---|
| **0** | `0x00BE6AB0` | **「準備しています」を出し、村へ入る前の一括処理を走らせる** |
| 1 | `0x00BE6B68` | 村へ行く（F-361 のチートが再現した分岐） |

case 0 の実体（CRO の内部再配置と匿名インポートを適用して逆アセンブル。
**実機のバイト列と 1 語ずつ一致することを確認済み**）:

```asm
00BE6AB0  LDR  R0,[R4,#588] ... 進行カウンタが 0 のときだけ下の初期化を通る
00BE6AD0  BL   0x002F9D3C          ; 村セーブの各種欄を作り直す
00BE6ADC  BL   0x0023CBB8          ; byte_94DB2C / byte_94DB2E をクリア
00BE6AE8  BL   0x0027EB34          ; (this+632) を初期化（中で sub_2F9D3C も呼ぶ）
00BE6AF4  BL   0x00583554          ; 旗の管理役
00BE6AF8  MOV  R1,#26
00BE6B00  BL   0x0058B934          ; 旗 26 を立てる
00BE6B04  MOV  R0,#1 / STR [SP] / STR [SP,#4]
00BE6B10  LDR  R0,=0x0094A6D4      ; ★off_94A6D4
00BE6B14  ADD  R3,R4,#632
00BE6B18  MOV  R1,#2               ; ★★ラベル番号 2
00BE6B1C  LDR  R2,[R0]             ; ★★"SYS_Save"
00BE6B20  MOV  R0,R4
00BE6B24  BL   0x002388BC          ; sub_2388BC(this, 2, "SYS_Save", this+632)
00BE6B28  CMP  R0,#1               ; 1 = メッセージ終了
00BE6B30  BNE  exit
00BE6B34  BL   0x0030C994          ; ★村へ入る前の一括処理（下記）
00BE6B40  BL   0x00583554
00BE6B44  MOV  R1,#26
00BE6B4C  BL   0x0058BA10          ; 旗 26 を下ろす
00BE6B58  BL   0x00237544          ; プレイヤー名の差し込み
```

要求の経路:
`sub_2388BC` `0x002388BC` → `sub_236B40` `0x00236B40`
→ `sub_5F30F8` `0x005F30F8`（アーカイブ FSS とラベル番号を要求スロットへ）
→ `sub_6019A4` `0x006019A4` が要求スロットを表示スロットへ複製
→ `sub_6012CC` `0x006012CC` がラベルを索引に解決して本文を流す。

★アーカイブは静的モジュールの **`.data`（seg2）からの匿名インポート**なので
`.code` を grep しても見つからない。実機で `0x00BE6F04 = 0x0094A6D4`（= `off_94A6D4`、
指す先が `"SYS_Save"`）を読んで裏を取った。
seg2 の基準は `0x0093F000`（3 件のインポートすべてが実機の値と一致）。

### 5. ★要求／表示スロットの構造 — 確定（HIGH）

script/talk マネージャ（`sub_6032E4` `0x006032E4` が構築）は 124 バイトの物体を 2 つ持つ:

- **`mgr+864` = 要求スロット**（誰かがここに書く）
- **`mgr+860` = 表示スロット**（`sub_6019A4` が要求スロットから複製し、要求側をリセット）

124 バイトの中身（`sub_6032E4` の構築順と `sub_60308C` のリセットで確定）:

| offset | 内容 |
|---|---|
| +0 | 種別（0=無 / 1=索引指定 / 2=ラベル番号指定 / 4=ラベル文字列指定 …） |
| +4 | 解決後の**索引**（`sub_6012CC` が `sub_159D80(mgr+812, これ)` で本文を引く） |
| +8 | **ラベル番号** |
| +12 | `sead::FixedSafeString<8>` = ラベル文字列（`"002"` 等） |
| +32 | `sead::FixedSafeString<32>` = アーカイブ名（`"SYS_Save"` 等） |
| +76 | `script::WordFix<9>`（名前の差し込み） |
| +120 / +121 | バイト |

**実機で「準備しています」表示中に読んだ値**（2026-09-08）:

```
mgr = 0x330A39F0
mgr+860 -> 0x330BA468   +0=7  +4=1  +8=2  ラベル="002"  アーカイブ="SYS_Save"
mgr+868 -> 0x330D955C   登録中のメッセージ物体（vtable 0x00BEB738 = CRO 側）
```

`+4 = 1` は **`SYS_Save.umsbt` の index 1** で、romfs 側の走査結果
（index 1 / ラベル 002 =「準備しています／電源ボタンに触らないでください」）と一致する。
**静的・動的・romfs の 3 系統が独立に同じ結論になった。**

### 6. ★しずえスキップのチートが飛ばしているもの — 確定

F-361 のチートは case 1 の動作だけを実行するので、**case 0 が丸ごと走らない**。
利用者の観測「準備中のロードすら挟まらず村に出た」はこれで説明がつく。飛ばしているのは:

- `sub_2F9D3C` `0x002F9D3C` — 村セーブの欄の作り直し
- `sub_23CBB8` / `sub_27EB34` — 旗と `this+632` の初期化
- 旗 26 の上げ下げ（`sub_58B934` / `sub_58BA10`）
- **`sub_30C994` `0x0030C994` → `sub_30C9C4` `0x0030C9C4`** ← ★実害があるならここ
- `sub_237544` — 名前の差し込み

`sub_30C9C4` は `byte_956231` で **boot 中 1 回だけ**走る一括処理で、
村セーブ + プレイヤー 10 人分（`+= 9496`）× 所持枠 16（`242 * j`）を回り、
`ItemToPlace`（`0x00955FF4`）の品を `sub_30D04C` / `sub_30D894` で配置し、
`sub_10D980` / `sub_110CFC` / `sub_10FF58` / `sub_10DBA0` / `sub_10CCB8` / `sub_110668`
を村セーブに対して実行する。

→ **チートは「起動時のセーブ」だけでなく、この一括処理も飛ばしている。**
   これが日付変更時の成長処理そのものかは**未確認**（`sub_10D980` 等の中身は未解析）。
