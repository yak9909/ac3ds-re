## F-344（2026-09-07）: ★手紙を開くと落ちる — 借用が nw::lyt ヒープを枯らしていた

**confidence: HIGH**（実機の停止位置・レジスタ・オブジェクトの中身 + 逆アセンブルの双方）
★**今回の変更（F-342 / F-343）が原因ではない。** 借用 `0x6C000` は F-325 からの値で、
  手紙を開く経路がこれまで一度も踏まれていなかっただけ。

### 止まった場所

```
PC = 0x00535A10   sub_535A08 の 3 命令目   LDR R3,[R2,#0x28]!   R2 = 0
  sub_535A08:  R2 = *(R0 + 8);  LDR R3,[R2,#0x28]!    ← +8 が null なら即死
呼び出し元 sub_1FC55C 0x001FC5E4:  R0 = R4 + 0x1BBC = item::ResLoader
```

`R7 = 0x33132CD4` の vtable `0x008FDC84` -> TypeInfo `0x008CA428` -> **`N4item9ResLoaderE`**。

### 何が起きたか（実機の値）

`item::ResLoader` の非同期読み込み器（`ResLoader + 0x1C`）を読むと:

| 欄 | 値 | 意味 |
|---|---|---|
| `+232` | **4** | 状態。3/4/5 は「終わった」 |
| `+68` が指す文字列 | **`Item/Model/letter_shic.bcres`** | 読もうとしたファイル |
| `+204` | **`0x32C45F78`** | ★**nw::lyt の `sead::ExpHeap` そのもの** |
| `+220` | **`0x20180` = 131,456 B** | 要求した大きさ |
| `+228` | `0x80` | 整列 |
| `ResLoader + 0xEC` | **0** | ★取れたバッファ = **null** |

**状態は「終わった」なのにバッファが null** = **確保に失敗した**。

そのとき `probe_lyt_heap.py`:

```
総量 3,866,624 B / 使用中 3,818,988 (98.8%) / 空き 47,636 B (1.2%) / 空きブロック 1 個
```

**131,456 B 要求に対して 47,636 B しかない（83,820 B 不足）。**

### なぜ落ちるのか（ゲーム側が結果を見ていない）

```
sub_536038: ... result = sub_4ED828(a1);  if (result) { ...; return 1; }  return result;  // 0
sub_4ED828: v2 = 非同期の完了判定;  if (v2 && !a1[1]) { a1[1] = a1[2] = a1[59]; }  // a1[59] = null
sub_1FC55C 0x001FC5D8: BL sub_536038      ← ★戻り値を捨てている
           0x001FC5E4: BL sub_535A08      ← そのまま +8 を参照して死ぬ
```

**確保に失敗しても止めてくれない。** 借りすぎるとこの形で落ちる。

### ★教訓

- **`g_GfxAllocator` 以外のヒープでも「確保できたか」を誰も見ていない**経路がある。
  借りっぱなしにすると、こちらが触っていない機能が落ちる。
- 借用量は「起動直後の空き 1,331,224 B」ではなく
  **一番きつい場面の空き（手紙で 490,004 B）**で決めること。
