## F-314: F-313 の裏取り。1 件は誤り、2 件は独立に裏付けが取れた — HIGH

> 「決め付けず裏取りする」ため、F-313 の結論を他の点・他のプログラムと突き合わせた。

### ★誤りが 1 件見つかった — `LIST_SIZE` は**別のヒープ**から取る

F-313 D は「借用 0x50000 + LIST 0x10000x2 = 426,032 B → ゲームへ 312,844 B 残る」
と書いたが、**`LIST_SIZE` を nw::lyt ヒープの予算から引いていた。これが誤り。**

経路を最後まで辿った:

```
sub_121988(size, qCount)              = nngxCmdlistStorage
  -> off_96EAA4 (実機ダンプで 0x00120A18)
     ★sub_120A18 は STR R3,[SP] で size を 5 番目の引数へ積む
       （decompiler は引数を落とす。F-164 と同じ罠。assembly を見た）
  -> *(0x0096F304) の vtable+0x08
     = graphic::MemoryMgr（RTTI `N7graphic9MemoryMgrE`、vtable 0x00904FA4）
  -> sub_6165A8: 分類 0x10000 なら **this+0x14 の器の vtable+0x18** を (size, 16) で呼ぶ
  -> this+0x14 = sead::ExpHeap
```

実機で読んだ 3 つのヒープ（すべて `sead::ExpHeap`）:

| 用途 | heap | 総量 | 空き |
|---|---|---|---|
| **nw::lyt**（自前 GUI が借りる） | `0x32C45F78` | 3,866,624 | 1,331,224 (34.4%) |
| **nngx**（`LIST_SIZE` の出どころ） | `0x3228A7C8` | **7,008,256** | **1,220,172 (17.4%)** |
| `g_GfxAllocator` | `0x329A4778` | 235,520 | 23,160 |

→ **2 つは別のヒープ。予算は独立に数える。**

| | |
|---|---|
| nw::lyt 側 | 借用 `0x50000` → 最悪時にゲームへ **411,180 B** 残る（F-310 の 738,876 から） |
| nngx 側 | LIST 上 `0x10000` + 下 `0x8000` = 98,336 B。空き 1,220,172 の **8.1%** |
| 現行からの増加 | `0x8000` x2 = 65,568 → 98,336。**増分はわずか 32,768 B** |

★`graphic::MemoryMgr` は先頭に別の `ExpHeap`（`+0x30`、総量 `0x7800`）も持つが、
  そちらは使い切られており（空き 0 個 / 使用中 2）、分類 0x10000 では使われない。
  **「MemoryMgr の中の最初のヒープ」を見て早合点しないこと。**

### ★裏付けが取れた 1 — `LIST_SIZE = 0x10000` は**実機で確保に成功した実績がある**

`RE/FINDINGS.md` の F-283/F-284 に記録があった。

> `/CTRPF_OwnGui.txt` は `上ノード list=41 記録長=1072 バイト` /
> `下ノード list=42 記録長=1072 バイト` を記録している。
> **組み込み直後は両画面ともコマンドリストを作れて記録もできていた**ので、
> 「`LIST_SIZE = 0x10000` が大きすぎて `nngxCmdlistStorage` の確保に失敗した」
> という前セッションの最有力仮説は**誤り**。

F-286 で `0x8000` へ戻したのは **F-282 への全面巻き戻しの一部**であって、
`0x10000` が失敗したからではない。

→ **静的解析（ゲーム自身が 0x10000/0x18000 を使う）と実機の実績が一致した。**

### ★裏付けが取れた 2 — 1 文字あたりの式が実測と 4% で一致

`RE/FINDINGS.md` の**別々の行**にある記録長を突き合わせた。

| 構成 | 記録長 |
|---|---|
| 上 74 枚 / 文字 0 | `0x38D0` = 14,544 B |
| 下 110 枚 / 文字 0 | `0x5580` = 21,888 B |
| 下 110 枚 / 自前フォント 17 字 | `0x5B00` = 23,296 B |

```
Picture 1 枚 = (0x5580 - 0x38D0) / (110 - 74) = 204.0 B
文字 17 字   = 0x5B00 - 0x5580 = 1,408 B  (82.8 B/字)
```

F-313 の式（`sub_4D6CE0` の語数）は 17 字・1 色で **338 語 = 1,352 B**。
実測 1,408 B との差は **−56 B（−4.0%）**。**独立した 2 つの結果が一致した。**

★F-308 が使っていた「Picture 199 B / 文字 83 B」は近い値だが、
  上の差分から取り直すと **Picture 204 B / 文字 82.8 B**。以後はこちらを使う。

★**v1 の「1 枚あたり約 127 バイト」と混同しない。**
  あれは自前ケーブのスプライト表の値で、`nw::lyt::Picture` とは別の機構。

### ★副産物 — 2 フォントを 1 枚のシートに置くとマテリアルの切り替えが起きない

`sub_4D6570` の群分けは **`*(字形の記述子 + 8)` の値**（= 物理アドレス >> 3）で行う。
F-312 で美咲と PixelMplus を**同じシート**に置いたので、
記述子は別でも `+8` の値は同じ → **群の切り替えが 1 度も起きない。**
文字列ごとに 12 語の状態ブロックを吐く必要が無くなる。

### 検算した走査の健全性

`BL 0x5685A4` の直前から R3 を拾う走査について、`0x18000` / `0x10000` / `0x11000` の
3 箇所を objdump で逆アセンブルし、
**間に R3 を壊す命令も分岐先も無い**ことを確認した（`MOV R3,#imm` の 3〜5 命令後に `BL`）。

### まだ確定していないこと

- **nngx ヒープの場面ごとの最小空き。** いまの 1,220,172 B は 1 場面の値で、
  F-310 で nw::lyt に対してやったのと同じ場面またぎの計測をしていない。
  ただし**増分は 32,768 B** と小さく、ゲーム自身が単発で `0x18000` を取るヒープなので、
  優先度は低い。測るなら `PATCHES/sample_lyt_heap.py` に nngx 側を足す。
