## F-287 (HIGH) — ★明滅と「文字が板になる」の真因は **観測リングが自前 TEV を毎フレーム潰していた**こと

F-283 の「真っ黒」、F-285 の「板＋明滅」、F-286（F-282 へ巻き戻したもの）の
「明滅」は**すべて同じ原因**だった。

### 決定的な観測（実機・記録されたコマンド列を直読み）

`LOG_CURIN`(LOG+0xD0) が下画面ノードの記録開始カーソル。そこから記録長ぶんを
吸い出して PICA として解読したところ、**先頭 144 バイトがコマンドではなくゴミ**だった。

```
0x327F2380: 00000410 327EA150 327EDC00 32C4CBCC 00003AB0 ...   ← ゴミ 144 バイト
0x327F2410: 00000100 0002006F   ← ここからやっと正しい（reg 0x06F mask2）
0x327F2418: 00011001 000B0080   ← reg 0x080 maskB
0x327F2428: 00800080 000F0082   ← テクスチャ 128x128
0x327F2438: 0453B0A0 000F0085 / 00000009 000F008E
```

そのゴミは `MATCMD`（自前 TEV 36 語の置き場）から丸ごと写されたもので、
**MATCMD の実体と 144/144 バイト一致**した。MATCMD には TEV が入っていなかった。

```
MATCMD 実際 : 00000410 327EA150 327EDC00 32C4CBCC 00003AB0 00000000
MATCMD 期待 : 00300030 804F00C0 00000000 00010001 FFFFFFFF 00000000
```

### 真因

`build_q` の観測リング書き込みは `AND R3,R2,#15` / `ADD R12,R12,R3,LSL#5` なので
**16 件 x 32 バイト = `0x200` バイト**を使う。原本（`cave_node_draw.py` 系。F-283 以前）は

```
MATBUF 0x9B5600 (0x100) / RING 0x9B5800 (0x200) / MATCMD 0x9B5A00 (0x400)
```

だったが、**F-283 で `.bss` を組み直したとき RING と MATCMD を 0x100 間隔に詰めた**
（`0x9BD800` / `0x9BD900`）。F-286 の巻き戻しでも同じ 0x100 間隔を再現してしまった。

→ **リングが MATCMD の先頭 0x100 を毎フレーム上書き**し、自前 TEV 36 語（0x90）が消える。
→ 記録列の先頭に**毎フレーム内容が変わるゴミ**が PICA コマンドとして積まれる。
   先頭語のヘッダ `0x327EA150` は reg=0xA150（存在しないレジスタ）/ extra=0x7E なので、
   **GPU が無効レジスタへ大量の語を書き込む**。TEV は一度も設定されない。

- **TEV 未設定** → テクスチャが合成されず四角形がベタで出る = **「文字が板」**
- **ゴミが毎フレーム変わる** → GPU 状態が毎フレーム変わる = **「白／黒に明滅」**

### なぜ検査をすり抜けたか

`_check_layout()` の `.bss` 重なり検査が **RING の大きさを `0x80` と書いていた**（実際は `0x200`）。
デバッガ側の初期化は 128 語 = `0x200` で正しく、`OwnGui.cpp` は `0x80`。
**同じ数値が 3 箇所にあり、2 箇所が古かった。**

### 直したもの

| ファイル | 変更 |
|---|---|
| `PATCHES/cave_node_record.py` | `RING 0x9B5700→0x9B5800` / `MATCMD 0x9B5800→0x9B5A00`（原本と同じ） |
| 同 `_check_layout()` | `("RING", RING, 0x80)` → **`0x200`**。以後この重なりは必ず検出される |
| `Sources/OwnGui.cpp` | `ZeroBss(kGuiRing, 0x80)` → **`0x200`** |
| `includes/GuiCaves.h` | 再生成（`kGuiRing = 0x009B5800` / `kGuiMatCmd = 0x009B5A00`） |

`.bss` 終端は `0x9B5E00`。`TABLE_TOP` 終端 `0x9B5000` と重ならない。

### 実機での裏取り

Suspend 中のプロセスで、ケーブ内のリテラル `0x008387B0`（RING）を `0x009B5C00` へ移し、
`0x9B5800` へ自前 TEV 36 語を書き戻した。**再開後に明滅と「板」が消えれば確定。**

### この件で確認できた「原因ではないもの」

フック 3 本・ケーブ全 580 語（不一致 0・残骸 0）・確保フックの復元・アトラスの実体・
テクスチャ番地・LOG のチャンク数（上 17 / 下 4）・vtable・投影行列（-2/400, -2/320）・
記録長（TOP 0x3AB0 / BOT 0x0E70、`LIST_SIZE=0x8000` 内）— **すべて設計どおり**。

### 教訓

- **同じ数値を 2 箇所に書いたら、片方から生成するか検査で突き合わせる。**
- `.bss` を動かすときは各領域の**実際の使用量を実装から読む**。コメントは正しかったのに検査だけ古かった。
- 「巻き戻した」つもりでも、**巻き戻し先の値を記録から取らず推定した箇所**がバグを持ち込む。

詳細は `scratchpad/MEMO_f287_ring_matcmd.md`。

### F-287 追記 — 実機で復旧を確認し、**基準版として固定した**

利用者が実機で「直りました」と確認（2026-09-04）。明滅も「文字が板」も消えた。
これで F-287 の診断（リングが `MATCMD` の自前 TEV を毎フレーム潰していた）は**確定**。

この版を `BASELINE/gui_render_ok_f287/` へ**基準版**として保存した。

- 21 ファイル（生成器・検査器・プラグインのソース・ヘッダ・`.3gx`・当時の検査出力）
- `MANIFEST.sha256` に全ファイルの SHA-256
- **`README.md` に描画の基準仕様を全部書いた**
  （`.text` ケーブ配置 / `.bss` 配置と F-287 の罠 / ノードの契約 /
  表の書式と座標系 / フォント / **記録列に必ず入っていなければならない並び** /
  実行時に差し替える 2 語 / 取り外しの順序 / 必ず通す検査 7 本）
- `PATCHES/verify_baseline.py` で差分検出と復元（`--restore`）ができる

**記録列の正しい先頭**（壊れたときの判定に使う）:

```
自前 TEV 36 語（先頭 00300030 804F00C0 …）  ← ここが違えば TEV が潰されている
00000100 0002006F   reg 0x06F mask2
00011001 000B0080   reg 0x080 maskB
00011001 00040080   reg 0x080 mask4
00800080 000F0082   テクスチャ 128x128
00000000 000F0083 / 0453B0A0 000F0085 / 00000009 000F008E
```

**壊れたときの調べ方**: `LOG+0xD0`(`LOG_CURIN`) が最後の記録の開始カーソル。
そこから `ノード+0x108`（記録長）ぶんを吸い出し、先頭 144 バイトが
`MATCMD` と一致していて TEV でないなら **`MATCMD` が誰かに潰されている**。
