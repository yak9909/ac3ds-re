## F-309: nw::lyt のヒープは `sead::ExpHeap`。残量は 1,200,132 バイト — HIGH

> F-308 の残件（実残量が未確定）の解決。**推測ではなく取得子の逆アセンブルで確定**した。

### A. 正体

`*(0x0096F150)` はアロケータ（`ssys::ma::Allocator`）で、その **`+0x04` が本体のヒープ**。
そのヒープの vtable は `0x008FFEF8`、RTTI 名は **`N4sead7ExpHeapE` = `sead::ExpHeap`**。
（`vtable-4` → TypeInfo `0x008CB438` → `+4` → マングル名。F-43 の手順）

同居する `0x008FEC38 = sead::CriticalSection`（`heap+0x54`）とも整合する。

★注意: `sub_4B8CF0` が呼ぶ `vtable+0x08` は**アロケータ側**の slot 2 であって、
**ExpHeap の slot 2 は `isDerivedFrom`**（`0x74DCF8`）。別クラスなので矛盾しない。

### B. vtable から確定した欄（すべて取得子の逆アセンブル）

| slot | +off | 関数 | 内容 |
|---|---|---|---|
| 12 | +0x30 | `0x74D85C` | `getStartAddress()` = `*(heap+0x1C)` |
| 13 | +0x34 | `0x74D84C` | `getEndAddress()` = `*(heap+0x20) + *(heap+0x1C)` |
| 14 | +0x38 | `0x74DE08` | `getSize()` = `*(heap+0x20)` |
| 15 | +0x3C | `0x74D744` | **`getFreeSize()`** — 自由リストを歩いて `*(node+0x0C)` を合計 |
| 16 | +0x40 | `0x74D8B0` | **`getMaxAllocatableSize(align)`** — 最大の空きブロック − 整列詰め |
| 22 | +0x58 | `0x74DE10` | `dump()` — **`use_list_size = *(heap+0x90)` / `free_list_size = *(heap+0x80)` と印字**しており、欄名がそのまま取れる |
| 26 | +0x68 | `0x74D83C` | 割り当て方式（Best Fit / First Fit）。`dump()` が文字列で出す |

`sead::OffsetList` の並び（`dump()` の印字位置と `getFreeSize()` の走査で確定）:

| off | 内容 |
|---|---|
| `+0x1C` | 領域先頭（= **ヒープ自身の番地**。ヘッダが自分の領域の先頭に載る） |
| `+0x20` | 総量 |
| `+0x78` / `+0x7C` | 自由リストの番兵 prev / next |
| `+0x80` | 自由ブロック数 |
| `+0x84` | リンクのオフセット補正（bias） |
| `+0x88` / `+0x8C` | 使用中リストの番兵 prev / next |
| `+0x90` | 使用中ブロック数 |

ブロックヘッダは **16 バイト**、`+0x04` = next（bias 付き）、`+0x0A` = 整列の前詰め、
**`+0x0C` = ペイロードの大きさ**。

### C. 実測（2026-09-06、実機）

```
heap = 0x32C45F78 (= 領域先頭)   総量 0x3B0000 (3,866,624 B, 3.69 MB)
末尾 = 0x32FF5F78
使用中 2,666,492 B (69.0%) / 空き 1,200,132 B (31.0%)
free.count = 1   ← 空きブロックはただ 1 個（断片化なし）
use.count  = 2783
```

**`getFreeSize()` = `0x125004` = 1,200,132 バイト (1.14 MB)。**
空きが 1 個なので `getMaxAllocatableSize` も同値＝**1 回の Alloc でこれだけ取れる**。

#### 独立した 2 つの結果が一致（CLAUDE.md の要求）

1. **slot 15 の算法を写経して自由リストを歩く** → `0x125004`
2. **領域末尾からの引き算** `0x32FF5F78 − 0x32ED0F64 − 16` → `0x125004`

さらに鎖の整合も取れた:
- `heap+0x88`（使用中リストの末尾）= `0x32EB0F50` = **我々が借りたブロックのヘッダ**
- そのヘッダ `+0x0C = 0x20004`（要求 `0x20000` より 4 バイト大きい。端数を吸っている）
- `0x32EB0F50 + 16 + 0x20004 = 0x32ED0F64` = **次の空きノードの先頭と一致**

**同じ場面のまま** 4 秒走らせて再測しても `free.count` / `use.count` / `getFreeSize` は
**完全に同一**だった。★これは「同一場面で安定している」ことしか示さない。
  **放置しただけでは場面もゲーム状態も変わらない**ので、場面変化への耐性の証拠にはならない。

### D. 使える量（F-308 の天井を書き直す）

| 予算 | バイト | 最大文字数 |
|---|---|---|
| いま借りている `0x20000` のまま | 131,076 | 318 |
| 空き全部を追加で借りる | 1,200,132 | 3,320 |
| 返して借り直す（空き＋現借用） | 1,331,208 | 3,688 |
| 空きの 50%（安全側） | 600,066 | 1,635 |
| 空きの 25%（さらに安全側） | 300,033 | 792 |

**F-308 で「借用 0x20000 を超える」とした 400／800／1200 文字は、いずれも空きに十分収まる。**

| 文字数 | 必要量 | 空き比 |
|---|---|---|
| 400 | 160,144 | 13.3% |
| 800 | 302,592 | 25.2% |
| 1200 | 445,040 | 37.1% |
| 3000 | 1,086,064 | 90.5% |

記録コマンドリストも同じヒープから借りるなら（上下 2 本ぶん）:

| `LIST_SIZE` | 文字数(Pic40枚) | 2 本の費用 | 空き比 |
|---|---|---|---|
| 0x8000 | 298 | 65,568 | 5.5% |
| 0x10000 | 693 | 131,104 | 10.9% |
| 0x20000 | 1,483 | 262,176 | 21.8% |
| 0x40000 | 3,062 | 524,320 | 43.7% |

**1,200 文字を実際に出す構成**（バッチ 445,040 + `LIST_SIZE=0x20000` を上下 2 本 262,176）
= **707,216 バイト＝空きの 58.9%**。収まるが、**ヒープの残り 4 割で
ゲーム自身のレイアウト確保をまかなうことになる**。

### E. 結論と注意

- **1,200 文字規模までは容量の問題は無い。** F-308 で懸念した借用量の壁は消えた。
- **ただし「全部取る」はしてはいけない。** 空きが 1 個しかないので、
  取り切るとゲームの次の `nw::lyt` 確保が失敗する。
- 4 秒の再測では空きが 1 バイトも動かなかったが、**これは同一場面での 2 点にすぎない。**
  走らせて放置しただけでは場面は変わらないので、**場面変化への耐性は測れていない。**
  建物に入る・地図を開く等ではレイアウトを確保する可能性があり、そこは**完全に未測定**。
  **場面をまたいで最小の空きを測ってから予算を決めること**（測り方は F-309 C の手順そのまま）。
  ★これには**利用者に操作を頼む必要がある**。こちらから場面を変える手段は無い。
