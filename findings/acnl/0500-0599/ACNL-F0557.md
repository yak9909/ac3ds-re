## IDA-unknown-F025: 過去の静的解析の誤り 2 件と見落とし 1 件（2026-09-18、HIGH）

自前の UnitCursor が「描画経路のふるいを全部通るのに画素が 1 つも出ない」という実機結果を受けて、記録済みの静的結論を洗い直した。3 件の瑕疵が見つかった。

**(1) 読み込み状態の番地が 28 バイトずれていた（誤り。HIGH）**。IDA-unknown-F021 と設計書 §3.2 は「ホルダ +232 が読み込み状態」としていたが、G3dResHolder_RequestLoad 0x317920 は `FileRes_RequestLoadAligned(a1 + 7語, ...)` と呼び、FileRes_RequestLoadAligned 0x569D94 はその第1引数を素通しで FileRes_RequestLoadAsync 0x569BA0 に渡す。つまり **FileRes 部分は holder+28 から始まる**。正しい対応は holder+96=パス、holder+232=ヒープ、holder+256=アライン、**holder+260=状態**、holder+261=非同期旗、**holder+236=読み込んだ資源の先頭**（完了時に holder+4 と holder+8 へ複写）。実機で holder+232 を読むと 0xC0 で 0..5 のどれでもなく、独立な 2 経路で一致した。ホルダ 264 B という IDA-unknown-F023 の値自体は holder+261 まで収まるので矛盾しない。

**(2) メッシュの GPU コマンド列は 2 本あるのに 1 本しか見ていなかった（見落とし。HIGH）**。sub_4957C4 0x4957C4 が `Mem_CopyBytes(g_GpuCmdPtr, *(mesh+96), *(mesh+100))` で**頂点属性・バッファ束縛のコマンド列**を流し、続けて mesh+48 から 48 バイトの埋め込みブロックを流し、mesh+44 のビット 0/1 で描画コンテキスト +20 の 0x80/0x100 を上げ下げする。sub_48D26C が末尾で流す mesh+0x68/+0x6C は**2 本目（描画コマンド）**にすぎない。IDA-unknown-F024 で sub_48D26C を読んだとき、この前段の呼び出しを追わずに「描画状態は MTOB の PICA 列」とだけ結論したのが漏れ。なお UnitCursor.bcres を走査すると 0x0200〜0x0230（属性バッファ系レジスタ）のコマンドが 1 つも無いので、**1 本目は実行時に組み立てられる**。組み立てるのはモデル生成側なので、生成が途中で打ち切られるとマテリアルだけ正常でジオメトリのコマンドが欠ける状態になりうる。

**(3) ModelInstance_Create の成功判定が不十分だった（訂正。HIGH、実機で確認）**。IDA-unknown-F007 は「戻り値 1 でも holder+4 が null のことがあるので両方見よ」としていたが、実際は**戻り値 1 かつ holder+4 も非 0 のまま半壊する**。ヒープが足りないと sub_4A9A04 の内部ビルダが負を返して打ち切られ、**MaterialActivator を作るブロックに到達せず model+0x1EC が 0 のまま**になる。その状態で描くと 0x494C18 の `LDR R2,[R0]` で NULL 参照する。したがって **model+0x1EC が非 0 であることまで確認する**必要がある。あわせて**資源用ヒープとインスタンス用ヒープは分ける**こと: ゲームの "UnitCursorRes"（20,480 B）は資源専用で、16,256 B の bcres を読むと約 4 KB しか残らず 3,064 B のインスタンスが静かに半壊する。IDA-unknown-F011 の 3,064 B は「インスタンス単体」の値であって「これだけ確保すれば足りる」ではない。

**この因果は当初は未検証の推定だった（実験も「新しいヒープにした」と「大きくした」を同時に変えていた）ので、あとから静的に裏を取った。**
sub_4A9A04 が呼ぶ内部ビルダ 9 本（sub_4976FC / sub_4A9C50 / sub_4B28D4 / sub_4AA0BC / sub_4AAEB8 / sub_4A9EAC / sub_4AA644 /
sub_4B2CF8 / sub_4B2E34）を機械的に走査し、0x80000000 を立てる全 28 箇所を確認したところ、**例外なくアロケータの vtable+8（Alloc）が
null を返したときだけ**（または 2 つ目の確保に失敗して 1 つ目を vtable+0x0C で解放する後始末のとき）だった。他関数の戻り値で判定していた
2 箇所（sub_4AF068 / sub_4B15E0）も中身は確保のみで、**データ不正や非対応形式で失敗する経路は存在しない**。
よって「負の戻り値 ⇒ 渡したアロケータが要求を満たせなかった」は確定。

ただし**「総バイト数が足りない」とは限らない**: 確保の多くは `(4*n, 32)` のように**整列 32** を要求するので、
断片化した／ほぼ満杯のヒープでは空きバイト数が要求を上回っていても失敗しうる。4,224 B 空きで 3,064 B が作れなかったのはこれで説明がつく。
正しい言い方は「**アロケータが要求（大きさ＋整列）を満たせなかった**」であり、「確保量が足りなかった」と断定するのは不正確だった。

**あわせて確認して問題が無かったもの**: G3dResHolder_Setup の第2引数はアロケータ物体（生ヒープではない。読み込み側は生ヒープなので取り違えやすい）。ModelInstance_Create の a3/a4 もアロケータ物体（IDA-unknown-F010 のとおり。ただし設計書 §7.2 の表に載っていなかったので追記）。sub_58EEC0 が生成直後に呼ぶ sub_4F05F4 / sub_4EC83C は副作用のない型チェック付きキャストで、設計書の手順に抜けは無い。Field_TileToWorld の `32×マス+16` は実機で拾った描画中モデルの平行移動 x=2607.82≒81×32+16 と一致。

**意味未確定として残すもの**: G3dResHolder_Setup が holder+12 に入れる値の bit31（実機で 0x80000002）。sub_4A5A74 は各資源項目の結果を OR で畳むだけで、Setup 自身は bit1 しか見ない。以前「失敗フラグではない（ヒープを増やしても同じ）」と書いたが、これは両方失敗している可能性を排除できておらず根拠として弱い。**断定を取り下げる**。

反証条件: FileRes 部分が holder+28 以外から始まる、mesh+96 の列が実行時ではなくファイル由来である、あるいは model+0x1EC が 0 のままでも描画できる実例がある。根拠 docs/topics/unit_cursor_outdoor.md §3.2/§7.2/§11、IDB コメント（0x569BA0 / 0x317920 / 0x4957C4 / 0x4F048C）。
