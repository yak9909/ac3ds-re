## IDA-unknown-F026: メッシュのコマンド列は誰が作るか。「ジオメトリが欠けている」仮説の反証（2026-09-18、HIGH、静的）

IDA-unknown-F025 で「メッシュの GPU コマンド列は 2 本ある」と分かったので、1 本目（頂点属性・バッファ束縛）の出どころを追った。

**(1) 資源側のモデル setup は空**。G3dResHolder_Setup → sub_4A5A74 は各 CMDL に sub_4A693C を呼び、そこは型タグ 0x80000000 / 0x40000000 で off_96F0F4 / off_96F0F8 の関数ポインタへ分岐する。この 2 つの値は .data の初期値で **0x004A6934 と 0x004A7254、どちらも `return 0` のスタブ**（書き換えるコードは存在しない）。よって**このビルドでは資源側のモデル setup は実質何もしない**。テクスチャ等は別の pass（sub_4A8FC8 ほか）が処理する。

**(2) 2 本とも作るのは sub_4A8B44（インスタンス生成側）**。`v28 = sub_4B14CC(mesh, desc)`（属性列の大きさ）と `v56 = sub_4B1540(mesh, desc)`（描画列の大きさ）を求め、**渡されたアロケータから 1 回だけ `v28+v56` を確保**し、sub_7E5710 で前半（属性）、sub_4B12C0 で後半（描画）を埋める。そのうえで **mesh+96=確保先頭 / mesh+100=v28 / mesh+104=先頭+v28 / mesh+108=v56 / mesh+128=アロケータ** をまとめて書く。sub_4B12C0 が書く語（0x76543210、0x801F02BB、0xBA98、`(3n+517)|0xF0000`＝0x000F0205、0x803F0232）は実機で読んだ 56 バイトの列と一字一句一致するので、対応は確実。

**(3) よって「ジオメトリのコマンドが欠けている」は成り立たない（自説の反証）**。2 本は同じ確保の前半・後半で、4 つの欄は同時に書かれる。実機で mesh+0x68=0x30FD1D54 / +0x6C=56 が有効だった以上、**mesh+0x60 も必ず有効**である。さらに sub_4B14CC は v2=12 から始めて属性ごとに +4〜+6、条件付きで +4 して `4*v2` を返すので、**最小でも 48 バイトで 0 にはならない**。IDA-unknown-F025 の末尾に書いた「次に mesh+0x60 を確認せよ」は、確認するまでもなく存在すると結論できる。

**(4) 付随して分かった注意点**: sub_4A8B44 は **常に 0 を返す**ので失敗を上位へ報告できず、確保結果の null 検査も無い（null なら低位番地へ書いて落ちるはずで、落ちていない以上は確保成功）。また **ワールド行列は node+188(0xBC)**、局所行列は node+76(0x4C)、**親は node+12** で、親が null なら sub_49F648 の単位元が使われる（sub_4EF69C）。したがって**親を持たない自前ノードでもワールド行列は正当に計算される**。

**残る候補**: 1 本目の中身は `desc`（材質から解決される頂点属性の対応表。v14+644 → sub_4A93A8 → +44 の配列を v14+652 で引く）に依存し、属性ごとに `desc[index+76] >= 0` で採否が決まる。ここが噛み合っていなければ属性が 1 つも出力されず、コマンド列は存在するのに描けない、という状態はありうる。次はここを読む。

反証条件: off_96F0F4 / off_96F0F8 が実行時に書き換えられている、sub_4A8B44 以外にも mesh+96 を書く経路がある、または sub_4B14CC が 0 を返す入力が存在する。根拠 IDB コメント（0x4A8B44 / 0x4B14CC / 0x4A693C / 0x4EF69C）。
