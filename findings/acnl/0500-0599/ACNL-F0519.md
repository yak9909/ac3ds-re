## IDA-opus-5.5-F012: 建物ごとのモデルはゲームのデータから集められる。写しの置き場は gohan 自身のメモリでよい（2026-09-23、HIGH（静的＋実機））

解析ソフト: IDA / 解析モデル: opus-5.5。利用者の依頼「建物ごとの対応表を自前で用意せず、ゲーム内から取得できないか」「写しの置き場を調査」。

### 1. 建物 → モデルの集め方（ゲームのデータだけで）

1. **建物表のスロット → 実体**: BsStrcMgr の一覧（F004）から建物 id（実体 +0x66）と位置（+0x14）で照合
2. **実体 → 子プロセス**: 基本マネージャ `*(0x96F2A4)` のスロット（1 つ 20 B: +0 プロセス、+4 親ノード、**+8 最初の子**、**+16 次の兄弟**。
   `UiScreen_RequestDestroyRecursive` が同じ読み方）。プレイヤー 1 の家の最初の子 = **AcStrcPost（ポスト）**
3. **各オブジェクトの範囲 = ヒープの見出しの大きさ**: 実体の手前 16 B の **+0xC がブロックの大きさ**
   （街灯 0x254 = 生成関数の `new(0x254)` と一致、家 0x5DC、ポスト 0x48C、hobj::Tent 0x30C）
4. **範囲内のモデル参照を集める**: RTTI が `nw::gfx::Model` / `SkeletalModel` の参照。範囲内から参照される `hobj::`（家の外観部品）の
   オブジェクトはその範囲も見る（テントは家の持つヒープの中には無く、ヒープの包含では決められなかった）

実機の結果: この規則で集まるのは 街灯（+0x90）、家（+0x2FC、柵）、hobj::Tent（+0x274、テント本体）、ポスト（+0x2FC）。
これだけを変えると**テント・柵・ポスト・街灯がすべて青**（`multi4_b0.png`）、restore で元どおり（`multi4_restored.png`、23 か所一致）。

**F011 の訂正**: F011 round 2/3 で「家の実体」として変えた +0xB28 / +0xBD8 / +0x11C0 は、家のブロック（0x5DC）の外で、
**直後の住民の家 0x0B（0x3311E5C0）のモデル**だった（画面外で気付かなかった）。柵は家 +0x2FC のモデル。

### 2. 写しの置き場

汎用の書き出し `gfx_MaterialActivator_Activate 0x49C08C` は TEV ブロック・色の表を **CPU で読んで値を GPU コマンドへコピーする**だけ
（`Copy24Bytes(g_GpuCmdPtr, …)`）。vtable の写しも CPU が読むだけ。**GPU が写しのメモリを直接参照することはない**。
→ 置き場は **gohan プラグインの静的な配列でよい**（ゲームのヒープは借りない）。戻したあとは次の書き出しから元のポインタが使われるので、
写しはすぐ手放してよい。場面が切り替わって実体が消えたときは、戻す前に実体が生きているか（プロセスのスロットと vtable）を確かめること。
