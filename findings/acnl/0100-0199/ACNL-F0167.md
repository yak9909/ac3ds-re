## F-129: `TextBox+224` は `nw::font::ResFont*`。実機には少なくとも4種の初期化済みCFNUがある

confidence: **HIGH**（静的 Ctor / RTTI・vtable / 実機オブジェクト・CFNU ヘッダを照合）

### 1. `+224` の生成側を静的に確定

`nwlyt_TextBox_Ctor`(`0x4BB2A4`) は、TextBox リソース `+82` の font index から
フォント名を引き、ResourceAccessor の virtual `+12` で `nw::font::Font*` を取得し、
**戻り値を TextBox `+224` に保存する**（`0x4BB3B0`）。

実機で通常UIの `+224 = 0x3302ABE0` を辿ると vptr は
`vtbl_nw_font_ResFont`(`0x008FCAAC`) で、参照先リソース先頭は `CFNU`、
ブロックは `FINF` / `TGLP` だった。したがって「フォントらしい非0ポインタ」ではなく、
**実体は `nw::font::ResFont*`** と確定した。

### 2. 1 MiB に限定したヒープ走査で見つかった ResFont

`0x33000000-0x330FFFFF` だけを読み、`vtbl_nw_font_ResFont` を4バイト境界で探索した。
初期化済み4個と未初期化1個が見つかった。アドレスはこの起動だけの値。

| runtime | CFNU file size | FINF linefeed | FINF metric 20/21/22 | 実際の利用ペイン |
|---|---:|---:|---:|---|
| `0x3302ABE0` | `0x13C8D8` | 24 | 24 / 18 / 18 | 通常UI、時計、会話本文、アイテム名 |
| `0x3302AD78` | `0x1AE8` | 7 | 7 / 7 / 5 | `RT_msg_0` / `RS_msg_0` / `RT_meg_0` / `RS_meg_0` |
| `0x3302AF10` | `0x1904` | 40 | 40 / 35 / 29 | 調査したUI範囲では使用箱なし |
| `0x3302B0A8` | `0x2114` | 26 | 26 / 24 / 17 | `T_bell_0` / `T_count_` |

`0x3302AD78` は7pxのルビ用、`0x3302B0A8` はベル・個数表示用とみられる
（ペイン名と実際の割当から **MEDIUM**）。40px版の用途はまだ不明。

UIヒープも `0x32C00000-0x32DFFFFF` を1 MiBずつ2回に分けて走査した。
88個の live `TextBox` が見つかり、上記の通常・7px・26pxの3種類が実際に
`+224` へ割り当てられていた。既知の時計・住民名・会話本文・アイテム名は全て通常版で、
アイテム名の見た目の差は `+228/+232 = 16.2 x 21.6` による。

### 3. 最小差し替え試験（目視確認まで完了）

`PATCHES/textbox_font_swap.py` を作成し、時計本文 `T_time_0` 1枚だけの `+224` を
通常版から7px版へ変更した。影ペインと `+228/+232` は未変更。

- 書込み前後で TextBox vptr、ペイン名、両 ResFont vptr を検証
- `+254` bit0 を立て、`run_timed.py` で5秒走行
- 描画後も `+224 = 0x3302AD78` が維持され、更新bitは描画側により0へ戻った
- クラッシュなし、`PC = 0x00137064` で正常停止

ユーザーの目視では、本文の `06` が**ぼやけた「あ」に変化**し、少なくとも2行に
折り返されて2行になり、2行目はTextBox内でclipされず画面下端の外へ出た。
一方、影は元の **`06` のまま**だった（縦方向の訂正と根拠はF-131）。
これにより次を動的にも確定した。

- `TextBox+224` の差し替えだけで、実際に描画されるフォント本体が変わる
- 本文 `T_time_0` と影は別 `TextBox` であり、一方の `+224` は他方へ波及しない
- `+228/+232` を元の `18 x 24` のままにすると、7pxフォントは大きく拡大表示される

7px版が数字 `0` / `6` を持たず、両方が代替グリフ（おそらく「あ」）へ落ちた可能性が高い。
2文字が縦に見えたのも、代替グリフのadvanceが時計ペイン幅を超えて折り返されたためと
考えると整合する。ただし **CMAPと代替文字の直接確認前なので、この原因部分はMEDIUM**。

7px版は復元済み。続く切り分けとして、数字を実際に使うカウンター用26px版
`0x3302B0A8` を同じ本文だけへ適用し、5秒描画後も正常Suspend・ポインタ維持を確認した。
目視では本文が `07` と正しく1行表示された。字形の骨格は影と同じに見えるが本文には
黒い縁取りがあり、隣のminute `03` より少し左上へずれて見えた。

変更したのは `+224` だけなので、文字列バッファ容量、ペイン座標、`+228/+232`、materialは
未変更。したがって黒縁はカウンターフォント資源側の字形または描画情報に由来する。
位置差もバッファサイズ変更ではなく、フォント固有メトリクスと字形の可視範囲による。
試験後は通常フォント `0x3302ABE0` へ復元し、5秒描画後の更新bit消費まで確認した。
