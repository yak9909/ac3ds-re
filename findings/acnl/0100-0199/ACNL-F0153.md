## F-115: ★F-110〜F-114 の精査（TODO-75 の前の検証）— 誤り 2 件・過剰主張 3 件を訂正

confidence: **HIGH**（訂正内容はいずれも一次証拠で確認）

TODO-75（実際に描かせる）に進む前の全面精査。**誤りが 2 件、裏を取っていない主張が 3 件**あった。

### ★誤り 1 — F-114 ①の関数名が違う（実害あり）

F-114 で「既製ブロックを `Mem_Copy` で転送」と書いたが、
アセンブリが呼んでいるのは **`sub_12EC54`** であって `Mem_Copy`(`0x2FBB8C`) ではない。

```
28e8c8  MOV R0, R5
28e8cc  BL  sub_12EC54          ← ★こちら
```

`sub_12EC54` を読むと、サイズ 8 以下を完全展開したバイト粒度の memcpy だった。
**「ブロック転送」という意味づけは正しいが、関数は別。** `Mem_CopyBytes` と命名した。
`Mem_Copy`(`0x2FBB8C`, ワード粒度) を使うのは
`BsShadowViewMgr_BuildShadowCmds` の中のブロックコピーのほう。

**原因: 意味が同じだったので名前を確認せずに書いた。**

### ★誤り 2 — 配列の 4 番目の dword は「capacity」ではない

F-111 / F-112 で `+0x14` を「capacity」と書いたが、実際は

```
上位 2 bit = フラグ, 下位 30 bit = capacity
```

`Render_DrawSceneIndexed` / `nwgfx_SceneTraverser_VisitCamera` / `sub_49909C` /
`sub_498F20` / `sub_499518` の**5 箇所すべてが** `& 0x3FFFFFFF` と
`& 0xC0000000) != 0x40000000` で読み書きしている。
実機の `cap_raw = 0x00000400` は flags = 0 / capacity = 1024。

フラグ `0x40000000` は「この配列はアロケータから確保したもの（＝解放してよい）」の意味と
見られる（`MEDIUM`。再確保パスがこのフラグを見て初めて realloc する）。

### ★過剰主張 1 — 「どの Visit も配列 #0 に入れる」は当時未検証だった（→ いま検証して成立）

F-112 でそう書いたが、実際に読んでいたのは **2 本だけ**
（汎用 `0x499080` と Camera `0x498860`）。残り 4 本は未確認のまま一般化していた。

**今回 6 本すべて読んで成立を確認した。** ついでに埋め先も全部判明した。

| visitor slot | 関数 | 配列 #0 | 追加の配列 |
|---|---|---|---|
| `vtbl[4]` (+16) | `0x499080` | ✔ | なし |
| `vtbl[5]` (+20) | `0x49909C` | ✔ | **#1**（`ctx+24`） |
| `vtbl[6]` (+24) | `0x498800` | ✔ | **#2**（`ctx+40`, `sub_7E4A18` 経由）, #14 |
| `vtbl[7]` (+28) | `0x498F20` | ✔ | **#2**, **#3**（`ctx+56`）, #14 |
| `vtbl[8]` (+32) | `0x498860` | ✔ | **#4**（`ctx+72`）= カメラ, #14 |
| `vtbl[9]` (+36) | `0x499518` | ✔ | **#5**（`ctx+88`）, #14 |

#14（`ctx+232`）は `*(node+40)` が非 0 のときだけ。

**★F-112 で「配列 #5 は不明」としたが、埋め手は visitor `vtbl[9]`(`0x499518`)。**
`Render_DrawSceneIndexed` が `sub_4A41EC` で回すのがこれ。
どのノードクラスがどのスロットを使うかは未確定（TODO-66 に残す）。

### ★過剰主張 2 — 2 つの描画パスの実行順は推測だった（→ いま実測して成立）

F-113 で「`Frame_DrawPass1040` はこのあとに走る」と書いた根拠は
「末尾に `Render_FrameEnd` があるから」という**推測**だけだった。

実機で判定した。`Frame_DrawPass1040`(`0x1B72E4`) の**入口**で `SceneContext` を読む:

| | 1024 が先なら | 1040 が先なら | 実測 |
|---|---|---|---|
| ctx[0] の n | 非 0 | 0 | **24** |
| ctx[2] の n | 1（影ノード） | 0 | **1**（`0x30896104`） |

**1024 が先で確定。** ctx[1] は 0 件（`byte_94CA2C = 0` なので scene 1 は使われていない）。

### ★呼び出し元も判明 — sead の MethodTree

bp ヒット時の `LR = 0x543C6C` から `MethodTree_WalkAndInvoke`(`0x543C48`) を特定。

```
if (!(*(node+0x44) & 1)) { vptr = *(node+0x2C); fn = vptr[0]; fn(node + 0x2C); }
if (*(node+0x14) && !(*(node+0x44) & 2)) 子を再帰
```

**★ただし断定を避けた点がある。** `0x1B71C4` / `0x1B72E4` は
`.rodata` の `0x8E5858` / `0x8E585C` に並んでおり、これは
`vtbl_SystemTask`(`0x8E57F4`) の延長上（スロット 25 / 26 に相当）にある。
しかし呼び出し側は `*(node+0x2C)` を vptr として `slot 0` を呼んでいる。

- 「`SystemTask` の仮想関数で、デリゲートの `slot 0` は tail-jump する thunk」
- 「`0x8E5858` / `0x8E585C` がそれぞれデリゲートの vtable 基点」

**thunk の tail-jump なら `LR` は変わらないので、静的にはこの 2 つを区別できない。**
どちらでも F-113 の結論（何をするか・どの順か）は変わらないので、
**断定せず両論併記のままにする。**

### ★過剰主張 3 — 「実機で動いている唯一の FuncNode コールバック」

F-114 の表現。実際には **1 つの部屋・1 つの瞬間に ctx[2] を見ただけ**。
別のシーン・別の部屋に他の `FuncNode` がいる可能性は排除していない。
「観測できた唯一の例」に緩める。

### 確認して問題がなかったもの

- レジスタ名 `0x2D5` = `VSH_OPDESCS_CONFIG` / `0x2D6` = `VSH_OPDESCS_DATA` —
  F-114 では記憶で書いていたが、`registers.h` を grep して**裏が取れた**

  `GpuCmd_Advance` の引数が基点からの総バイト数であること — アセンブリと一致
- `0x823F0203` → reg `0x203` extra 35（属性バッファ 12 本 × 3 reg = 0x203..0x226）、
  `0x803F0232` → reg `0x232` extra 3 consec 1 — `int_convert` とビット分解で一致
- 15 本の配列（begin = `+0x0C + 0x10*n`, n = 0..14）— デストラクタと
  `Scene_ResetAllContexts` の 2 経路が完全一致
- `Scene_SubmitNode` の push（`n: 0 → 1`）— 実機で直接観測（F-112）
