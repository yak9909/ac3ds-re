## F-102: ★実機観測でコマンドバッファ構造を確定（初の HIGH）

confidence: **HIGH**（CLAUDE.md の定義どおり**静的解析と動的観測の双方**で確認）

TODO-45。IDA を実機プロセスにアタッチし Suspend 状態で観測した。

### 0. 前提の検証（CLAUDE.md「静的アドレスと実行時アドレスが一致すると仮定しない」）

- `get_process_state()` = **-1（停止）** を自分で確認
- PC = `0x00137064`、SP = `0x00946C70`
- **既知の命令列でビルド同一性を照合**:
  - `0x13149C` = `70 40 2d e9 70 4f 1d ee ...`（`PUSH {R4-R6,LR}` / `MRC p15,0,R4,c13,c0,3`）
  - `0x1280B4` = `0c 10 9f e5 00 20 91 e5 02 00 80 e0 00 00 81 e5 1e ff 2f e1`
  - **両方とも `code_runtime.bin` と完全一致** → 同一ビルド、静的アドレスがそのまま使える
- `GpuCmd_Advance` の `LDR R1,[PC,#0xC]` が指すリテラル `0x1280C8` = **`0x0096EA94`**
  → **`g_GpuCmdPtr` のアドレスが命令エンコードと独立に裏付けられた**

### 1. ★実機の値

| addr | 名前 | 実機の値 |
|---|---|---|
| `0x96EA94` | `g_GpuCmdPtr` | `0x323CE870` |
| `0x96EA98` | `g_GpuCmdEnd` | `0x324B2130` |
| `0xAD995C` | `g_GpuCmdListMgr` | `0x323B20D0` |
| `0xAD9960` | （現在処理中） | `0x3229D06C` |

いずれも `0x32xxxxxx` = 3DS の linear heap 帯。

### 2. ★構造が恒等式で確定

マネージャ（`0x323B20D0`）の実測:

```
mgr[ 0] = 00000002      id
mgr[ 1] = 323B2130      バッファ基底
mgr[ 2] = 00100000      バッファサイズ (1MB)   ★新規特定
mgr[ 3] = 0001C740      現在オフセット
mgr[ 5] = 0001C740      前回提出済みオフセット
mgr[ 6] = 324B2130      GX キュー基底
mgr[ 7] = 00000C00
mgr[ 8] = 0000000C      積んだ数 (12)
mgr[ 9] = 00000000      処理カーソル
mgr[10] = 00000000
mgr[11] = 00000300
```

**恒等式が 2 本とも成立:**

```
mgr[1] + mgr[3] = 0x323B2130 + 0x1C740  = 0x323CE870 = g_GpuCmdPtr  ★
mgr[1] + mgr[2] = 0x323B2130 + 0x100000 = 0x324B2130 = g_GpuCmdEnd  ★
mgr[6]          = 0x324B2130            = 基底 + サイズ（＝バッファ直後に GX キュー）
```

**偶然では成立しない。F-96 / F-101 のレイアウト推定が実機で裏付けられた。**

### 3. ★二重コマンドバッファが実在

`g_GpuCmdListMgr` と `dword_AD9960` が**別オブジェクトを指していた**。
もう一方（`0x3229D06C`）も読むと:

```
mgr2[0] = 00000001      id（もう一方は 2）
mgr2[1] = 3229D0C0      基底
mgr2[2] = 00100000      サイズ（同じ 1MB）
mgr2[3] = 00000020      現在オフセット
mgr2[6] = 3239D0C0      = 基底 + サイズ  ★同じ恒等式が成立
mgr2[7] = 00000C00      mgr[7] と同値
mgr2[8] = 00000002      積んだ数 (2)
mgr2[11] = 00000300     mgr[11] と同値
```

**同一レイアウトの独立した 2 インスタンス（id 1 と 2、各 1MB）。**
`sead::DoubleCmdGameFrameworkCtrNw4c`（F-98）の
**「DoubleCmd」= 二重コマンドバッファという読みが実機で裏付けられた。**

現在 `g_GpuCmdPtr` は id=2 の側（構築中）を指し、
`dword_AD9960` は id=1 の側（提出／処理中）を指している。

### 4. 確度を上げられた項目

以下は **静的 + 動的の双方**で確認できたので `HIGH`:

- `g_GpuCmdPtr`(`0x96EA94`) がコマンドバッファ書き込み位置であること
- `g_GpuCmdEnd`(`0x96EA98`) がその上限であること
- `g_GpuCmdListMgr` の `[1]` 基底 / `[2]` サイズ / `[3]` 現在オフセット /
  `[6]` GX キュー基底 / `[8]` 積んだ数
- 二重コマンドバッファであること
- 実機と `code.bin.i64` / `code_runtime.bin` が同一ビルドであること

### 5. まだ `MEDIUM` のもの

- `mgr[7]`(`0xC00`) / `mgr[11]`(`0x300`) の意味。両インスタンスで同値なので定数らしい
- `mgr[10]` の役割（F-101 で `mgr[9]` と別物と判明したが用途未確定）
- GX 5 本の type バイト（静的には確認済みだが実機で発火を見ていない）
- PICA レジスタ名（`REFERENCES` 由来）

### F-102 追記: ★二重バッファの入れ替えを実機で直接観測

`continue` → 手動 Suspend で 2 回目の標本を取得（`get_process_state()` = -1 を自分で確認）。

**2 つのマネージャポインタが完全に交換されていた:**

| | `g_GpuCmdListMgr`(`0xAD995C`) | `dword_AD9960` |
|---|---|---|
| 1 回目 | `0x323B20D0` (id=2) | `0x3229D06C` (id=1) |
| 2 回目 | **`0x3229D06C` (id=1)** | **`0x323B20D0` (id=2)** |

**入れ替わりを直接観測した。二重コマンドバッファの確定的証拠。**

### `g_GpuCmdEnd` は固定値ではない

| | `g_GpuCmdPtr` | `g_GpuCmdEnd` |
|---|---|---|
| 1 回目 | `0x323CE870` | `0x324B2130` |
| 2 回目 | `0x322B8D60` | **`0x3239D0C0`** |

**★スワップに追随して更新される。** 恒等式は 2 回目でも成立:

```
base + off  = 0x3229D0C0 + 0x1BCA0  = 0x322B8D60 = g_GpuCmdPtr  ★
base + size = 0x3229D0C0 + 0x100000 = 0x3239D0C0 = g_GpuCmdEnd  ★
```

**自前コマンドを積むコードは `g_GpuCmdPtr` / `g_GpuCmdEnd` を
毎回読み直す必要がある。キャッシュすると別バッファを壊す。**

### 1 フレームあたりの実測量

id=1 のバッファのオフセット推移: `0x20` → `0x1BCA0`

- **コマンド量 ≈ `0x1BC80` バイト（113,280）**
- バッファは 1MB (`0x100000`) なので **空き ≈ 900KB**
- GX キューのエントリ数 `mgr[8]` は両標本とも **`0xC`（12）**

**自前のコマンドを足す余地は十分にある。**

### この観測で HIGH になった項目（CLAUDE.md: 静的 + 動的）

- 二重コマンドバッファであり、**フレームごとにスワップする**こと
- `g_GpuCmdEnd` が**マネージャごとの値でスワップに追随する**こと
- `g_GpuCmdPtr` が実際に前進すること（≈113KB/フレーム）
- `mgr[1]` 基底 / `mgr[2]` サイズ / `mgr[3]` オフセット / `mgr[5]` 提出済み /
  `mgr[8]` 積んだ数 の各役割（2 マネージャ × 2 標本で恒等式が成立）
