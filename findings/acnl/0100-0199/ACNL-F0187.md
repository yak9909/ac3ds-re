## F-161: ★★ケーブは `.text` 末尾のゼロ埋めに置く。ただし `.text` へは書けない — `HIGH`（実機の SIGSEGV と復帰で確認）

### 1. `0x01E81000` の頁は boot ごとにマップされたりされなかったりする

これまで全ケーブが使っていた `0x01E81000`-`0x01E81FFF` は、
**再起動後の boot では未マップだった**（全 `0xFFFFFFFF`、書き込みが定着しない）。

1MB 刻みで探索した結果、マップされているのは:

```
0x00100000-0x00C00000   コード像
0x08000000 / 0x0A000000 / 0x0C000000 / 0x10000000
0x30000000 / 0x32000000  ヒープ
```

**`0x01E81xxx` は boot 依存。毎回検証してから使うこと。**

### 2. ★恒久的なケーブ: `.text` 末尾のゼロ埋め `0x00838018`（`0xFE8` バイト）

`code_runtime.bin` を走査して発見。直前が

```
00838008  E128F002  MSR  CPSR_f, R2
0083800C  E12FFF1E  BX   LR
00838010  E3A00000  MOV  R0, #0
00838014  E12FFF1E  BX   LR
00838018  00000000  ← ここからゼロ埋め 0xFE8 バイト
```

直後は `.rodata` らしきデータ。**`.text` 末尾のアライメント埋め。**
同じ頁の先頭に実コードがあるので **RX で実行可能**。

検証:

- ARM の `B`/`BL` でこの範囲を指すもの **0 件**（イメージ全体を走査）
- 値としての出現は `0x0097803C` と `0x00AF6B2C` の 2 件のみ（`.data` 側）
  → **これらを避けて `0x00838080` 以降を使う**（992 ワードがゼロ）
- 実機で読み書き可能（GDB 経由）

### 3. ★★`.text` はプロセスから見て RX。ケーブ内から `.text` へ `STR` すると落ちる

LOG 用に `0x00838200`（`.text` 内）へ `STR R1,[R2],#4` したところ

```
8380A0: got SIGSEGV signal (Segmentation fault) (exc.code b, tid 251)
```

`PC` はまさにその `STR`、`R2 = 0x00838200`、`R12 = 0x10`（ループ 1 回目）。

**GDB 経由では書けるが、ゲーム自身の store は許されない。**
以前 `0x01E81xxx` で通っていたのは、あの領域が RW だったから。

**したがって:**

| 用途 | 置き場所 |
|---|---|
| ケーブのコード | `.text` のゼロ埋め（`0x00838080`〜） |
| リテラル・パラメータ表（**読むだけ**） | 同上で可 |
| **書き込む先**（ログ・観測バッファ） | **`.data`/`.bss` の RW 領域**（例 `0x009B0000`） |

### 4. SIGSEGV からは復帰できる

1. 落ちた命令を含むループを NOP (`MOV R1,R1` = `0xE1A01001`) で潰す
2. `set_reg_val("PC", 次の命令)` で飛ばす
3. **I-cache に古い命令が残る恐れがあるので、修正版は未実行の別番地に作って
   フックを張り替える**（F-155a）。実行中の呼び出しは旧ケーブの残りを走り終える
4. `continue` すると通常どおり動く（`PC` が待機位置 `0x00137064` に戻ることで確認）

`MOV R0,R0` を NOP に使わないこと。**`R0` は cursor を保持している。**
