## F-202: ★★★メインリストの末尾に積んでも UI は描かれない。2 回目のクラッシュの原因 — `HIGH`（実機）

### 1. 何を試したか

F-200 / F-201 の静的解析に基づき、**`Frame_DrawPass1024` の末尾**
（`0x1B72B8` の `BL Frame_EndDrawPass1024` をケーブへ差し替え）に相乗りした。

`GpuCmd_SplitAndSubmit` を避けたのは F-201 の罠
（呼び出し元がカーソル由来の値をキャッシュしている）を踏まないため。
**その回避自体は正しく、同じ形のハングは起きなかった。**

### 2. 結果

| 観測 | 意味 |
|---|---|
| **発火回数 = 120（4 秒 x 30fps でぴったり）** | ケーブは毎フレーム走り、安全確認も通り、コマンドも書けている |
| **何も描画されない** | ★決定的な否定的結果 |
| **メニューを開くとフリーズ** | 記帳と内容がずれた |

### 3. ★★原因 — UI の GPU 状態はサブリストの中にしかない

**UI の状態（ビューポート・シェーダ・フレームバッファ・TexEnv）は、
レイアウトごとの記録リストの中で設定される**（F-200）。
それらは GX キューのエントリとして差し込まれるので、
**メインリストの末尾には UI の状態が残っていない。**

私たちのコマンドは実行されても、**正しい状態が無いので何も見えない。**

**現に動いている版（最初のフラッシュに相乗り）は、
レイアウトの「記録中」に割り込んでいるため状態が整っている。**

### 4. ★設計上の誤り — 「列の末尾＝最前面」はこのゲームでは成り立たない

| 想定 | 実際 |
|---|---|
| 描画コマンドは 1 本の列に順に積まれる | **レイアウトごとに別リストへ記録し、再生で差し込む** |
| 列の末尾に積めば最前面 | **末尾には UI の状態が無い。何も描かれない** |

**「どこに積むか」だけでなく「そこに正しい GPU 状態があるか」を必ず考えること。**

### 5. フリーズの原因（推定）

メインリストへ追記したことで、
`mgr[3]`（現在のオフセット）と `mgr[5]`（最後に提出したオフセット）、
および `GpuCmd_CommitListAndCaptureDelta` が記録済みの範囲との間に
ずれが生じたとみられる。**メニューを開いてレイアウト構成が変わると顕在化した。**

### 6. ★次の方針

**「メインリストの末尾」ではなく「最後に再生されるレイアウトの記録」に入る。**

1. `ssys_ma_lyt_Layout_ReplayRecordedList`（`0x5682DC`）をフックし、
   各フレームで**最後に再生されたレイアウト**を記録する（**読み取りのみ・安全**）
2. そのレイアウトが安定して同じかを確かめる
3. 次フレームで、そのレイアウトの**記録中**（`RecordPaneTree` の内側）に積む

これなら状態は正しく、かつ最前面になる。

### 7. ★手順の教訓

**設計に入る前に必ず `RE/TODO.md` と `RE/FINDINGS.md` を読むこと。**
F-200 で「UI はレイアウトごとに別リストへ記録される」と自分で書いていたのに、
その含意（**状態もサブリストの中にある**）を設計に反映できていなかった。
