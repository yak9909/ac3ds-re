## F-263: ★★★★★F-257 / F-258 の説明は誤りだった。作業配列は Drawer の**固定メンバ**である — `HIGH`（静的）

Drawer（＝drawctx）のコンストラクタ `sub_4D7364`（`nw::font::RectDrawer` 派生）が
作業配列のポインタを**構築時に自分自身の内部へ向けて固定**していた。

```c
*(_DWORD *)(d + 1640) = d + 148;    // 索引配列 = drawctx + 0x094
*(_DWORD *)(d + 1644) = d + 580;    // 行列配列 = drawctx + 0x244
*(_DWORD *)(d + 1648) = d + 1108;   // 幾何配列 = drawctx + 0x454
*(_DWORD *)(d + 1652) = d + 644;    // ★4 本目  = drawctx + 0x284
```

### したがって F-257 の説明は誤りである

F-257 では「`drawctx+1640/1644/1648` はフレームごとに使い回される作業領域で、
記録が走っていないフレームでは中身も寿命も保証されない」と書いた。**これは誤り。**
4 本とも Drawer オブジェクトの内部を指す固定メンバで、プログラムの寿命いっぱい有効である。

F-256 のゲート（ゲームが記録したフレームだけ描く）が実機でフリーズを止めたという
**観測結果そのものは正しい**。誤っていたのは、その理由の説明である。
残る候補は「replay の列に後から積むと GPU 状態（属性構成・TEV・投影）が
そのフレームに対して確立されていない」であり、これは F-259 の
「状態は `DrawBegin1` が記録の先頭で確立する」と整合する。

### F-258（自前バッファ）が画面を壊した理由も説明がつく

我々は `+1640 / +1644 / +1648` の 3 本だけを自前バッファへ向け替え、
**`+1652`（`drawctx + 0x284`）を残した**。4 本は元来 1 つのオブジェクト内に
連続して置かれており、`DrawCtx_FlushBatch` が相対位置を前提にしている可能性が高い。
3 本だけ別領域へ動かせば幾何が壊れる。実機で見えた
「テクスチャが四方向に伸び 45 度傾く」はこれで説明できる。

さらに、配列の `[-4]`（＝ `drawctx + 0x090`）から word0 を復元する処理も、
Drawer の内部メンバを読む前提の処理であり、自前バッファへ持ち込めるものではなかった。

**結論: 作業配列は借り物ではなく、そのまま使ってよい。自前バッファ化は不要かつ有害。**

### 新設計への影響

`PATCHES/cave_node_record.py`（F-259〜F-262）は作業配列をそのまま使い、
`DrawBegin1` を自分で通す。**この方針は本発見と矛盾しない。**
`cave_node_draw_v2_ownbuf.py`（F-258）は理由が分かった以上、二度と使わない。
