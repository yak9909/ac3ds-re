## F-258: 作業配列を自前バッファへ差し替える案は失敗した — `HIGH`（実機・目視）

> **★F-263 で理由が判明した。** 作業配列は 4 本（`+1640/1644/1648/1652`）あり、
> すべて Drawer 内部の連続した領域を指している。3 本だけ別領域へ動かしたので幾何が壊れた。
> `[-4]` から word0 を復元する処理も Drawer 内部メンバ前提だった。**自前バッファ化は不要かつ有害。**


F-257 の対策案 1（頂点／行列／索引の作業配列を自前で持つ）を実装して実機で試した。
`PATCHES/cave_node_draw_v2_ownbuf.py` に保存してある。**採用しない。**

### やったこと

確保済みの `0x4000` を分割して使った（追加確保なし）。

```
0x329D8500 +0x0000 テクスチャ（64x64 LA4）
           +0x1000 索引配列   +0x2000 行列配列   +0x3000 幾何配列
```

描く直前に `drawctx+1640/1644/1648` を自前バッファへ差し替え、
`DrawCtx_FlushBatch` を呼び、直後にゲームの値へ戻す。
配列の `[-4]` にある「フラッシュで潰れる word0 の原本」は
ゲームの配列から一度だけ写した。CPU で書くので `svcFlushProcessDataCache` で `0x4000` を吐き出した。

### 結果

**狙いの半分は達成した。**

- 描画回数が **2 回/フレーム → 3 回/フレーム**になった（F-256 のゲートが外れた）
- 書き込みバイト数は全回 **2072 で一定**（自前バッファ自体は機能している）

**しかし駄目だった。**

- **フリーズは直らない。** 相変わらず「上画面のマテリアルが消えた瞬間」に GPU が止まる
- **実機の画面が乱れた。** 変なテクスチャが四方向に引き伸ばされ、45 度傾く
  （利用者の目視）。上下両画面で発生

### 分かること

画面の乱れは**幾何／行列の中身が壊れている**ことを示す。
配列の word0 を `[-4]` から復元する仕組みはゲームの配列専用であり、
**自前バッファへ単純に持ち込んではいけない**と考えられる。
`[-4]` の値がゲームの配列に固有の情報（オフセットやポインタ）である疑いが強い。

`reg 0x080 = 1`（テクスチャユニット 0 番のみ有効）も同時に入れたが、フリーズは変わらなかった。
したがって**ユニット 1/2 の解放済みテクスチャ説も否定**された。

### 現状の採用版へ戻した

`PATCHES/cave_node_draw.py` は `cave_node_draw_v1_gated.py` と同じ内容
（F-255 / F-256 の到達点）に戻してある。落ちないが、
**レイアウトが記録し直されたフレームしか描けない**という制限が残る。

### 次に検討すべき方向

作業配列の借用をやめる方向は「word0 の意味」を解かないと進めない。
それより、**ゲーム自身と同じ土俵に乗る**方が筋が良い可能性がある。

- 自前ノードに**自分の記録リスト**を持たせ、`Layout_RecordPaneTree` と同じ手順で
  一度記録し、以後は毎フレーム replay する（内容が変わったときだけ記録し直す）
- そうすれば作業配列も GPU 状態もゲームと同じ経路で確立される
- 容量は `GpuCmd_SelectList` が id ごとに管理する（F-236 のバッファ拡張が使える）
