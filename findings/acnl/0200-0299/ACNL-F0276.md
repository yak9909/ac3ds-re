## F-253: ★★★★★描画パスは 3 本。`Frame_DrawPass1040` は下画面ではなく「上画面の右目」 — `HIGH`（静的＋実機の独立 2 系統）

F-252 で「Layout 用のリストは 1 本だけ」「投影は上下とも 400x240」と書いたのは**誤り**である。
実機で `LayoutList_SetDisplay` の出口を観測したところ、**1 フレームに 3 回**呼ばれていた。
`PATCHES/probe_setdisplay_exit.py`（読み取り専用）で確定した。

### 実測（タイトル画面、1000 ms ずつ 3 標本）

出口到達は毎回きっちり 3 等分（例: 総 99 回 = 33 / 33 / 33）。リングに残った戻り先で
呼び出し元まで確定した。

| 実行順 | display | 戻り先 | 関数 | 投影 | レイアウトリスト |
|---|---|---|---|---|---|
| 1 | `0x400` | `0x001B7294` | `Frame_DrawPass1024` → `LayoutMgr_RenderTop` | 400x240 | `mgr+0x04` |
| 2 | `0x410` | `0x005692D0` | `Frame_DrawPass1040` → `LayoutMgr_RenderTopRightEye`(`0x5692B0`) | 400x240 | `mgr+0x04` |
| 3 | `0x401` | `0x00568FCC` | `Frame_DrawPass1025`(`0x1B7090`) → `LayoutMgr_RenderBottom`(`0x568F98`) | **320x240** | **`mgr+0x10`** |

3 本は関数テーブル `0x8E5854` / `0x8E5858` / `0x8E585C` に並んでいる。

### 独立した 2 つ目の結果 — Layout 再生数

`Layout_ReplayRecordedList` の入口でも `Layout+0x134` を読んで display 別に数えた。

```
0x400 = 231   0x410 = 231   0x401 = 264      （33 パスぶん）
1 パスあたり  0x400 = 7.00   0x410 = 7.00   0x401 = 8.00
```

**`0x400` と `0x410` は再生数が完全に一致する。** 同じリスト（`mgr+0x04`）を 2 回再生している
からである。`0x401` だけ数が違うのは別のリスト（`mgr+0x10`）だから。
静的な「投影幅 400 / 400 / 320」「リスト `mgr+4` / `mgr+4` / `mgr+0x10`」と完全に整合する。

したがって **`0x400` と `0x410` は同じ画面（上画面の左目・右目）、`0x401` が下画面**である。

### F-205 の訂正

F-205 は「パス 1024 = 上画面、パス 1040 = 下画面」「再生数 5 / 14」としていた。
`PATCHES/probe_screen_order.py` は**描画パスが 2 本しかない前提**で、
`0x1B71C4` と `0x1B72E4` の入口だけに印を付けていた。3 本目 `0x1B7090` には印が無いので、
**下画面パスの再生が直前の「印 2」に混ざって数えられていた。**

その帳尻も合う。`0x410` の再生数は必ず `0x400` と等しいので、当時 `0x400`=5 なら `0x410`=5、
記録された 14 は `5 + 9`（下画面パス）である。「id 15 に積んだら下画面に出た」という
実機の見た目は正しく、id 15 は**下画面リストのレイアウト**だった。
つまり **F-205 の観測は正しく、パスへの帰属だけが誤っていた。**

### F-252 の訂正

- 「Layout 用のリストは `mgr+4` の 1 本だけ」→ **誤り**。`mgr+0x04` が上画面、
  `mgr+0x10` が下画面。`mgr+0x10` を `TexBufList` と見たのは、`sub_566F44` が
  別のオブジェクトの ctor だったのを取り違えたためである。
  render.txt の `m_LayoutListTop` / `m_LayoutListBottom` という 2 本構成は**本作でも正しい**。
- 「投影は上下とも 400x240 なので下画面は 0.8 倍」→ **誤り**。下画面パスは 320x240 である。
  F-208 が実測した「横 0.8 / 縦 1.0」は、`SetDisplaySize` ではなく
  **相乗り先の Layout 自身が記録した投影**から来ている。数値が偶然一致しただけで、
  因果は別である。**F-252 のこの一致は取り下げる。**
- 「静的にはリストが 1 本なのに F-205 はパスごとに最後が違う」という未解決も、これで解消した。

### ★`LayoutMgr_AddLayout`（`0x56928C`）— 描画順は Layout 自身が持つ優先度で決まる

```c
AddLayout(mgr, layout, screen):
    screen == 0 -> list = mgr + 0x04     // 上画面
    screen == 1 -> list = mgr + 0x10     // 下画面
    それ以外    -> 何もしない
    // loc_566E68: list+4 から node+8 を辿り、
    //   while (node[+0x0C] <= layout[+0x0C]) node = node[+8];
    // の位置へ挿入する（昇順ソート挿入）
```

- **`Layout+0x0C`（バイト）が描画優先度**。値が大きいほど後ろ＝前面。
- リストは各画面のパス末尾で `sead_List_UnlinkAll` により空にされる。
  **つまり Layout は毎フレーム登録し直される。** F-238 / F-239 の
  「固定 id・固定 heap ポインタで対象を選ぶな」はこの構造から来ていた。

### これが自前 GUI に与える設計（次の第一候補）

F-252 で挙げた「`LayoutList_SetDisplay` の出口へ積む」より、**さらに素直な道がある**。

**自前の Layout ノードを毎フレーム `AddLayout` でリストへ入れ、優先度 `0xFF` で末尾に置く。**

- ノードに必要なのは `+0x00` vtable ポインタ、`+0x04` prev、`+0x08` next、
  `+0x0C` 優先度バイト、そして `SetDisplay` が書く `+0x134`（＝0x138 バイト以上確保する）。
- vtable の `+0x08` に自前の replay ケーブを置けば、**その画面の全 Layout の後に呼ばれる**。
  ケーブの中で `ノード+0x134` を読めば `0x400` / `0x410` / `0x401` が分かるので、
  **上下の描き分けも、左目・右目の描き分けも同時に取れる**（ユーザー要件そのもの）。
- vtable の `+0x14`（記録）には安全なスタブ（`BX LR`）を置く。
- 積み先は Layout の記録リスト（容量 `0x1000` 級）ではなく**主リスト**。
  実測の残量は `0xF6000` 以上あり、F-232 の容量超過は構造的に起きない。
- **ゲーム自身が毎フレーム `UnlinkAll` で外してくれる**ので、後始末の破壊が残らない。

**未検証**: 偽の Layout ノードを実機のリストへ入れて安全か、replay ケーブが
主リストへ直接コマンドを積んで正しく提出されるか。F-235 で
`Frame_EndDrawPass1024` の主リスト末尾に積んだときは画面更新が止まっている。
次は**まず何も描かない空のノード**を 1 フレームだけ入れて、
クラッシュしないこと・順序が末尾になることだけを確認する。
