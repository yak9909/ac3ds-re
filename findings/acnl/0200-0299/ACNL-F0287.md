## F-264: 自前ノードの幅・高さは雛形任せにせず画面実寸を明示する — `HIGH`（静的のみ）

`Layout_ReplayRecordedList`（`0x5682DC`）は scissor コマンドの値を
ノード `+0x28` / `+0x2C` の float から `((幅-1)<<16) | (高さ-1)` として組み立てる（F-262）。

`cave_node_record.py` は登録時に**リスト末尾の本物の Layout から 0x50 バイトを写して**
雛形にしている。したがって `+0x28` / `+0x2C` も写し元のレイアウト次第で変わる。
写し元は「その boot で初回登録時にたまたま末尾だったレイアウト」なので**不定**であり、
切り取り範囲が場面によって変わりうる。

**対策**: 登録ケーブで毎フレーム、画面の実寸を明示的に書く。

```
LDR R2,=400.0 (上) / 320.0 (下)   ; 0x43C80000 / 0x43A00000
STR R2,[R1,#0x28]
LDR R2,=240.0                     ; 0x43700000
STR R2,[R1,#0x2C]
```

上画面 400x240・下画面 320x240 は F-253（3 描画パス）で確定した実寸。

### 検証（独立 3 系統が一致）

1. **IDA**（`insn_query`。生成語を `.text` の空き `0x836700` へ一時的に当てて逆アセンブル、
   直後に元バイトへ復元。`idb_save` はしていない）

   ```
   0x836700 MOV R2, #0
   0x836704 STR R2, [R1,#0xFC]
   0x836708 LDR R2, loc_836754      ← PC+0x4C
   0x83670c STR R2, [R1,#0x28]
   0x836710 LDR R2, loc_836758      ← PC+0x48（4 バイト後ろ＝連続する 2 本のリテラル）
   0x836714 STR R2, [R1,#0x2C]
   0x836718 LDR R2, [R1,#0xF8]
   0x83671c CMP R2, #0
   0x836720 MOVNE R2, #1
   ```

2. **`audit_node_cave.py`**: 全 LDR リテラル参照先・分岐先・領域境界・重なり → 総異常 0 件

3. **リテラル値の直接デコード**（導入部 1725/1726 行と同一引数で `build_a` を呼ぶ）

   | ケーブ | 語数 | 幅 | 高 |
   |---|---|---|---|
   | A1（上） | 93 | `0x838AA8` = `0x43C80000` = 400.0 | `0x838AAC` = `0x43700000` = 240.0 |
   | A2（下） | 88 | `0x838C18` = `0x43A00000` = 320.0 | `0x838C1C` = `0x43700000` = 240.0 |

   いずれもケーブ内に収まっている。

### ★この検証で見つけた手順上の落とし穴

最初、検証スクリプトが `build_a` を**導入部と違う引数**で呼んでいた
（A2 を `tail_off=0x0C, clear_mat=True` で作った。正しくは `0x18, False`）。
生成される語数が変わるため、リテラルがケーブ外に見える誤った結果が出た。

**`build_a` のような可変長ジェネレータを検証するときは、
導入部と 1 文字も違わない引数で呼ぶこと。** 引数が違えば別物を検証している。
