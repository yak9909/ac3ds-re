## F-272: F-264〜F-271 の整合監査。独立な結果と突き合わせて 1 件の誤りを訂正し、`SET_PROJECTION` を廃止した — `HIGH`

新しい結論が既存の独立した結果と矛盾しないかを、6 点について確かめた。

### 1. 自前 TEV はゲームの描画を壊さないか — **壊さない**

`Material_EmitState` の 4 モードのテンプレートを全部復号し、**各モードの先頭段が
`PREVIOUS` を読むか**を見た。読んでいれば、その手前の段（＝我々が触った段）が
ゲームの絵に混ざる。

| モード | 触る段 | 先頭段の rgb src0/1/2 | `PREVIOUS` を読むか |
|---|---|---|---|
| 0（`0x97B6EC`） | 5 | `PRIMARY, CONST, CONST` | **読まない** |
| 1（`0x97B704`） | 3,4,5 | `CONST, TEX0, CONST` | **読まない** |
| 2（`0x97B7AC`） | 3,4,5 | `TEX0, TEX1, CONST` | **読まない** |
| 3（`0x97B804`） | 1,2,3,4,5 | `TEX0, CONST, CONST` | **読まない** |

**どのモードでも鎖は途中の段から新しく始まる。** だから
我々が残した段 0〜2 の設定はゲームの出力に影響しない。
逆に、我々は 6 段すべてを書くのでゲームが残した段も上書きされる。**双方向で安全。**

（モード 2/3 は `reg 0x0FD` と `reg 0x0E0`（TEV バッファ）も触るが、
我々の段は `BUFFER` を読まないので無関係。）

### 2. マテリアルの状態キャッシュを我々が壊さないか — **壊さない**

`Material_EmitState` は `drawctx+1698`（前回のモード）が一致すると
**テンプレートを出さず色だけ差し替える**。我々がキャッシュを更新せずに
TEV を書き換えたら、ゲームが「もう出してある」と誤認する恐れがあった。

`sub_4D7274`（DrawBegin1 の本体）を読んで解決した。

```c
*(_DWORD *)(a1 + 1684) = 0;   *(_DWORD *)(a1 + 1688) = 0;
*(_DWORD *)(a1 + 1692) = 0;                 // UV セット数
*(_BYTE  *)(a1 + 1698) = 6;                 // ★マテリアルのモードキャッシュを無効化
*(_BYTE  *)(a1 + 1696) = 1;
TextBox_UpdateDrawState(a1, a2, 0, 0);      // a3=0 → テクスチャキャッシュを無効化するだけ
sub_4D72C4(a1, …);                          // reg 0x06F / 0x080 を出す
```

**`+1698 = 6` は 0/1/2/3 のどれとも一致しないので、
各レイアウトの記録の先頭で必ずフルのテンプレートが出る。**
`TextBox_UpdateDrawState(…, 0, 0)` も `unk_97B74C` の 3 スロットを 0 にして
テクスチャ状態キャッシュを無効化する（コマンドは 1 語も出さない）。

つまり **各レイアウトの記録リストは TEV もテクスチャも自己完結**しており、
我々が GPU 状態を変えても次のレイアウトの replay で作り直される。

### ★ ここで F-268 の裏が取れた

`sub_4B77CC` / `sub_4D7274` が入れる値と、既定ブロックの中身がぴったり対応していた。

| drawctx | 値 | 意味 | 既定ブロックの対応 |
|---|---|---|---|
| `+1696` | 1 | ブレンド/色演算は発行済み | `unk_8ADB10` が `reg 0x100` / `0x101` を出す |
| `+1697` | 1（init 時） | アルファテストは発行済み | `unk_8ADB10` が `reg 0x104` を出す |
| `+1698` | **6（無効）** | マテリアルの TEV は**未発行** | **既定ブロックに TEV 段が無い** |

**キャッシュの初期値と既定ブロックの中身が、独立に同じことを言っている。**
「既定列は TEV を作らない」という F-268 の結論はこれで裏付けられた。

### 3. 描画パス 3 本とビューポート — **F-253 が正しい。F-252 の注釈が誤り**

3 つを全部逆コンパイルした。

```
RenderTop        (0x566DF8) RecordChildren(mgr+4)    → SetDisplaySize(400,240) → SetDisplay(mgr+4, 0x400)
RenderTopRightEye(0x5692B0)                          → SetDisplaySize(400,240) → SetDisplay(mgr+4, 0x410) → UnlinkAll(mgr+4)
RenderBottom     (0x568F98) RecordChildren(mgr+0x10) → SetDisplaySize(320,240) → SetDisplay(mgr+0x10,0x401) → UnlinkAll(mgr+0x10)
```

`0x566DF8` の IDB 注釈に F-252 時代の
「投影幅が両画面 400 なので、実幅 320 の下画面では 1 単位 = 0.8px」が残っていた。
**これは誤りである。** 下画面パスは `SetDisplaySize(0x140, 0xF0)` = **320x240** を使う。
IDB の注釈を訂正した。

### 4. F-208（実機実測）と F-266（静的）の突き合わせ — **一致する**

F-208 の実測は「リスト id 15 のレイアウトは **等方 1 単位 = 1px、原点は画面中央、320x240**」。

F-266 の式は `l = -W/2, r = W/2, t = H/2, b = -H/2`（`W` = Layout+0x28, `H` = Layout+0x2C）。
`W = 320, H = 240` なら `x = ±160` / `y = ±120` が NDC ±1。
下画面パスのビューポートは 320x240 なので **1 単位 = 1px、原点は中央**。
**実測と完全に一致する。**

旧経路の「横 0.8 / 縦 1.0」も同じ式で説明できる。
相乗り先の Layout 自身の `+0x28` が 400 だったなら、
320 幅のビューポートでは `320/400 = 0.8`、高さは両方 240 なので `1.0`。

**つまり原因は「パスの `SetDisplaySize`」ではなく「レイアウトごとの `+0x28`」であり、
F-208 の見出し「レイアウトごとに投影が違う」がそのまま正しい機序だった。**
F-252 で一度この現象をパス側のせいにしたのは二重に誤りだった（値も機序も）。

### 5. `sead_List_UnlinkAll`（`0x133B20`）— 毎フレームの再登録が成立する

```c
v1 = *(list + 4);                       // 先頭
while (v1) { v2 = *(v1+8); *(v1+8) = 0; *(v1+4) = 0; v1 = v2; }
*(list + 4) = 0;  *(list + 8) = 0;      // 先頭・末尾
```

- **各ノードの `+4`（prev）と `+8`（next）が 0 にされる** → 登録ケーブの
  「prev != 0 なら見送る / next != 0 なら見送る」という二重挿入防止が成立する
- **`list+4` = 先頭、`list+8` = 末尾** → 上リスト `mgr+4` の末尾は `mgr+0xC`、
  下リスト `mgr+0x10` の末尾は `mgr+0x18`。
  `build_a` の `tail_off = 0x0C / 0x18` が独立に裏付けられた

### 6. 優先度 `0xFF` が本当に末尾になるか — **なる**

`LayoutMgr_AddLayout`（`0x56928C`）の挿入ループは

```c
while (*(u8*)(v4 + 12) <= *(u8*)(new + 12)) { v4 = *(v4 + 8); if (!v4) return push_back(list, new); }
```

`new[+0x0C] = 0xFF` ならバイト比較は常に真なので、必ず末尾まで歩いて `push_back` する。
**同じ 0xFF が他に無い限り最前面が保証される**（実機でも確認済み。F-254）。
