## F-230: ★★★★相乗り先は「候補のうち最後に再生されたもの 1 つ」。両方に積むと二重になる — `HIGH`（実機）

F-228 で「通常用（id 15 / id 16）とフェード用（id 9 / id 8）の**両方に積む**」ことにした。
フェードには勝てたが、**両方が生きている場面で同じ絵が 2 枚出た。**

> 下の画面のテキストがおかしくなっており、元々のテキストと
> 追加で横に潰された同じテキストが複製されて重なって表示されています。

**フェード用レイアウトは座標系が違う**ので、片方が横に潰れて見える。

### 対策

**候補のどちらでも「同じ 1 つの枠」へ控える。** 最後に再生されたものが残るので、

- 通常時 … id 15 / id 16
- フェードが後に来る場面 … id 9 / id 8

が自動的に選ばれ、**常に 1 枚だけ**、しかも候補の中で最も手前に出る。

### ★順序は場面で入れ替わる

| 場面 | 下画面パスの順 |
|---|---|
| フェード中 | ... id15 → id16 → id8 → id9（**id 9 が最後**） |
| ロード中 | id19 → id9 → **id15**（**id 15 が最後**） |

**固定の優先順位を決め打ちしてはいけない。「最後に再生されたもの」を見ること。**

実機で確認: 上下とも 1 枚だけ、フェード中も残る。

### 残っている制限 — 上画面のロード画像（F-234 で経路確定）

上画面のロード画像に隠れるという見た目の現象は、F-234 のロード画像表示中 trace で
**id 8 の後にロード画像 Layout id 10 が replay されるため**と確定した。
旧「Layout より後の別経路」説は誤りで、同じ `Layout_ReplayRecordedList` 経路だった。
下画面が正常だったという観測自体は維持する。

id 10 の記録リスト残量は `0xD40` しかなく全GUIには不足するため、次候補は
**`Frame_EndDrawPass1024` 入口（描画パス末尾の位置）へ積む**方式。
ただし F-233/F-234 により、通常 submit 点ではなく、現行ケーブも投影を自前確立していない。
まず UI 画像（スプライト）1枚の自然提出版から検証する。
