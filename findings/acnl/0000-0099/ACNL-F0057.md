## F-19 18B キューのスロットは解放されないと枯渇する — `HIGH`

### 構造の裏付け

`0x595EA8`-`0x595EC0` がスロットの確保・初期化を行う:

```
LDR  R1, =0x9AE15C        ; キュー基準
ADD  R0, R4, R4,LSL#3     ; R4*9
ADD  R0, R1, R0,LSL#1     ; = 0x9AE15C + R4*18   ← 基準とエントリサイズの直接の根拠
STRB R4, [R0,#0x10]       ; slot[16] = スロット番号
STRB R1, [R0,#0x0E]       ; slot[14] = 0
STRB R1, [R0,#0x0F]       ; slot[15] = 0         ← 解放
```

実測でも `slot[16]` は 0/1/2/3 とスロット番号に一致し、
インデックス計算コードから読んだ解釈と独立に噛み合う。

### `slot[15]` の意味

| 値 | 設定箇所 |
|---|---|
| 0 | `0x595EC0`（空き） |
| 1 | `0x59E674`（`Player_StartFieldAction` が確保） |
| 2 | `0x59E968`（`FieldAction_Dispatch` case 1） |
| 3 | `0x59E988`（`FieldAction_Dispatch` case 2） |

`Player_StartFieldAction` の空き探索は `slot[15] == 0` のみを空きとみなす
(`0x59E5D4 : LDRB R2,[R2,#0xF]`)。4 スロットすべて非 0 になると `-1` を返す。

### 解放されない

`0x595EC0` の解放は `sub_59E068`（`0x59E068`-`0x59E0D8`）が返したスロットに対して行う。
`sub_59E068` は**使用中スロットのうち `slot[14]`（actionID）が
`{2, 4, 5, 21, 23, 24, 25, 26}` のものだけ**を返す。
**19（掘る）はこの集合に含まれない。**

実機観測（セッション2）:

```
slot0  actionID=19  [12]=19 [13]=84   [15]=3 [16]=0 [17]=0x0C
slot1  actionID=19  [12]=19 [13]=136  [15]=3 [16]=1 [17]=0x0C
slot2  actionID=19  [12]=19 [13]=156  [15]=3 [16]=2 [17]=0x0C
slot3  actionID=19  [12]=19 [13]=152  [15]=3 [16]=3 [17]=0x0C
```

**3 秒間 Resume しても 4 スロットは 1 バイトも変化しなかった。**
`[15]=3` は恒久的に残る。これが「三つ掘ると掘れなくなる」の直接原因。

手動で `slot[14]=0, slot[15]=0` を書けば空き状態に戻せる
（`0x595EBC`-`0x595EC0` と同じ操作）。

### 訂正: 解放経路は存在する

**実機で確認済み。** ケーブを外した状態で何度も掘った後にキューを読むと、
4 スロットとも `[15]=0`（空き）に戻っており、`slot0` は新しい掘りで
`[12]=65 [13]=33 [17]=0x00` に更新されていた。

したがって actionID=19 のスロットも解放される。
`0x590000`-`0x5B0000` の `STRB [Rn,#0xF]` 走査で見つからなかったのは、
**走査範囲外にあるか `STRH [Rn,#0xE]` 等で `[14]`/`[15]` を同時にクリアしている**ため。
解放コードそのものの特定は未了だが、3x3 の実装には支障しない。

**F-19 で観測した滞留は通常動作ではなく、壊れたケーブが原因だった（F-20 を参照）。**
