## F-20 【訂正】滞留の原因は PUSH 後のスタック引数のずれ — `HIGH`

**当初「滞留 4 件は `0x598688` 由来ではない」と結論したが、これは誤り。**
実際にはケーブ自身が壊れた引数で呼んでいたものだった。

### 誤りの発端

`slot[17]` は `Player_StartFieldAction` が a7..a11 から**全ビット組み立て直す**
（`0x59E624`-`0x59E690`。`0x01|0x02|0x1C|0x20|0xC0 = 0xFF` をすべて置換）:

```
slot[17] = (a7 & 1) | ((a8<<1) & 2) | ((a9<<2) & 0x1C)
         | ((a10<<5) & 0x20) | ((a11<<6) & 0xC0)
```

`0x598688` は a7..a11 をすべて R7(=0) で渡すので `slot[17] = 0` になるはず。
実測が `0x0C` だったため「別の呼び出し元」と判断してしまった。

### 真の原因

**`PUSH` で SP を下げた状態で `BL` すると、呼び出し先が読むスタック引数は
「その時点の SP+0」から始まる。**

ケーブは `PUSH {R0-R6,LR}` (32B) の後、元の引数領域 `[SP+0x20]` を書き換えて
呼んでいたが、`Player_StartFieldAction` が実際に読んだのは `SP+0` 以降、
すなわち**保存した R0-R6,LR そのもの**だった:

| 引数 | 実際に渡った値 | 実測との対応 |
|---|---|---|
| a5 (X) | 保存した R0 = **actionID = 19** | `[12]=19`（4 件とも同じ理由） |
| a6 (Y) | 保存した R1 = 対象item ポインタ | `[13]`=84/136/156/152（下位バイト） |
| a7 | 保存した R2 = 結果item ポインタ | `[17]` bit0 |
| a8 | 保存した R3 = `0x955FF4` | `[17]` bit1 |
| a9 | 保存した R4 = centerX = 19 | `(19<<2)&0x1C = 0x0C` ✓ |
| a10 | 保存した R5 = centerY | `[17]` bit5 = 0 → Y は偶数 |
| a11 | 保存した R6 = X+1 = 20 | `(20<<6)&0xC0 = 0` ✓ |

`[17] = 0x0C` の**全ビットが説明できる**。

でたらめな座標 (X=19=actionID, Y=ポインタ下位バイト) の掘削要求がキューに積まれ、
`sub_59EC9C` が不成立と判断して case 2 → `slot[15]=3` に落とし、
そのまま解放されずに 4 スロットを埋めた。これが「三つ掘ると掘れなくなる」の正体。

### 修正

スタック引数は書き換えるのではなく、`SUB SP,SP,#28` で**引数領域を作り直して**積む。
中心マスは元の引数領域を一切触らないままテールジャンプするので完全に元通りになる。

### 教訓

`0x598688` からの正常な呼び出しでは実測 `[17] = 0x00` であり、
**F-15 の「a7..a11 = 0」は実機で裏付けられた**。
`slot[17]` は解放時（`0x595EBC`-`0x595EC0` は `[14]`/`[15]` のみ書く）に
クリアされないので、**空きスロットの `[17]` を見ても意味がない**。
