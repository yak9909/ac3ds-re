## 結論

再解析で確認。`LayoutMgr_AddLayout` は screen=0 を `mgr+4`、1 を `mgr+0x10` へ振り分け、他は何もしない。正常な未所属 node を `Layout+0x0C` の符号なしバイト優先度で昇順に挿入する。同値では後から登録したものが後ろになり、再生巡回もその順に進む。

確度 MEDIUM：符号なし比較とリンク挿入の命令、独立した再生巡回・ゲーム自身の登録呼出しが整合する。実画面の重なりは未追試。

## 根拠

一次証拠：`_local/evidence/16/ida-primary.txt`、`ida-followup.txt`。

- `0x56928C..0x5692AC` は screen の0/1だけを受け、挿入本体 `0x566E68` へ分岐する。
- `0x566E74` は新 node の `LDRB R3,[R2,#0xC]`、`0x566E7C` は既存 node の `LDRB R12,[R1,#0xC]`。`0x566E80` の比較後、`0x566E84 BLS 0x566E8C` なので既存値 **<=** 新規値なら進む。`0x566E8C` で next を読み、nullなら `0x13F84C`（PushBack）。既存値が大きい位置では `0x566E88` から `0x56A7F8` へ分岐して直前へ挿入する。
- `0x56A824..0x56A834` は先頭への挿入、`0x56A854..0x56A868` は既存 node の prev と新規 node の prev/next をつなぎ、前の node の next も更新する。従って同値の全既存 node を通過してから挿入される。
- `0x566E38` が head、`0x566E58` が next を読む再生巡回なので、優先度の昇順・同値の登録順がそのまま vslot `+8` の呼出し順になる。
- `0x13F84C..0x13F85C` は新規 node の next/prev が両方ゼロでなければ PushBack を見送る。ただし唯一の所属 node は両方ゼロなので、この検査だけでは二重登録を防げない。また中間挿入 `0x56A854` には同じ検査がない。AddLayout 全体に完全な所属検査があるとは言えない。
- 下パス入口 `0x1B7090` より後、`0x1B70F0` は `0x2E3190` を呼び、`0x2E31A8` で下、`0x2E31BC` で上へ登録する。さらに `0x1B70FC` → `0x60B930` は条件付きで上へ登録する。`RenderBottom` はその後の `0x1B7114`。パス入口と再生直前では登録済み集合が違い得る。
- 上の Frame 関数は Layout 再生から戻った後にも `0x1B729C` / `0x1B7380` で `Render_DrawScene1` を呼ぶ。「最後の Layout」と「そのパスの最後の描画処理」も同一ではない。
